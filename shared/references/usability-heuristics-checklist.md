# Nielsen 十大可用性启发式原则检查清单

> 用于代码审查与启发式评估（Heuristic Evaluation）的速查手册。
> 每条原则包含定义、代码审查检查点、常见违反模式、严重度指引和关联原则。

---

## 速查表

| # | 原则名称（中文） | Principle Name（English） |
|---|---|---|
| 1 | 系统状态可见性 | Visibility of System Status |

| 3 | 用户控制权与自由度 | User Control and Freedom |
| 4 | 一致性与标准 | Consistency and Standards |

| 10 | 帮助与文档 | Help and Documentation |

## 原则 1：系统状态可见性（Visibility of System Status）

### 定义

系统应当在合理的时间内，通过清晰的反馈让用户始终了解当前正在发生什么。用户在执行任何操作后都应得到即时响应，避免"我点了到底有没有用？"的困惑。状态反馈是信任的基础——没有反馈，用户会怀疑系统是否崩溃。

### 代码审查检查点

- [ ] 每个异步操作（API 调用、文件上传、表单提交）是否都有 loading 状态？
- [ ] 操作完成后是否有成功/失败的明确反馈（toast、状态变更、页面跳转）？
- [ ] 长耗时操作是否展示了进度指示器（progress bar、百分比、步骤条）？
- [ ] 列表/数据加载是否区分了 loading / error / empty / success 四种状态？
- [ ] 网络请求失败时是否向用户展示了可读的错误信息而非空白页？
- [ ] 按钮在提交过程中是否被 disabled 以防止重复提交？
- [ ] 文件上传是否展示了上传进度和完成状态？
- [ ] 轮询 / WebSocket 连接断开时是否通知了用户？

### 常见违反模式

1. **静默失败**：API 请求失败后页面没有任何提示，用户看到的是空白或旧数据
2. **幽灵按钮**：点击按钮后按钮无反应、不变灰、不 loading，用户不知道操作是否已触发
3. **薛定谔的表单**：提交表单后页面既不跳转也不提示成功，用户反复点击
4. **假死列表**：数据列表在加载时不显示 skeleton 或 spinner，看起来像没数据

### 严重度指引

- **灾难级**：支付/提交类操作无反馈——用户不确定钱是否付了、订单是否提交了
- **严重**：核心流程（注册、登录）的状态不明确导致用户反复操作
- **中等**：非关键区域的加载状态缺失，如设置页的次要选项
- **轻微**：装饰性动画的缺失，不影响功能理解

### 关联原则

- → 原则 9（错误恢复）：反馈不仅包含成功，也包含错误状态的传达
- → 原则 6（识别而非回忆）：状态可见减少用户记忆负担
- → 原则 5（错误预防）：loading 状态可防止用户因不确定而重复操作

## 原则 2：系统与现实匹配（Match Between System and the Real World）

### 定义

系统应当使用用户的语言，遵循现实世界的惯例和文化规范，以自然且符合逻辑的顺序呈现信息。界面中的概念模型应当映射用户的心智模型，而非系统的技术实现模型。技术术语对普通用户而言毫无意义。

### 代码审查检查点

- [ ] 错误信息是否使用用户能理解的语言，而非技术堆栈信息（如 "Error 500: ECONNREFUSED"）？
- [ ] 日期、时间、货币格式是否遵循用户所在地区的本地化惯例？
- [ ] 图标和隐喻是否符合目标用户的文化认知（如垃圾桶=删除、信封=邮件）？
- [ ] 业务术语是否与用户日常使用的词汇一致（而非数据库字段名）？
- [ ] 表单字段的标签是否使用了用户语言而非技术缩写？
- [ ] 操作顺序是否符合现实世界的逻辑（如先选目的地再选出发日期）？
- [ ] 是否避免了面向开发者的内部编号、ID 作为用户可见标识？

### 常见违反模式

1. **技术报错暴露**：用户看到 "TypeError: Cannot read property 'map' of undefined" 而非 "数据加载失败，请重试"
2. **数据库字段名泄露**：表单标签显示 "usr_nm" 而非 "用户名"
3. **违反物理直觉**：删除操作没有"回收站"概念，直接永久消失且无确认
4. **文化不匹配**：面向中国用户的界面使用英制单位或不熟悉的西方隐喻

### 严重度指引

- **灾难级**：错误信息完全无法理解，用户不知道发生了什么也不知道该怎么办
- **严重**：核心流程中的术语混淆导致用户做出错误操作（如把"归档"理解成"删除"）
- **中等**：日期格式不符合习惯但可通过上下文推断
- **轻微**：个别非关键文案措辞不够自然但不影响理解

### 关联原则

- → 原则 9（错误恢复）：错误信息使用用户语言是恢复的前提
- → 原则 4（一致性与标准）：现实匹配包含遵循行业/平台惯例
- → 原则 6（识别而非回忆）：现实隐喻帮助用户识别而非回忆技术细节

## 原则 3：用户控制权与自由度（User Control and Freedom）

### 定义

用户常常会误操作，他们需要明确的"紧急出口"来离开不想要的状态。支持撤销（undo）和重做（redo）能让用户大胆探索界面而不必担心犯错。紧急出口应当显眼且随时可用。

### 代码审查检查点

- [ ] 破坏性操作（删除、清空、覆盖）是否有二次确认弹窗？
- [ ] 是否实现了撤销（undo）功能，至少在关键操作中（如删除、批量修改）？
- [ ] 用户是否可以中途取消正在进行的长流程（如多步表单、文件上传）？
- [ ] 弹窗/模态框是否可以通过 ESC 键、点击遮罩或关闭按钮退出？
- [ ] 导航是否支持返回上一级（浏览器后退、面包屑、返回按钮）？
- [ ] 自动保存或草稿功能是否存在于长表单中？
- [ ] 用户是否可以关闭/跳过非必要的引导或弹窗？
- [ ] 全屏/沉浸式模式是否有明确的退出方式？

### 常见违反模式

1. **死亡对话框**：模态弹窗没有关闭按钮，只能点击"确认"才能继续
2. **不可逆删除**：删除操作没有确认、没有撤销，数据永久丢失
3. **强制流程**：多步向导没有"跳过"或"返回"选项，用户被困在中间步骤
4. **劫持导航**：页面阻止浏览器后退按钮或强制重定向

### 严重度指引

- **灾难级**：误操作导致数据永久丢失且无法恢复（如清空数据库无确认）
- **严重**：核心流程中无法退出或返回，用户被迫完成不想要的操作
- **中等**：缺少撤销功能但可以通过其他方式补救（如重新添加已删除项）
- **轻微**：非关键弹窗的关闭方式不够便捷

### 关联原则

- → 原则 5（错误预防）：确认对话框同时服务于错误预防和用户控制
- → 原则 1（系统状态可见性）：退出路径的可见性本身也是状态反馈
- → 原则 7（灵活性与效率）：紧急出口对新手尤其重要

## 原则 4：一致性与标准（Consistency and Standards）

### 定义

用户不应该猜测不同的词汇、情境或操作是否意味着相同的事情。遵循平台惯例和行业标准和用户预期保持一致。内部一致性（同一产品内相同功能使用相同设计）和外部一致性（与行业/平台标准保持一致）都至关重要。

### 代码审查检查点

- [ ] 同一组件在不同页面中是否使用相同的 props / 样式 / 交互行为？
- [ ] 相同功能是否使用了相同的术语（如"删除"不要有时叫"移除"有时叫"清除"）？
- [ ] 颜色语义是否一致（如红色=危险/删除，绿色=成功，蓝色=链接）？
- [ ] 交互模式是否一致（如所有表格的排序、筛选、分页行为是否相同）？
- [ ] 是否遵循了所用 UI 框架的设计规范（如 Material Design、Ant Design、HIG）？
- [ ] 快捷键是否在不同页面中保持一致？
- [ ] 图标含义是否全局统一（同一个图标不要在不同地方代表不同功能）？

### 常见违反模式

1. **术语混乱**：同一概念在不同页面叫不同名字（"提交"/"确认"/"发送"/"确定"）
2. **样式漂移**：相同类型的按钮在不同页面大小、颜色、圆角各异
3. **交互不一致**：有些表格点击行跳转详情，有些需要点专门的链接
4. **违反平台惯例**：macOS 应用使用了 Windows 风格的关闭按钮位置

### 严重度指引

- **灾难级**：核心操作的行为不一致导致用户频繁误操作（如"确认"有时提交有时只是校验）
- **严重**：同一组件在不同场景表现不同，用户需要重新学习
- **中等**：文案术语不统一，增加认知负担但不导致错误
- **轻微**：纯视觉层面的细微不一致（如间距差异 2px）

### 关联原则

- → 原则 2（系统与现实匹配）：外部一致性就是与现实世界标准匹配
- → 原则 6（识别而非回忆）：一致性让用户识别模式而非回忆每个页面的特殊规则
- → 原则 8（美学与极简设计）：一致性减少视觉噪音

## 原则 5：错误预防（Error Prevention）

### 定义

最好的错误信息是"在错误发生之前就防止它"的设计。应当消除容易出错的条件，或在用户操作前提供确认。分为两类：slip（执行层面的小失误，如打字错误）和 mistake（心智模型错误，如误解了按钮的功能）。

### 代码审查检查点

- [ ] 表单是否有实时输入验证（格式校验、长度限制、必填检查）？
- [ ] 危险操作（删除、覆盖、批量修改）是否要求二次确认？
- [ ] 不可逆操作前是否明确告知了后果？
- [ ] 输入框是否有合适的 input type（email、number、tel）和 placeholder 引导？
- [ ] 是否限制了不合理输入（如日期选择器不允许选择过去日期用于"出发日期"）？
- [ ] 搜索框是否做了防抖（debounce）以避免无效请求？
- [ ] 密码字段是否有强度提示和格式要求说明？
- [ ] 是否防止了常见的数据录入错误（如多余空格、大小写不一致）？

### 常见违反模式

1. **延迟报错**：表单填了 10 个字段，提交后才告诉你第一个字段格式不对
2. **无保护的危险操作**：一个按钮就能删除整个项目，没有确认
3. **模糊的输入域**：文本框没有任何格式提示，用户猜该填什么
4. **静默截断**：输入超出长度限制时被静默截断，用户不知道数据丢失

### 严重度指引

- **灾难级**：缺乏预防导致不可逆的严重后果（如误删生产数据、误转账）
- **严重**：频繁出现可预防的输入错误，严重影响效率
- **中等**：错误可以修复但带来不便（如提交后才发现格式错误）
- **轻微**：错误容易发现且修正成本低

### 关联原则

- → 原则 3（用户控制权）：撤销功能是错误预防的最后一道防线
- → 原则 9（错误恢复）：当预防失败时，恢复机制变得关键
- → 原则 1（系统状态可见性）：实时验证反馈是状态可见性的体现

## 原则 6：识别而非回忆（Recognition Rather Than Recall）

### 定义

让元素、操作和选项随时可见，最小化用户的记忆负担。用户不应该需要记住从一个界面到另一个界面的信息。可见的提示比需要记忆的内容更有效。系统应当提供"再认"的线索而非要求"回忆"。

### 代码审查检查点

- [ ] 导航菜单是否清晰可见，用户不需要记住页面层级结构？
- [ ] 搜索历史、最近操作、浏览记录是否可被展示以减少回忆负担？
- [ ] 表单是否在当前步骤可见之前步骤已填写的内容（如订单确认页）？
- [ ] 可用操作是否在上下文中直接展示，而非藏在需要记忆的快捷键中？
- [ ] 错误信息是否明确指出了出错位置，而非让用户自己找？
- [ ] 面包屑导航是否存在于深层页面中？
- [ ] 对象名称/ID 在操作时是否可见（如删除时显示名称而非 "确认删除 #10086"）？
- [ ] 工具提示（tooltip）是否在需要时提供了额外的说明信息？

### 常见违反模式

1. **隐藏导航结构**：用户必须记住"那个功能在哪个菜单下"
2. **无上下文的表单**：多步表单的后几步看不到前面填了什么
3. **神秘编号**：操作确认只显示 ID 不显示名称，用户不知道在操作什么
4. **记忆型快捷键**：必须记住快捷键才能高效操作，没有可见的替代方式

### 严重度指引

- **灾难级**：用户完全迷失在系统中，无法找到返回或继续的路径
- **严重**：核心流程需要用户记住大量信息才能完成
- **中等**：缺少辅助记忆的工具（如搜索历史），降低了效率
- **轻微**：偶发的信息不可见，但用户可通过简单探索找回

### 关联原则

- → 原则 1（系统状态可见性）：状态可见就是减少回忆负担
- → 原则 4（一致性与标准）：一致性让用户识别模式
- → 原则 8（美学与极简设计）：过度隐藏信息以追求"简洁"反而违背此原则

## 原则 7：使用灵活性与效率（Flexibility and Efficiency of Use）

### 定义

系统应当同时满足新手和专家用户的需求。为 frequent users 提供加速器（快捷键、自定义、批量操作），同时保持对新手友好的引导。灵活的设计能让更多用户以自己的方式高效完成任务。

### 代码审查检查点

- [ ] 是否提供了键盘快捷键用于高频操作？
- [ ] 批量操作是否被支持（如批量选择、批量删除、批量导出）？
- [ ] 高级用户是否可以跳过引导/教程直接操作？
- [ ] 是否支持自定义（如布局调整、常用功能置顶、筛选器保存）？
- [ ] 搜索是否支持高级语法（如过滤器、布尔运算）以满足专家用户？
- [ ] 是否有"快速操作"入口（如命令面板 Command+K、右键菜单）？
- [ ] 新手引导是否可以被关闭且不再显示？

### 常见违反模式

1. **只有鼠标路径**：所有操作只能通过点击完成，没有快捷键
2. **逐一操作**：必须一个一个处理，没有批量操作能力
3. **强制引导**：每次进入都弹出教程，无法永久关闭
4. **一刀切界面**：新手和专家被迫使用完全相同的交互路径

### 严重度指引

- **灾难级**：极少——缺乏灵活性很少导致完全无法使用
- **严重**：高频操作效率极低，严重影响生产力工具的核心价值
- **中等**：缺少批量操作等便利功能，增加重复劳动
- **轻微**：仅缺少锦上添花的快捷功能

### 关联原则

- → 原则 3（用户控制权）：灵活性的本质是给用户更多控制
- → 原则 8（美学与极简设计）：加速器不能以牺牲界面简洁为代价
- → 原则 6（识别而非回忆）：快捷键需要配合可见的提示（如 tooltip 展示快捷键）

---

## 原则 8：美学与极简设计（Aesthetic and Minimalist Design）

### 定义

界面不应当包含用户不需要或很少需要的信息。每一份额外的信息都会与相关信息竞争，降低相对可见性。简洁不是"少"，而是"恰到好处"——去掉一切不服务于用户目标的内容。

### 代码审查检查点

- [ ] 页面是否只展示了当前任务所需的信息，没有无关内容？
- [ ] 弹窗/模态框是否只包含必要的信息和操作选项？
- [ ] 是否避免了过长的说明文字（考虑用图示或渐进式展示替代）？
- [ ] 错误信息是否简洁明了，没有大段技术描述？
- [ ] 是否避免了"以防万一"而添加的功能按钮或信息？
- [ ] 视觉层次是否清晰（重点突出、次要信息弱化）？
- [ ] 空状态页面是否有意义且简洁（而非仅显示"暂无数据"）？

### 常见违反模式

1. **信息过载**：Dashboard 堆砌几十个指标，用户找不到真正重要的
2. **弹窗轰炸**：一个操作触发连续多个弹窗，每个都"很重要"
3. **防御性文案**：错误信息写了三段话解释技术原因，用户只需要知道"怎么办"
4. **功能膨胀**：工具栏塞了 30 个按钮，常用的只有 3 个

### 严重度指引

- **灾难级**：极少——信息过多很少导致完全无法使用
- **严重**：关键信息被噪音淹没，导致用户做出错误判断
- **中等**：界面杂乱增加认知负担，降低操作效率
- **轻微**：纯美学层面的不够精致

### 关联原则

- → 原则 6（识别而非回忆）：简洁的界面更容易识别
- → 原则 4（一致性与标准）：一致性本身减少视觉噪音
- → 原则 7（灵活性与效率）：简洁与功能丰富之间的平衡

---

## 原则 9：帮助用户识别、诊断和恢复错误（Help Users Recognize, Diagnose, and Recover from Errors）

### 定义

错误信息应当使用通俗语言（避免错误代码），精确指出问题所在，并建设性地建议解决方案。好的错误信息遵循三段式：发生了什么 → 为什么发生 → 下一步怎么办。让用户在 3 秒内理解错误并知道如何修复。

### 代码审查检查点

- [ ] 错误信息是否包含三个要素：问题描述 + 原因 + 解决建议？
- [ ] 是否避免了技术术语和错误代码（或同时提供人类可读的解释）？
- [ ] 表单验证错误是否精确定位到出错的字段？
- [ ] 网络错误是否提供了重试选项？
- [ ] 权限错误是否告知了用户应该联系谁或如何获取权限？
- [ ] 错误信息是否使用了建设性语气（"请..."而非"你不能..."）？
- [ ] 全局错误（如 500）是否有用户友好的 fallback 页面？
- [ ] 错误日志是否同时记录了技术细节（供开发者调试）和用户信息？

### 常见违反模式

1. **裸错误码**：只显示 "Error 404" 或 "ERR_NETWORK"，没有任何解释
2. **推卸责任**：错误信息暗示是用户的错（"输入格式不正确" 但不告诉正确格式）
3. **死胡同**：告知出错了但不提供任何下一步操作选项
4. **技术天书**：错误信息包含 stack trace 或 SQL 语句

### 严重度指引

- **灾难级**：关键流程出错时用户完全无法理解也无法继续（如支付失败无说明）
- **严重**：错误频繁发生且恢复路径不明确
- **中等**：错误信息不够友好但用户最终能猜到如何解决
- **轻微**：错误信息措辞可以优化但不影响功能恢复

### 关联原则

- → 原则 2（系统与现实匹配）：错误信息必须使用用户语言
- → 原则 5（错误预防）：最好的错误处理是预防
- → 原则 1（系统状态可见性）：错误状态也是系统状态的一部分
- → 原则 3（用户控制权）：恢复选项给用户控制权

## 原则 10：帮助与文档（Help and Documentation）

### 定义

虽然最好的设计是不需要帮助就能使用的，但帮助文档仍然是必要的。帮助文档应当易于搜索，以用户任务为导向，列出具体步骤，且不要过于庞大。好的帮助在用户需要的上下文中出现（contextual help），而非藏在独立的文档中心。

### 代码审查检查点

- [ ] 是否在复杂功能旁边提供了上下文相关的帮助（tooltip、侧边帮助面板）？
- [ ] 空状态页面是否包含引导信息（"如何开始"、操作指引）？
- [ ] 首次使用的功能是否有简短的引导说明？
- [ ] 帮助内容是否可以被搜索到？
- [ ] 表单字段是否有 placeholder 或 helper text 说明期望的输入格式？
- [ ] 键盘快捷键是否有查看入口（如帮助菜单中的快捷键列表）？
- [ ] 帮助文档是否使用了用户的语言而非技术术语？
- [ ] 404 页面是否提供了导航帮助（搜索框、常用链接）？

### 常见违反模式

1. **帮助失踪**：有帮助入口但点进去是空的或过时的
2. **文档孤岛**：帮助文档与产品完全脱节，用户需要切换到另一个网站查找
3. **技术文档面向开发者**：帮助内容充满了技术术语，普通用户看不懂
4. **缺少上下文帮助**：所有帮助都在一个巨大的 FAQ 页面，用户需要自己找

### 严重度指引

- **灾难级**：核心功能复杂到没有文档完全无法使用，且没有引导
- **严重**：用户频繁卡住但找不到帮助
- **中等**：帮助存在但不够 contextual，需要用户主动搜索
- **轻微**：帮助文档的措辞或排版可以优化

### 关联原则

- → 原则 2（系统与现实匹配）：帮助文档也要使用用户语言
- → 原则 6（识别而非回忆）：上下文帮助让用户在操作现场获得提示
- → 原则 8（美学与极简设计）：帮助应当渐进式展示，不要一次性倾倒
