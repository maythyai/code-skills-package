# 编码期反模式与模块化拆分参考

> 本文件集中**编码阶段（05 实施）就应警惕**的常见编程反模式，重点是"如何在写代码时
> 就避免，而不是等 06/07 审查才发现"。每条给：症状 → 为何发生 → **编码期预防规则** →
> 检测信号 → 修复。供 `prompts/05-implementation.md` §七「工程规范基线」与 §十二反模式表
> 引用；`csp-code-reviewer` / `csp-codebase-audit` / `07-reviewer` 的 B 维度也复用同一判定。

## 0. 总原则：设计在前，拆分在后，但边界在编码前定

- **先定边界再写码**：每个新文件/类/模块动手前先写一行"它只负责什么"作为职责契约；写的过程中
  发现"还要管别的" → 停下，要么拆新文件，要么更新职责契约，不默默扩张。
- **拆分不是事后补救**：god file 是"每次顺手加一点"累积出来的——编码时一旦发现某文件开始承担
  第二个不相关职责，立刻拆，不留给"以后重构"。
- **阈值是触发器不是目标**：下列 LOC/方法数/复杂度阈值是"该停下来审视"的信号，不是"必须压到
  阈值以下"的硬指标；达标但职责单一的大文件（如生成代码、长配置表）不必强拆。

## 1. 模块化与文件组织（god file / god class / god module）

### 1.1 God file / God class / God module

**症状**：单个文件/类承担多个不相关职责；"什么都知道、什么都改"；改一个业务点要动这个文件；
merge 冲突反复集中在此文件。

**为何发生**：每次"顺手加一点"——新功能不新建文件，往既有文件塞；怕"文件太多"；没有模块边界
意识，把"相关"等同于"放一起"。

**编码期预防规则**：
1. **一文件一职责契约**：新建文件先写一行职责说明（docstring/头注释）；写入第二类职责时**立即拆**。
2. **新功能默认新文件**，除非它明显属于既有模块的同一职责；"放进来更省事"不是理由。
3. **命名驱动职责**：类/文件名应能预测其内容；若名字需要"和"连接（如 `OrderAndUser`）→ 已是 god，
   拆。
4. **动手时问三个问题**：这段逻辑改动的频率与谁一致？它依赖谁、被谁依赖？如果把它移走，本文件
   是否还能独立成立？移走不痛 → 该移。

**检测信号**（触发审视，非定罪）：
- 单文件源码 > 400 行（业务代码；生成代码/配置表/聚合 index 不适用）。
- 单类公共方法 > 10 个，或方法名跨 ≥2 个业务域（如 `createOrder` + `sendNewsletter` + `exportReport`）。
- 文件 import 的业务域 ≥ 3 个不相关域。
- 改动该文件的 commit 频率显著高于其他文件，且 commit 主题跨多个域。

**修复**：
1. **按职责切面**：用职责而非技术层切（"订单" vs "用户"），不是"工具" vs "业务"。
2. **先抽接口再搬代码**：把要移走的部分抽成明确接口，新文件实现接口，原文件持有引用——避免
   搬动时撕裂共享状态。
3. **小步原子提交**：一次只移一个职责，每步可编译可测；不一次性大爆炸重构（与 05「顺手重构」
   反模式冲突时，**拆 god file 算计划内工作**，需先回 04 建 task，不混入功能提交）。
4. **移完删原**：搬空的职责从原文件删除，不留"备份注释代码"。

### 1.2 巨石函数（god method）

**症状**：单函数 > 80 行 / 圈复杂度 > 10 / 嵌套 > 4 层；无法用一句话描述它做什么（要用"然后…然后…"）。

**为何发生**：把一个完整流程塞进一个函数"看着清楚"；不想抽小函数因为"就这一次"。

**编码期预防规则**：
1. **函数名 = 一句话职责**：写不出一句话函数名 → 函数在做 ≥2 件事 → 拆。
2. **嵌套 ≥ 3 层触发审视**：用早返回（guard clause）压平；`if-else if-else if` 链 ≥ 3 分支 →
   考虑策略表/多态。
3. **参数 ≤ 4**：超 4 个参数大概率是"该有一个参数对象"或"该拆函数"；布尔参数尤其危险（通常
   说明函数做两件事）。

**修复**：按"步骤"拆——每个步骤一个命名良好的小函数；步骤间用清晰的顺序/流水线组合；保留主函数
作为"编排者"只读步骤不实现细节。

### 1.3 过度拆分（反向反模式）

**症状**：每个函数 2-3 行、跨 5 个文件才能追完一个简单流程；"包装层"比逻辑多。

**为何发生**：把"拆分好"当目标，为拆而拆；教条执行阈值。

**预防**：拆分是为了**降低理解成本**，不是为了达标。如果一个函数拆开后读者要跳 4 个文件才能拼出
原意，且每段单独无意义 → 不要拆，改为加注释/重命名。**职责单一 ≠ 文件单一**。

## 2. 耦合与依赖

### 2.1 循环依赖

**症状**：A 依赖 B、B 依赖 A；改 A 要改 B、改 B 要改 A；测试 A 必须先 mock B 而 mock B 又要 A。

**预防**：编码前画一眼依赖方向（单向 DAG）；发现要"反过来 import 上层" → 停下，要么反转依赖
（依赖倒置：上层定义接口，下层实现），要么抽共享底层模块。CI 用 `madge`/`dependency-cruiser`
守护。

### 2.2 跨层穿透

**症状**：Router 直接查 ORM；Service 直接拼 HTTP 响应；Controller 里写业务规则。

**预防**：分层职责 + **禁止项**写在 CMS/CLAUDE.md，编码时对照执行（05 硬边界 4）：
- Router 禁业务、禁直接 DB。
- Service 禁 HTTP、禁直接 SQL 字符串。
- Repository 禁业务判断、禁 HTTP。
import 方向用 ESLint 自定义规则 / `import-linter` 在 CI 强制。

### 2.3 Feature envy（特性依赖）

**症状**：A 的方法大量读/写 B 的字段；"这段逻辑更应该属于 B"。

**预防**：写一个方法时问"我在用谁的数据？"——如果答案是另一个对象的大部分字段，把逻辑搬过去
（Move Method），A 改为调用。

### 2.4 Shotgun surgery（霰弹式修改）

**症状**：改一个业务概念要动 6 个分散文件；"每次加一个字段都要碰 N 处"。

**预防**：如果一个变更反复需要分散修改 → 这是"该有一个聚合对象/模块"的信号；把分散的相关逻辑
收敛进一个内聚模块（如把"用户通知偏好"的 5 处散落逻辑收进 `NotificationPreference`）。反之，
**散弹式修改的反面是"改一处影响过广"**——两者都要看：广而不内聚 = god，散而不聚 = 缺抽象。

### 2.5 共享可变状态

**症状**：全局单例/静态 mutable 被多处读写；时序决定结果；测试因顺序 flaky。

**预防**：默认不可变；必须可变的状态收进显式生命周期对象（构造注入，禁运行时 `ServiceLocator`
取）；跨请求/跨线程状态必须显式标注并发安全契约。

## 3. 抽象与复杂度

### 3.1 推测性抽象 / 过早抽象

**症状**：为"将来可能要的"预留扩展点；接口只有一个实现；抽象层不降低复杂度反而增加跳转。

**预防**（与 05 硬边界 7 一致）：**只建 Spec 要的，不建"将来可能要的"**。出现 ≥2 个真实变体再抽
接口（Rule of Three）；YAGNI 优先于"灵活性"。抽象的代价是"读者要多跳一层"，没有收益不要付。

### 3.2 Primitive obsession（基本类型迷恋）

**症状**：到处传 `string`/`int`，同一个 `string` 时是 email、时是 userId；参数表一串同类型基本值。

**预防**：领域概念用值对象/类型别名包一层（`UserId`、`Email`、`Money`）；TS 用 branded type，
Python 用 `NewType`/Pydantic。代价小、收益大（类型守护 + 不可构造错值）。

### 3.3 魔法数 / 硬编码

**症状**：代码里 `if status == 3`、`setTimeout(86400000)`、`"/api/v1/..."` 散落。

**预防**：命名常量/枚举/配置；业务状态用枚举不用裸数字；超时/阈值/URL 走配置或常量模块；pre-commit
可加 `no-magic-numbers`（对业务代码，不对测试/生成代码）。

## 4. 错误处理

### 4.1 宽泛吞错（最常见、最危险）

**症状**：`except Exception: pass` / `catch (e) {}` / `// TODO: handle`；错误无声消失，出 bug
无栈无日志。

**预防**（05 工程规范基线明令）：
1. **精确捕获**：捕具体异常类型，不捕基类宽网。
2. **捕获即处理**：要么处理（记日志 + 降级 + 明确语义）、要么传播（不 catch 让上层处理）、要么
   包装重抛（加上下文）；**禁止"捕获了却什么都不做"**。
3. **携上下文**：重抛时带上业务上下文（什么操作、什么输入、trace_id），不只 `throw e`。
4. **禁空 catch**：CI lint 规则禁 `except: pass` / `catch {}` 无日志的空捕获。

### 4.2 错误码与异常混用 / 静默返回 nil

**症状**：失败返回 `null`/`-1`/`false`，调用方不判 → NPE；或一半函数用异常一半用返回码，调用方
不知道该查哪个。

**预防**：统一一种错误模型（异常 or Result 类型）；失败不返回"看起来成功"的值；用 Result/Option
类型让"可能失败"在类型上可见（Rust `Result`、TS `Result<T,E>`、Python 显式 raise）。

### 4.3 副作用藏在使用者不知情处

**症状**：getter 里改状态、查询函数里发请求、构造函数里做 IO。

**预防**：查询无副作用（Command-Query Separation）；有副作用的方法名必须暴露意图（`save`/`send`
/`invalidate`，不是 `get`/`load`）；构造函数只赋值，重活放显式 `init()`。

## 5. 性能（编码期可避免的）

### 5.1 N+1 查询

**症状**：循环里查 DB；列表页加载慢，日志里同类查询成百上千条。

**预防**：列表查询带 `IN`/预加载关联（eager load）；编码时凡"在循环里访问关联数据"就停下来
想"这会触发几次查询"；用 ORM 的 `selectinload`/`prefetch_related` 而非懒加载。

### 5.2 循环内 IO / 无谓分配

**症状**：循环里 `await fetch`、循环里 `JSON.parse` 同一文件、循环里 `new Array` 累积大对象。

**预防**：循环外取一次、批量化、流式处理；热路径不做重复计算（缓存/记忆化）。

### 5.3 过早优化

**症状**：为想象中的性能问题牺牲可读性（手写位运算、缓存一切、回避清晰抽象）。

**预防**：先正确后清晰再测量后优化；不猜瓶颈，用 benchmark/profiler 定位；优化点加注释说明为什么
这样写不直观（"性能：避免 N 次分配，见 benchmark X"）。

## 6. 可维护性

### 6.1 死代码与未用引用

**症状**：未用 import、注释掉的代码块、`@deprecated` 但不删、永不调用的分支。

**预防**：删不用的，不注释留着（git 记着历史）；`@deprecated` 必带"替代方案 + 移除版本"；CI 跑
`knip`/`ts-prune`/`ruff F401` 守护零未用 import。

### 6.2 命名不一致

**症状**：同一概念多种命名（`userId`/`uid`/`user_id`/`account_id`）；同名不同义。

**预防**：遵循 CMS 既有命名（05 硬边界 4——ground 既有模式）；新概念定名后写进 CMS 术语表；
review 时把"同概念多命名"当缺陷提，不是 nitpick。

### 6.3 注释与代码 drift

**症状**：注释描述的参数/行为与代码不符；陈旧注释比无注释更糟（误导）。

**预防**：改代码行为必同步改注释；注释写"为什么"不写"做什么"（做什么看代码）；复杂业务规则
注释带 Spec/AC 引用（`# 见 SPEC-F-order-3 §事务边界`），便于追溯。

## 7. 数据层

### 7.1 共享 schema 耦合

**症状**：多服务/模块直接读写同一张表；改表结构要协调 N 个消费方。

**预防**：表归一个 owner 模块，他方走该模块的 API/视图，不直连表；跨模块读用只读视图或契约化
的读模型。

### 7.2 缺索引 / 索引滥用

**预防**：高频查询条件编码时就标"需索引"，落地 migration 时建；但不在每列堆索引（写放大）；
用 EXPLAIN 验证，不猜。

### 7.3 事务边界与 session 生命周期

**预防**：事务包住"业务原子单元"，不包网络调用/外部 IO；明确 session 范围（请求级 vs 单元工作级），
避免 lazy-load 脱离 session 报错。

## 8. 编码期自检清单（提交前 60 秒过一遍）

> 这不是 06 门控（那是机器跑测试/lint/build），这是**写代码时人的自检**——抓"编码期就该发现"
> 的问题，不留给 review。

- [ ] **每个新文件有一行职责契约**，且没有承担第二类不相关职责。
- [ ] **没有"顺手加一点"**：新功能进了既有文件，是因为同职责，不是因为省事。
- [ ] **依赖方向是单向 DAG**，没有"反过来 import 上层"。
- [ ] **分层禁止项守住了**（Router 不碰 DB、Service 不碰 HTTP）。
- [ ] **函数能一句话说清做什么**；嵌套 ≤ 3；参数 ≤ 4。
- [ ] **没有空 catch / `except: pass`**；异常要么处理要么传播要么包装重抛带上下文。
- [ ] **没有魔法数/硬编码 URL**；业务状态用枚举。
- [ ] **没有在循环里查 DB/发请求**。
- [ ] **只建 Spec 要的**，没有"将来可能要的"预留抽象。
- [ ] **命名遵循 CMS 既有模式**；同概念无多命名。
- [ ] **删了不用的代码/import**，没有注释掉的备份。
- [ ] **改动行为同步改了注释**；注释写 why 不写 what。

## 9. 与其他阶段/技能的分工

| 场景 | 在哪做 | 用本文件的什么 |
|------|--------|----------------|
| 编码期自检（05） | 写代码时 | §8 自检清单 + 各反模式「编码期预防规则」 |
| 代码审查（06 S7 / csp-code-reviewer） | 提交后 | 各反模式「检测信号」作 finding 依据 |
| 深度审计（audit / csp-codebase-audit / 07 B12） | 里程碑后 | 体积阈值/依赖方向/死代码做量化审计 |
| 重构（csp-graph-refactor / csp-legacy-modernization） | 计划性重构 | §1 拆分方法 + §2.4 散弹式修改判定 |

> **编码期 vs 审查期**：本文件强调"编码时就守规则"——god file 不是审查时才发现的"大文件"，
> 是编码时"顺手加一点"累积出来的；在 05 把第二职责塞进既有文件的那一刻就该停下拆分，而不是
> 等到 06/07 报告"该文件 600 行需重构"。**阈值是审视触发器，职责单一才是判据。**
