# 专利交底书（Software Patent Disclosure）

## 边界声明（先读，不可跳过）

本技能产出的是**技术交底书**——一份给专利代理人看的技术材料。它**不是**法律文件。

| 本技能做 | 本技能不做 |
|---|---|
| 把工程实现翻译成可主张的技术方案描述 | 判断方案是否具备专利性 |
| 组织现有技术检索并写出区别技术特征 | 出具新颖性 / 创造性结论 |
| 按九节结构产出可提交的交底稿 | 撰写权利要求书、说明书摘要 |
| 给出特征分层建议（哪些是必要技术特征） | 决定保护范围宽窄、决定是否申请 |
| 标注信息缺口与 `[TBD]` | 补全发明人未提供的技术事实 |

**最终申请文件必须由有资质的专利代理人撰写。** 交底书中任何形如「本方案具备新颖性」「可以授权」的表述都是越界，写出来就是错误。本技能所有自检结论一律用「自检判断（非法律结论）」标注。

## When to Use

- 已实现或已设计的技术方案，需要转成给代理人/法务的交底材料
- 公开发布（上线、大会演讲、开源、论文投稿、招标文档）**之前**，需要评估是否要抢在公开前立案
- 手上只有一句话想法，需要判断能不能提炼出可主张的发明点
- 代理人已回问「区别技术特征是什么」「效果数据呢」，需要补材料

## When NOT to Use

- 需要撰写权利要求书 / 答复审查意见通知书 → 归专利代理人，本技能不介入
- 需要侵权比对、FTO（自由实施）分析 → 法律工作，本技能不做
- 只是要写技术方案文档给团队看 → 用 `csp-tech-solution-design`
- 要做的是学术综述而非专利检索 → 用 `csp-literature-review`
- 纯 UI 视觉设计、纯文案、纯商标 → 不属专利客体范畴，换别的保护路径

## 主流程

```
Step 0  边界声明 + 输入盘点（缺什么）
Step 1  发明点提炼（一份交底书 = 一个发明构思）
Step 2  可专利性初筛（自检，非法律结论）
Step 3  现有技术检索与区别特征分析
Step 4  特征分层与权利要求布局思路
Step 5  九节逐节撰写
Step 6  充分公开 / 技术秘密切分
Step 7  自检 + 落盘 + 交接
```

信息不足时随时插入发明人访谈（`references/inventor-interview.md`）。

### Step 0：边界声明与输入盘点

第一件事：向用户复述边界（交底书 ≠ 法律文件 ≠ 申请文件）。第二件事：盘点输入。

| 输入源 | 提取什么 | 缺失时 |
|---|---|---|
| 技术方案文档（`.csp/specs/`、`docs/`） | 架构、步骤、数据结构、参数 | 转访谈 |
| PRD（`docs/prd/`） | 场景、痛点、验收指标 | 注意 PRD 是产品语言，必须技术化重写 |
| 代码仓库 | 实际实现、边界处理、默认值 | 用 Grep/Glob 定位核心模块，不要整仓粘贴 |
| 性能测试 / 压测报告 | 效果数值与口径 | 标 `[TBD]`，不要编数 |
| 发明人口述 | 难点、试错过程、被否决的方案 | 转访谈清单 |

**盘点输出**：一张「已知 / 未知」表。未知项 ≥ 3 条时先跑访谈再动笔，否则会在第 4、5 节大面积卡壳。

### Step 1：发明点提炼

规则（违反任何一条都要重来）：

1. **一份交底书聚焦一个发明构思。** 判据：能否用一句话说清「用什么手段解决什么技术问题」，且这句话里只有一个手段核心。出现「并且」「同时」「另外还」通常意味着两个构思。
2. **把「我们做了什么」翻译成「解决了什么技术问题」。** 「我们加了一个布隆过滤器」→「在缓存穿透场景下，如何在不引入额外网络往返的前提下过滤不存在的键」。
3. **区分发明点与工程细节。** 大量工程实现是不可主张的常规手段（重试、超时、连接池、灰度开关、日志打点、配置中心）。会砍：凡是「换个项目也会这么写」的，都是工程细节，不进发明点，只在第 4 节作为可选实施细节出现。
4. **一个方案可能有多个可独立主张的发明点。** 分别列出，逐个跑 Step 2；然后判断是否拆成多件申请。

**发明点清单模板**（落盘前先填这张表）：

| # | 发明点一句话 | 技术问题 | 核心手段 | 可否独立成立 | 拆分建议 |
|---|---|---|---|---|---|
| 1 | 基于请求指纹聚类的自适应限流阈值计算 | 固定阈值在流量结构突变时误杀正常请求 | 按指纹聚类分桶，桶内独立统计并动态推导阈值 | 是 | 主件 |
| 2 | 指纹字段的自动选择与降权 | 指纹维度爆炸导致聚类不稳定 | 按区分度与稳定性打分选字段，低分字段降权 | 是（依赖 1 的场景） | 可拆分为从案 |
| 3 | 限流决策的边缘节点下沉 | — | 常规部署优化 | 否（常规手段） | 不申请 |

**拆分判据**：发明点 2 若脱离发明点 1 仍能解决一个独立的技术问题，且有独立的现有技术对照 → 拆成两件。若 2 只是 1 的优选实现 → 留在同一件里作从属层次。

### Step 2：可专利性初筛（自检）

对每个发明点跑三要件自检 + 客体（subject-matter）自检。**这一步是自检不是法律结论**，输出三档：

| 档位 | 含义 | 下一步 |
|---|---|---|
| A 可直接交底 | 技术问题-手段-效果链条完整，客体无争议 | 进 Step 3 |
| B 需重构表述 | 技术内核存在，但当前写法落在纯算法/纯商业方法上 | 按落地改写表重写后重跑 |
| C 不建议交底 | 找不到技术手段落点，或效果纯属商业/审美层面 | 明确告知用户，并说明这是自检判断，仍建议由代理人复核 |

软件类方案最常掉进 **B 档**：内核是真的，但写法是「一种计算权重的方法」。三要件各自要问什么、客体落地的具体改法、常见驳回写法与可授权写法的逐条对照，见 `references/patentability-screening.md`（**每个发明点都必须读它跑一遍，不要凭印象判档**）。

### Step 3：现有技术检索与区别特征分析

**关键规则：找到最接近的现有技术不是坏事，是交底书最有价值的部分。**

检索不到现有技术的交底书，代理人无法论证创造性，审查员会自己找到并直接驳回。找到 D1（最接近的现有技术）并写清区别技术特征，等于把创造性的落点交到代理人手上。

**区别特征三问**（对每条区别都要答完，答不出第二问说明它不是区别而是常规改进）：

1. 区别是什么？——用技术特征语言，不用效果语言。（「按请求指纹聚类分桶后桶内独立统计」是特征；「更精准」不是）
2. 这个区别解决了什么现有技术解决不了的问题？——必须对应 D1 的一个具体失效条件。
3. 带来什么可量化的技术效果？——必须有测量口径。

检索源清单、检索式构造方法（关键词扩展 / 分类号 / 引文追踪）、检索记录表格式、检索停止条件、以及「检索不到」时怎么写，见 `references/prior-art-search.md`（**开始检索前读；用 WebSearch 时按其中的检索式模板构造查询，不要只搜一次就下结论**）。

### Step 4：特征分层与权利要求布局思路

这是**交底层面的理解，不是权利要求撰写**。目的是把「哪些特征必不可少、哪些可以没有」的判断从发明人手里传给代理人——代理人无法替发明人做这个判断，因为它是技术判断不是法律判断。

**必要技术特征提取法**：对每个候选特征问一句——

> 去掉这个特征，本发明还能解决那个技术问题吗？

- **能解决** → 不是必要技术特征 → 移到从属层次（或不写进权利要求，只留在说明书）
- **不能解决** → 必要技术特征 → 进独立权利要求

独立权利要求要写得尽量上位（覆盖范围宽），但必须包含全部必要技术特征（否则得不到说明书支持、也容易被无效）。从属权利要求逐层加限定，作为退守防线：独权被驳时逐层收缩，而不是整件死掉。

三层特征表的填法、上位化改写示例、以及为什么发明人必须给「可有可无」判断，见 `references/claims-layout.md`（**Step 5 第 4 节和第 9 节动笔前读**）。

### Step 5：九节逐节撰写

交底书主体固定九节，顺序不可调：

```
1 技术领域              5 有益效果
2 背景技术与现有技术缺陷  6 具体实施例
3 发明目的与要解决的技术问题 7 附图说明
4 技术方案详述（最重）    8 关键术语定义
                        9 可替代方案与扩展
```

每节的**目的 / 必填要素 / 写作要点 / 填好的示例片段 / 常见错误**见 `references/disclosure-sections.md`——**逐节撰写时打开它对照写，不要凭记忆**。空白骨架与占位符见 `references/templates.md`。

第 4 节是全篇最重的一节：完整步骤流程、系统模块划分与连接关系、关键数据结构、参数与取值范围、可选实施例的并列方案，要求写到**本领域技术人员照着能实现**（即「充分公开」）的程度。第 4 节写不到这个程度，其余八节写得再漂亮也是废稿。

配图需要时（流程图 / 架构图 / 时序图 / 数据结构图各自何时必需）用 `csp-tech-diagram` 出图，再回到第 7 节登记。**铁律：图中标号与正文标号必须一致**（步骤用 `S1…Sn`，模块用 `101/102…`，同一编号在两处指同一事物）。

### Step 6：充分公开与技术秘密的切分

专利是**以公开换保护**。必须公开到本领域技术人员能实现；但**不需要公开**与发明点无关的工程 know-how（具体调参经验、内部系统集成细节、数据清洗的脏活、供应商配置）。这些更适合走技术秘密。

切分判断规则、必须公开 / 可以保留的对照表、以及「专利 + 技术秘密」混合策略，见 `references/sufficiency-and-secrecy.md`（**第 4、6 节写完自检时读；用户表达「这个不想写进去」时也读，判断是合法保留还是致命的公开不足**）。

### Step 7：自检、落盘与交接

**落盘前自检清单**（逐项打勾，任何一项不过就回对应 Step）：

```
[ ] 全篇没有「具备新颖性」「可以授权」「专利性强」等法律结论表述
[ ] 一个发明构思（不是「并且/同时」拼起来的多个）
[ ] 三要件自检档位已标注为 A/B/C，且标明「自检判断（非法律结论）」
[ ] 已列出至少 1 条最接近的现有技术，且每条区别都过了三问
[ ] 第 2 节每条缺陷在第 5 节都有对应效果行（闭环）
[ ] 第 4 节含：编号步骤 + 模块连接关系 + 数据结构字段表 + 参数取值范围
[ ] 第 5 节每个效果都有测量口径（数据集/压测条件/硬件），缺失处标 [TBD]
[ ] 第 6 节至少 1 个端到端实施例，含具体数值
[ ] 第 7 节图号与正文标号一致，无孤立标号
[ ] 第 9 节至少 2 条真实可行的替代路线（非「本领域技术人员可以想到」套话）
[ ] 特征分层表已填（必要 / 优选 / 具体实现三档）
[ ] 信息缺口全部标 [TBD] 并汇总在文末，没有编造数值、竞品或参考文献
```

**产物路径**：`docs/analysis/PATENT-DISCLOSURE-{发明点简称}-{YYYY-MM-DD}.md`

例：`docs/analysis/PATENT-DISCLOSURE-adaptive-rate-limiting-2026-10-14.md`

- 发明点简称用短横线小写英文或短中文，≤ 24 字符
- 绝不写仓库根目录；`docs/analysis/` 不存在则创建
- 多件申请拆分成多个文件，一个文件一个发明构思
- 若仓库使用 `.csp/manifest.json`，按既有约定回写条目（`source_type=doc`）

## 时间线与流程

```
发明人 + 本技能            内部评审              专利代理人            发明人
─────────────────────────────────────────────────────────────────────────
D0  交底书初稿        ──►  D+3 技术/IP 评审  ──►  D+7 起草申请文件  ──►  D+14 技术确认
    （九节 + 检索记录）      （拆分/合并/放弃）      （权利要求书）        （逐字确认）
                                                                        │
                                                              D+17 提交申请 ◄┘
```

| 阶段 | 谁 | 关键动作 | 常见耗时 |
|---|---|---|---|
| 交底 | 发明人 | 九节写完，检索记录附后，`[TBD]` 汇总 | 2–5 个工作日 |
| 内部评审 | 技术负责人 + IP | 决定申请/放弃/拆分/合并；确认对外公开时间窗 | 3–5 个工作日 |
| 代理人撰写 | 专利代理人 | 起草说明书与权利要求书，回问技术细节 | 5–15 个工作日 |
| **发明人技术确认** | 发明人 | **逐字确认技术描述准确性** | 1–3 个工作日 |
| 提交 | 代理人 | 递交申请，取得申请日 | — |

**强调：发明人必须逐字确认技术描述准确性。** 申请文件一旦提交，技术内容的修改空间极窄（超出原始记载范围的新内容通常不被允许加入），签错的技术描述后续很难改，甚至会把一个能授权的方案签成不能授权的。确认时按第 4 节步骤逐条核对：步骤顺序对不对、判定条件对不对、参数范围对不对、有没有把优选方案写成了唯一方案。

**时间窗规则**：任何对外公开（上线、演讲、开源、投稿、招标、客户 POC 交付）都可能启动新颖性时钟，且各国宽限期规则不同。发明人**不要自行判断「已经公开了就没救了」**——如实写出每一次公开的时间、地点、方式，交给代理人。

## Key Principles

1. **交底书是技术材料不是法律文件。** 出现任何专利性结论即越界；自检结论必须标注「非法律结论」。
2. **一份交底书一个发明构思。** 出现「并且/同时/另外还」就先拆分，混装会让每件都弱。
3. **最接近的现有技术是资产不是威胁。** 写清区别技术特征就是给创造性找落点；检索不到才是最坏情况。
4. **软件方案必须落到「解决技术问题的技术手段产生技术效果」。** 纯算法、纯商业方法、纯智力活动规则在多数司法辖区不受保护，抽象内核要绑定到具体数据处理流程、系统架构或硬件交互上。
5. **第 4 节的验收标准是「本领域技术人员照着能实现」。** 步骤、判定条件、数据结构、参数范围缺一即为公开不足。
6. **效果必须可验证。** 「显著提升」不是效果，「同一压测脚本下 P99 从 820ms 降到 210ms」才是。
7. **必要技术特征的判断只能来自发明人。** 「去掉它还能解决问题吗」是技术问题，代理人替发明人猜会猜错。
8. **不编造。** 数值、竞品、参考文献、检索结果一律不脑补，缺失标 `[TBD]`。

## Anti-Patterns

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 产品语言：「用户可以语音搜索商品」 | 描述的是功能而非技术手段，无法界定保护范围，也落在客体争议区 | 「音频经特征提取编码为 N 维向量，与候选项语义向量做相似度匹配，阈值按 X 规则动态调整」 |
| 背景技术写「现有技术效率低、体验差」 | 空话无法支撑创造性；审查员需要具体失效条件 | 「在 QPS 突增 3 倍且请求分布倾斜时，固定阈值限流会误杀约 12% 正常请求，因为阈值按全局均值推导」 |
| 第 4 节贴代码 | 代码是实现产物，代理人反推不出必要技术特征，且代码里的常规工程细节会淹没发明点 | 写编号步骤 + 判定条件 + 数据结构 + 参数范围；代码只在必要时作附录片段并配文字解释 |
| 第 4 节只给架构图不写步骤 | 图表达静态关系，无法公开动态过程与分支逻辑，构成公开不足 | 架构图 + 编号步骤流程（含异常分支）+ 跨服务时序图 |
| 参数只写一个值（「阈值设为 100」） | 单点值把保护范围钉死在一个数字上，改一个数就绕开 | 给取值范围 + 默认值 + 选取依据（「阈值取值区间 [50, 500]，默认 100，按桶内 QPS 的 p95 推导」） |
| 效果写「显著提升性能」 | 不可验证，会被要求补正，也无法与现有技术缺陷闭环 | 给对照实验：数据集 / 硬件 / 压测脚本 / 指标 / 数值 / 相对变化 |
| 第 2 节列 3 个缺陷，第 5 节只答 1 个 | 缺陷-效果不闭环，创造性论证断链 | 一一对应表：每条缺陷 → 对应技术手段 → 对应量化效果 |
| 替代方案写「本领域技术人员可以想到其他实现方式」 | 套话等于没写，直接压缩保护范围 | 给 ≥2 条真实可行路线（如「用规则引擎替代聚类模型」）+ 各自差异 + 各自优缺点 |
| 检索只做一次中文关键词搜索就下结论 | 漏检会让代理人在错误的现有技术基础上撰写，后续被驳回代价更高 | 中英同义词扩展 + 分类号 + 引文追踪三轮，记录检索式与命中数 |
| 「已经上线了所以不能申请」自行放弃 | 公开是否构成现有技术取决于时间、地域、方式，是法律判断 | 如实记录首次公开的时间地点方式，交代理人判断 |
| 编造竞品或参考文献 | 交底书一旦被发现虚构，代理人对全篇的信任都会打折 | 只写公开可查证来源；查不到就写「在本轮检索范围内未发现」 |
| 一份交底书塞进整个项目的五个功能 | 构思混杂，每个都写不透，代理人只能挑一个 | 按发明构思拆成多份，各自跑完整流程 |

## 反合理化速查

| 你会想说的话 | 实际情况 |
|---|---|
| 「这个功能已经上线了，没法申请了」 | 公开使用是否构成现有技术取决于时间与地域，需要专业判断，不能自行放弃 |
| 「先把代码贴进去，代理人会看懂」 | 代码不是技术方案描述，代理人需要的是步骤与原理 |
| 「效果很好，写『显著提升』就行」 | 不可验证的效果描述会被要求补正，或直接削弱创造性论证 |
| 「权利要求写窄一点更容易授权」 | 过窄的权利要求授权后无保护价值，竞品改一个非必要特征就绕开 |
| 「检索不到相关技术，说明我们很创新」 | 检索不到 ≠ 不存在；公开延迟与检索式不足都会漏检 |
| 「一个交底书全写进去更省事」 | 多构思混装让每件都弱，按发明构思拆分 |
| 「这是常规做法，不值得交底」 | 是否常规由检索与代理人判断；发明人最常见的误判就是低估自己反复调试出来的方案 |
