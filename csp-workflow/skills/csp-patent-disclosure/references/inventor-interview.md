# 发明人访谈清单

**读这份文件的时机**：Step 0 盘点发现未知项 ≥ 3 条；Step 1 提炼不出发明点；Step 5 某节写不下去；或用户只给了一句话想法。

## 访谈规则

1. **一次问一节，不要一次抛 40 个问题。** 发明人会疲劳，疲劳后答案质量骤降。
2. **先问「难在哪」，再问「做了什么」。** 「做了什么」得到的是功能清单；「难在哪」得到的才是发明点。
3. **追问到数值为止。** 「性能有提升」→「哪个指标？从多少到多少？怎么测的？」。问不出数值就记 `[TBD]`，不要接受模糊描述然后自己编。
4. **不要诱导。** 问「这个字段是必要的吗」不如问「去掉这个字段会发生什么」。
5. **记录原话。** 发明人脱口而出的比喻（「就像给每条流单独装一个水龙头」）往往是最准确的上位表述，比正式术语更适合写进交底书第 4 节的开场。
6. **每节结束做一次复述确认。** 「我理解你说的是 X，对吗？」——技术描述签错的代价见 SKILL.md 时间线一节。

## 第 0 组：立项与时间窗（先问，决定后续一切）

| # | 问题 | 为什么问 |
|---|---|---|
| 0.1 | 这个方案第一次对外可见是什么时候？以什么形式？（上线/演讲/开源/论文/招标/客户 POC/演示视频） | 决定新颖性时间窗，是法律判断的输入 |
| 0.2 | 有没有更早的对外文档提到过它？（技术博客、白皮书、公开 API 文档、招聘信息里的技术栈描述） | 同上，常被遗漏 |
| 0.3 | 有几个人参与？谁做了哪部分？ | 发明人署名，不能漏也不能多 |
| 0.4 | 这个方案是职务发明吗？有无合作单位、外包、开源贡献者参与？ | 权属问题，需上报法务 |
| 0.5 | 有没有已经在申请中或已授权的相关专利（自己公司的）？ | 避免重复申请，也可能构成抵触申请 |
| 0.6 | 期望什么时候提交？有没有硬性的公开截止日（发布会、投稿 deadline）？ | 决定流程压缩程度 |

## 第 1 组：技术领域（对应交底书第 1 节）

| # | 问题 |
|---|---|
| 1.1 | 这个方案跑在什么环境里？（客户端 / 边缘 / 网关 / 服务端 / 数据库 / 嵌入式 / 离线批处理） |
| 1.2 | 它处理的数据是什么？数据从哪来、到哪去？ |
| 1.3 | 如果不看业务，只看技术动作，它在做什么？（检索 / 分类 / 调度 / 压缩 / 同步 / 校验 / 编码 / 缓存 / 路由） |
| 1.4 | 同行业里做同样事情的人，会说这属于哪个技术方向？ |

## 第 2 组：背景与现有技术缺陷（对应第 2 节，最容易得到空话的一节，必须追问）

| # | 问题 | 追问 |
|---|---|---|
| 2.1 | 在你做这个之前，团队/行业是怎么解决的？ | 「具体怎么做的？参数怎么定的？」 |
| 2.2 | 那个做法在什么情况下会出问题？ | 「出问题时你观察到什么现象？日志里长什么样？」 |
| 2.3 | 为什么那个时候会出问题？根因是什么？ | 「如果只调参数能不能绕过？为什么不能？」 |
| 2.4 | 出问题时的量化后果是什么？ | 「多少比例？多长时间？多少资源？」 |
| 2.5 | 这个缺陷是新出现的还是一直存在的？ | 「为什么以前没人解决？是没有需求还是技术上做不到？」← **这一问经常挖出「长期存在的技术难题」，是创造性的强力支撑** |
| 2.6 | 有没有你试过但失败的其他路线？为什么失败？ | 失败路线是第 9 节「明确不可行的替代」的素材 |

## 第 3 组：技术问题（对应第 3 节）

| # | 问题 |
|---|---|
| 3.1 | 如果只能用一句话、且必须含一个可测量的指标，你要解决什么问题？ |
| 3.2 | 「解决了」的验收标准是什么？谁来判断？用什么测量？ |
| 3.3 | 有哪些约束是你必须遵守的？（内存上限 / 时延上限 / 不能改客户端 / 不能加硬件 / 不能引入新依赖） |
| 3.4 | 你**不**打算解决什么？（明确排除项） |
| 3.5 | 这个问题是计算机自身的问题（性能/资源/正确性/稳定性），还是业务流程的问题？ |

**3.5 是客体自检的关键。** 如果发明人答「业务流程」，不要直接判 C 档，接着问：「为了实现这个业务流程，你在计算机层面遇到了什么障碍？」——障碍通常才是真正的技术问题。

## 第 4 组：技术方案（对应第 4 节，问得最久的一组）

### 4A 步骤

| # | 问题 |
|---|---|
| 4A.1 | 一个请求/一条数据进来，从头到尾经过哪些处理？请按顺序说，每步说清输入和输出 |
| 4A.2 | 每一步有没有判定条件？条件成立和不成立分别走哪条路？ |
| 4A.3 | 有没有循环？循环的退出条件是什么？ |
| 4A.4 | 哪些步骤是并行的？哪些必须串行？为什么？ |
| 4A.5 | 出异常怎么办？（超时 / 数据缺失 / 依赖不可用 / 状态不一致） |
| 4A.6 | 冷启动时怎么办？状态是空的时候走什么路径？ |
| 4A.7 | 有没有哪一步是你反复改过很多次的？最后为什么定成这样？ |

### 4B 结构与连接

| # | 问题 |
|---|---|
| 4B.1 | 系统由哪几个模块组成？各自负责什么？ |
| 4B.2 | 模块之间怎么通信？同步还是异步？传的是什么数据？ |
| 4B.3 | 各模块部署在哪里？为什么部署在那里？ |
| 4B.4 | 有没有反馈回路 / 控制环？回路周期多长？ |
| 4B.5 | 哪个模块是你自己写的，哪个是复用的现成组件？ |

### 4C 数据结构

| # | 问题 |
|---|---|
| 4C.1 | 核心的数据结构是什么？有哪些字段？ |
| 4C.2 | 每个字段的类型和取值范围？有没有特殊值（0、-1、null）的含义？ |
| 4C.3 | 数据的生命周期：什么时候创建、什么时候更新、什么时候淘汰？ |
| 4C.4 | 数据量级有多大？单条多大？总量多大？ |
| 4C.5 | 存在哪里？内存 / 本地磁盘 / 共享存储？为什么？ |

### 4D 参数

| # | 问题 |
|---|---|
| 4D.1 | 有哪些可配置参数？默认值是多少？ |
| 4D.2 | 每个参数的合理取值区间？超出区间会发生什么？ |
| 4D.3 | 参数是怎么定出来的？（理论推导 / 实验 / 拍脑袋 / 抄来的） |
| 4D.4 | 哪些参数在不同场景下必须不同？由什么决定？ |
| 4D.5 | 有没有参数是自动调整的？调整规则是什么？ ← **自适应类发明点常藏在这一问** |

### 4E 并列方案

| # | 问题 |
|---|---|
| 4E.1 | 同一个目标，你考虑过哪几种实现路线？各自为什么被选中或被否决？ |
| 4E.2 | 现在这个实现里，哪些部分是「恰好这么做」而不是「必须这么做」？ ← **L2/L3 分层的直接输入** |
| 4E.3 | 如果换一个编程语言/存储/部署平台，方案还成立吗？哪里会变？ |

## 第 5 组：有益效果（对应第 5 节）

| # | 问题 | 追问 |
|---|---|---|
| 5.1 | 和之前的做法比，哪个指标变好了？从多少到多少？ | 「这个数值是怎么测出来的？」 |
| 5.2 | 测量环境是什么？（硬件规格 / 节点数 / 并发 / 时长 / 数据集） | 「换一个数据集结论还成立吗？」 |
| 5.3 | 对照组是什么？参数怎么设的？ | 「对照组的参数是它的最优值吗？」← 不公平对照会被审查员/无效请求人抓住 |
| 5.4 | 有没有变差的指标？代价是什么？ | 主动问，别等发明人自己想起来 |
| 5.5 | 有没有哪个效果是你**没预料到**的？ | ← **「预料不到的技术效果」是创造性最有力的支撑，一定要问** |
| 5.6 | 这些数据现在还能复现吗？压测脚本和原始结果还在吗？ | 不在 → 标 `[TBD]`，安排补测 |

## 第 6 组：具体实施例（对应第 6 节）

| # | 问题 |
|---|---|
| 6.1 | 给我一个最典型的例子：一条真实（或构造）的输入，走完整个流程，每步的中间值是什么？ |
| 6.2 | 有没有一个边界例子，触发了异常分支或降级路径？ |
| 6.3 | 有没有一个失败例子，方案处理不了？（这会变成第 3 节的「非目的」或第 9 节的「不可行替代」） |
| 6.4 | 例子里的数值是实测的还是构造的？ |

## 第 7 组：附图（对应第 7 节）

| # | 问题 |
|---|---|
| 7.1 | 有没有现成的架构图/流程图/时序图？在哪？（设计文档、评审材料、白板照片） |
| 7.2 | 哪些关系用文字说不清、必须看图？ |
| 7.3 | 图里有没有内部系统名、真实域名、客户名需要脱敏？ |

## 第 8 组：术语（对应第 8 节）

| # | 问题 |
|---|---|
| 8.1 | 你刚才用的这个词，是你们内部的说法还是行业通用说法？ |
| 8.2 | 有没有哪个词，你们的意思和外面常见的意思不一样？ ← **最容易漏、影响保护范围最大的一问** |
| 8.3 | 有哪些缩写需要展开？ |

## 第 9 组：替代与扩展（对应第 9 节）

| # | 问题 |
|---|---|
| 9.1 | 除了现在这个路线，还有哪条路能达到同样效果？它的缺点是什么？ |
| 9.2 | 这个手段还能用在别的地方吗？换什么就行？ |
| 9.3 | 竞品如果想绕开你这个方案，最可能怎么改？ ← **规避设计的直接输入** |
| 9.4 | 有没有哪种做法看起来像你的方案但其实行不通？为什么？ |

## 第 10 组：特征分层（对应 Step 4）

| # | 问题 |
|---|---|
| 10.1 | 我把方案拆成了这 N 个特征（列表给发明人看）。逐个告诉我：**去掉它，还能解决 3.1 那个问题吗？** |
| 10.2 | 哪些特征是你反复调试才定下来的？哪些是随便选的？ |
| 10.3 | 如果竞品只用其中一半特征，能达到你的效果吗？哪一半？ |
| 10.4 | 有没有哪个特征你觉得「可能别人也会这么做」？ ← 发明人对「常规性」的直觉是有价值的输入，但要标注为发明人判断 |

## 访谈记录格式

```markdown
### 发明人访谈记录

访谈对象角色：后端工程师（本案主要实现者）
访谈时间：2026-10-14
访谈轮次：第 2 轮（第 1 轮聚焦 0/2/3 组，本轮聚焦 4/5 组）

| 组 | 问题 | 回答要点 | 已填入章节 | 遗留 [TBD] |
|---|---|---|---|---|
| 2 | 2.5 缺陷是否长期存在 | 全局限流误杀问题自 2023 年起被多次提出，两次尝试均因状态开销失败 | 第 2 节缺陷一 | — |
| 4D | 4D.5 参数是否自动调整 | B_max 目前静态；字段数 k 由 S2.3.3 打分自动选择 | 第 4 节 4.2 / 4.4 | k 的最优区间待压测确认 |
| 5 | 5.5 意外效果 | 未预料到桶数收敛后，指标上报的网络包数下降 62% | 第 5 节 E6 | 需补测口径 |
| 5 | 5.6 数据可复现性 | 压测脚本已归档，原始结果保留 90 天 | 第 5 节测量环境 | 90 天后需重跑 |
```

**遗留 `[TBD]` 汇总**：访谈结束时把所有 `[TBD]` 汇总到交底书文末一张表，标明「需要谁、做什么、什么时候能给」。这是内部评审时唯一需要盯的东西。
