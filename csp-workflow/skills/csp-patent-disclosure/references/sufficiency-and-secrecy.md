# 充分公开与技术秘密的平衡

**读这份文件的时机**：Step 6，第 4 节与第 6 节写完自检时；或当发明人说「这段不想写进去」时，用来判断这是**合法保留**还是**致命的公开不足**。

## 一、基本立场

专利制度的交换是：**你公开到本领域技术人员能实现，国家给你一段时间的排他权。**

两边都会出错：

| 错法 | 后果 |
|---|---|
| 公开不足（该写的没写） | 审查阶段被以「说明书公开不充分」驳回；即便授权，也可能在无效程序中被整体无效掉 |
| 过度公开（不该写的都写了） | 把与发明点无关的工程 know-how 永久公开，竞争对手免费获得；专利期满后这些 know-how 也不再受任何保护 |

**注意：过度公开的后果是不可逆的。** 申请文件一旦提交，写进去的内容就是永久公开记录，撤不回、删不掉。公开不足至少还有答复审查意见补正的机会（虽然补正范围受限）。所以**拿不准的时候，先按「充分公开」写，再由 Step 6 的规则逐条判断哪些可以移出去**——而不是先藏着，再被要求补。

## 二、必须公开 vs 可以保留：判断规则

**唯一判据**：

> 这条信息是不是「本领域技术人员实现所述发明点」的必要条件？

- **是** → 必须公开，藏起来就是公开不足
- **否** → 可以保留为技术秘密，但要在交底书里说明「此处存在未公开的工程细节，不影响方案实现」

拆成可操作的三问：

| 问 | 如果答「是」 |
|---|---|
| Q1：不写这条信息，本领域技术人员能否照着第 4 节实现出功能等价的系统？ | 不能 → **必须公开** |
| Q2：这条信息是不是发明点（L1 必要技术特征）的组成部分？ | 是 → **必须公开** |
| Q3：这条信息能不能从产品的对外行为中被逆向观察到？ | 能 → 公开与否都不影响保密性，**建议公开**（换取权利要求支持）；不能 → 是技术秘密的好候选 |

### 对照表

| 信息类型 | 判定 | 理由 |
|---|---|---|
| 步骤流程、判定条件、分支逻辑 | **必须公开** | Q1 = 不能实现 |
| 关键数据结构的字段、类型、取值范围 | **必须公开** | 同上 |
| 参数的**取值区间**与选取依据 | **必须公开** | 区间是权利要求支持的依据 |
| 参数的**最优值**及其调优过程 | 可保留 | Q1 = 能实现（用区间内任意值都能跑）；调参经验是 know-how |
| 至少一个完整实施例（含具体数值） | **必须公开** | 实施例是充分公开的法定支撑 |
| 全部实施例（10 个场景的完整数据） | 可保留 | 1–2 个足够；其余作内部资料 |
| 模块划分与连接关系 | **必须公开** | 架构是方案的骨架 |
| 内部系统集成的胶水代码、适配层细节 | 可保留 | 与发明点无关；Q2 = 否 |
| 与第三方系统的对接协议细节、密钥/凭据管理方式 | **必须保留** | 安全信息，公开会造成风险；且与发明点无关 |
| 训练数据的清洗规则、标注规范、数据来源与规模 | 视情况 | 若发明点在数据处理流程 → 必须公开；若发明点在模型结构且用常规数据即可复现 → 可保留清洗细节，但**数据规模与分布特征要写**（影响可复现性） |
| 模型结构、损失函数、超参区间 | 若发明点在模型 → **必须公开** | Q2 = 是 |
| 具体开源库名、编程语言、部署平台 | 可保留（且**不应该**写进必要特征） | Q2 = 否；属 L3 实现细节 |
| 性能调优的「土办法」（如某个魔法常量、某处缓存预热的时机） | 可保留 | Q1 = 能实现，只是效果略差 |
| 运维手册、告警阈值、故障处理 SOP | 可保留 | 属产品运维而非技术方案 |
| 商业数据（用户量、营收、成本结构） | **必须保留** | 与技术无关，且是敏感商业信息 |
| 未公开的路线图、下一代方案构想 | **必须保留** | 提前公开会摧毁后续申请的新颖性 |

## 三、保留时的写法（关键）

**不要静默删除。** 静默删除会让代理人以为方案就到此为止，从而把权利要求写窄，或在审查意见答复时无法补正。

正确写法是在交底书里显式标注：

```markdown
### 公开范围说明

本案第 4 节已公开实现所述发明点所需的全部步骤、判定条件、数据结构与参数区间。
以下信息经发明人判断为与发明点无关的工程 know-how，未在本交底书中公开，
不影响本领域技术人员实现本案方案：

| 项 | 类型 | 未公开理由 | 对实现的影响 |
|---|---|---|---|
| 阈值推导公式中系数 c1、c2 的最优取值及其网格搜索过程 | 调参经验 | 属 Q1「能实现」范畴；区间已在 4.4 给出 | 无（区间内取值均可工作，效果差异 < 5%） |
| 与内部监控系统的指标上报适配层实现 | 集成细节 | 与发明点无关（Q2 = 否） | 无（可用任意指标上报通道替代） |
| 生产环境实际使用的 B_max 值与集群规模 | 运营数据 | 属敏感运营信息 | 无（第 6 节实施例已给出可复现的示例配置） |

**建议保护路径**：上表前两项建议按技术秘密管理（见第四节）。
```

这段说明有三个作用：告诉代理人哪里是有意留白；给内部评审一个决策点；万一后续被质疑公开不足，能证明留白是经过判断的而非疏漏。

## 四、混合保护策略：专利 + 技术秘密

不是所有创新都该走专利。判断维度：

| 维度 | 走专利 | 走技术秘密 |
|---|---|---|
| **可逆向性** | 竞品能从产品外部行为观察/推断出方案 | 竞品无法从外部行为推断（如纯服务端内部逻辑、内部调参） |
| **独立发现风险** | 这个方向很多人在做，别人可能独立发明并抢先申请，反过来告你侵权 | 冷门方向，独立发现概率低 |
| **技术寿命** | 技术迭代快（2–3 年），专利期够用 | 技术寿命长（配方型 know-how 可用十年以上），专利期满即失去保护 |
| **公开代价** | 公开后竞品收益有限 | 公开后竞品直接获得核心竞争力 |
| **举证可行性** | 侵权可从产品行为取证 | 侵权无法取证（秘密被偷用你根本不知道），此时专利反而更有威慑力 |
| **是否已在标准/开源中曝光** | 尚未公开 | 已经开源 → 专利与技术秘密都失效，只剩著作权 |

**典型混合切分（服务端软件）**：

```
可逆向的部分（客户端能看到的行为）        → 专利
  · 协议交互流程、请求/响应结构
  · 客户端可见的降级与重试策略
  · 从外部压测能推断出的调度行为

不可逆向的部分（只在服务端内部）          → 技术秘密
  · 具体阈值调优经验与网格搜索结果
  · 内部特征工程的脏数据处理规则
  · 容量规划与成本模型
  · 故障演练中沉淀的运维手册

结构性创新（架构、数据流）                → 专利
  · 一旦泄露（前员工、代码审计、供应链）就无法追回，专利提供排他权兜底
```

**注意一个陷阱**：如果一项技术秘密有可能被他人独立发明并申请专利，那么「藏着」的结果是**你自己变成侵权方**。这类技术应该申请专利（哪怕公开代价大），或用防御性公开（defensive publication）把它变成现有技术，阻断他人申请。**防御性公开是不可逆的决定，必须由 IP/法务判断，本技能只负责把选项摆出来。**

## 五、Step 6 自检清单

```
[ ] 第 4 节的每个步骤都有输入/处理/判定条件/输出，无「系统进行优化处理」式空描述
[ ] 参数给的是取值区间 + 默认值，不是单一魔法数字
[ ] 至少 1 个完整实施例含具体数值
[ ] 敏感信息（凭据、密钥、内部域名、真实集群名、商业数据、客户名）已清除或替换为占位符
[ ] 未公开项已汇总成「公开范围说明」表，每项写明类型/理由/对实现的影响
[ ] 未公开项没有一项是 L1 必要技术特征（若有 → 必须公开，否则公开不足）
[ ] 已对每个未公开项判断保护路径（技术秘密 / 无需保护 / 需 IP 复核）
[ ] 若存在「可能被他人独立发明并抢先申请」的技术秘密 → 已标记为需 IP/法务决策
[ ] 未把下一代未公开构想写进本案（会破坏后续申请的新颖性）
```

## 六、发明人说「这个不想写」时的处理流程

```
发明人：「S4.2 里那个系数怎么调出来的，我不想写。」
        │
        ├─ Q2：它是 L1 必要技术特征吗？
        │     是 → 「不写就是公开不足，会被驳回或无效。要么写，要么把它移出必要特征。」
        │     否 ↓
        ├─ Q1：不写它，本领域技术人员能实现吗？
        │     不能 → 「那它是实现所必需的细节，必须写（可以只写区间不写最优值）。」
        │     能 ↓
        ├─ Q3：能从产品外部行为逆向出来吗？
        │     能 → 「藏不住，建议写进去换权利要求支持。」
        │     不能 → 「合法保留。填进『公开范围说明』表，走技术秘密。」
        │
        └─ 最后：把结论告诉代理人，不要静默删除。
```

**永远不要静默删除。** 静默删除是本节唯一的严重错误。
