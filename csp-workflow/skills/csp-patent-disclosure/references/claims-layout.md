# 特征分层与权利要求布局思路

**读这份文件的时机**：Step 4，以及 Step 5 撰写第 4 节（技术方案详述）与第 9 节（可替代方案）之前。

**先划边界**：这份文件讲的是**交底层面**对权利要求布局的理解，不是权利要求撰写方法。权利要求书由专利代理人写。发明人要交付的是**特征分层判断**——哪些特征必不可少、哪些可有可无、哪些只是当前项目里恰好这么实现。这个判断代理人做不了。

## 一、为什么发明人必须给「可有可无」判断

代理人拿到交底书后会做两件事：把独立权利要求写得尽量上位（覆盖范围宽），把从属权利要求逐层加限定（作为退守防线）。这两件事都依赖一个输入：**每个技术特征是不是必要的**。

而这个判断是**技术判断，不是法律判断**：

| 判断 | 谁能做 | 为什么 |
|---|---|---|
| 「去掉特征 F3，方案还能解决那个技术问题吗」 | **只有发明人** | 需要理解方案的工作机理；代理人只能从文字推测 |
| 「F3 写进独权还是从权」 | 代理人 | 需要权衡检索结果、审查实践、无效风险 |
| 「F3 能不能上位化成 F3'」 | 代理人起草 + **发明人确认技术等价性** | 上位化后是否仍能工作，是技术问题 |

**发明人只给第一条，其余交给代理人。** 但第一条不给，代理人就只能猜，猜错的方向通常是「把所有特征都塞进独权」——结果是独权极窄，竞品改一个非必要特征就绕开了。

**反面后果**：过窄的权利要求授权后没有保护价值。授权不是目的，**授权且别人绕不开**才是目的。「写窄一点更容易授权」是最贵的一种自我安慰。

## 二、必要技术特征提取法

对候选特征逐个问一句：

> **去掉这个特征，本发明还能解决那个技术问题吗？**

- **能解决** → 不是必要技术特征 → 移到从属层次，或只留在说明书里作为优选实施例
- **不能解决** → 必要技术特征 → 进独立权利要求

问的时候要具体：不是抽象地问「重要吗」，而是**在脑中把方案跑一遍，去掉这个特征，看它在哪一步断掉、断掉后输出什么错误结果**。断不掉的就是非必要特征。

### 常见误判

| 误判 | 真相 | 怎么发现 |
|---|---|---|
| 「这是核心模块，肯定必要」 | 有些「核心模块」只是当前架构的选择，换一种架构可以不要 | 问：有没有不含这个模块也能解决同一问题的实现？ |
| 「这个参数很重要」 | 参数的**具体值**几乎从来不是必要特征；参数的**存在**或**取值范围**才可能是 | 问：如果这个参数换成任意值，方案还成立吗？成立 → 值不是必要特征 |
| 「我们调了很久才调好」 | 投入的工作量与技术必要性无关；调参经验通常是技术秘密而非必要特征 | 问：说明书里不写这段调参过程，本领域技术人员还能实现吗？能 → 不必要 |
| 「代码里就是这么写的」 | 实现细节（数据结构选型、库、语言）通常不是必要特征 | 问：换成另一种等价数据结构，方案还成立吗？ |
| 「这是我们的创新点」 | 发明点 ≠ 必要技术特征的集合；发明点通常由 1–3 个必要特征承载，其余是配套 | 做下面的三层表 |

## 三、三层特征表（交底书必填）

| 层 | 定义 | 去向 | 示例（自适应限流方案） |
|---|---|---|---|
| **L1 必要技术特征** | 去掉它发明无法解决所述技术问题 | 独立权利要求 | ① 从请求中提取多维字段构成请求指纹；② 按指纹对请求聚类分桶；③ 每桶独立维护滑动窗口统计量；④ 按桶内统计量独立推导该桶的准入阈值；⑤ 按桶阈值执行准入判定 |
| **L2 优选技术特征** | 去掉它发明仍能工作，但效果变差 | 从属权利要求（逐层加限定） | ⑥ 指纹字段按区分度打分后选择，低分字段降权；⑦ 桶内统计量采用指数加权移动平均；⑧ 阈值推导引入滞回区间以避免抖动；⑨ 冷启动期使用全局兜底阈值 |
| **L3 具体实现细节** | 当前项目里的实现选择，可任意替换 | 只写进说明书的具体实施例，不进权利要求 | ⑩ 用 Redis 存桶状态；⑪ 决策模块部署在 sidecar；⑫ 用 Go 实现；⑬ 窗口长度 10s、步长 1s；⑭ 阈值上下限 [50, 500] |

**填表规则**：

- L1 控制在 **4–8 条**。超过 10 条几乎肯定混进了 L2/L3；少于 3 条通常上位化过头，会得不到说明书支持。
- L1 里**不能出现具体数值、具体产品名、具体编程语言、具体开源库名**。这些属于 L3。
- L2 每条都要能回答「加上它带来了什么额外效果」，答不出就是 L3。
- L3 越详细越好——它是说明书「充分公开」的素材，也是实施例的血肉。
- 三层之间存在**上位化链条**：L3 是 L2 的具体化，L2 是 L1 的具体化。写交底书时把这条链写清楚，代理人上位化时才有依据。

### 上位化改写示例（发明人提供技术等价性确认）

| L3 具体 | L2 优选 | L1 必要（上位） | 发明人要确认的事 |
|---|---|---|---|
| 窗口长度 10s、步长 1s | 滑动窗口统计量 | 按时间窗维护统计量 | 换成计数窗口（每 N 个请求）还能工作吗？能 → 上位到「统计窗」 |
| Redis 存桶状态 | 外部共享状态存储 | 桶状态可被多个决策实例读取 | 换成本地内存 + 定期同步还能工作吗？能 → 上位到「可访问的状态存储」 |
| sidecar 部署 | 靠近请求入口的决策点 | 在请求进入业务处理前完成准入判定 | 部署在集中式网关还能工作吗？能 → 上位到「请求路径上的准入节点」 |
| 指数加权移动平均 | 带时间衰减的统计量 | 桶内独立统计 | 换成简单均值还能工作吗？能（但效果差）→ EWMA 属 L2 |

**这张表交给代理人时，附带一句**：「以上等价性判断由发明人基于方案机理给出，未逐一实测；标 `[未实测]` 的行请代理人谨慎上位化。」——诚实标注比假装确定更有价值。

## 四、独立/从属的布局思路（交底层面的理解）

```
独立权利要求（上位、宽）
  └── 包含且仅包含 L1 全部必要技术特征
       │
       ├── 从属 1（加 L2-⑥）      ← 第一道退守防线
       │    └── 从属 2（加 L2-⑦） ← 第二道
       │         └── 从属 3（加 L3 具体值范围） ← 最窄但最容易站住
       │
       └── 从属 4（加 L2-⑧）      ← 并列的另一条退守路径
```

交底书里要提供的输入：

| 输入 | 用途 |
|---|---|
| L1/L2/L3 三层表 | 代理人划定独权与从权的层次 |
| 每条 L2 的「额外效果」 | 代理人写从属权利要求时的技术依据（也是创造性论证素材） |
| 上位化等价性确认表 | 代理人判断能上位到哪一层 |
| 第 9 节的可替代方案 | 避免独权把保护范围钉在单一实现路线上 |
| 检索到的 D1 + 区别特征 | 代理人判断哪一层能站住 |

**发明人不要做的事**：不要在交底书里写「权利要求 1：一种……方法，其特征在于包括以下步骤……」这种正式权利要求文本。写了反而有害——代理人会以为这就是发明人的定稿，或者要花力气推翻它。交底书只给**特征清单 + 分层 + 等价性判断**。

## 五、拆分申请的判据

一份交底书对应一件申请是默认假设。出现以下情况要考虑拆：

| 情形 | 判据 | 处置 |
|---|---|---|
| 两个发明点各自解决独立的技术问题 | 去掉其中一个，另一个仍完整成立；各自有不同的 D1 | **拆成两件**，各写一份交底书 |
| 发明点 B 是发明点 A 的优选实现 | B 依赖 A 才能工作；B 的 D1 与 A 相同 | **不拆**，B 作为 A 的 L2 |
| 发明点 A 是方法，B 是承载该方法的系统/装置 | 同一发明构思的不同权利要求类别 | **不拆**，同一件里写方法权利要求 + 系统权利要求（由代理人处理） |
| 发明点 A 是通用机制，B 是 A 在某个垂直场景的特化 | B 的特化本身带来了 A 没有的额外技术效果 | **可拆**：A 一件（宽），B 一件（窄但更稳） |
| 一份交底书里 L1 超过 12 条且能分成两组互不依赖的特征 | 每组各自构成完整的技术方案 | **拆成两件** |

**拆分的时间成本**：每件申请都要跑完整的检索 + 九节撰写。发明点数量 > 3 时，先按上表排优先级，把最强的一件做完，其余登记在「待交底清单」里排队，不要同时铺开五件半成品。

## 六、输出格式

Step 4 的产物直接粘进交底书（在第 4 节之后、第 5 节之前，或作为附录 B）：

```markdown
## 附录 B：特征分层与布局建议（发明人判断，供代理人参考）

### B.1 三层特征表
| 层 | 特征编号 | 特征描述 | 去掉后是否仍能解决技术问题 | 额外效果 |
|---|---|---|---|---|
| L1 | F1 | 从请求中提取多维字段构成请求指纹 | 否（无法分组） | — |
| L1 | F2 | 按指纹对请求聚类分桶 | 否（退化为全局限流，即 D1） | — |
| L2 | F6 | 指纹字段按区分度打分选择 | 是，但高维下聚类不稳定 | 桶数从 10^4 降至 ~200 |
| L3 | F10 | 桶状态存于 Redis | 是，可换任意共享存储 | — |

### B.2 上位化等价性确认
（见上表格式，标 [未实测] 的行请谨慎上位化）

### B.3 拆分建议
本案含 1 个主发明构思（自适应分桶限流）。发明点「指纹字段自动选择」
建议作为从属层次保留在同一件内，理由：脱离分桶限流场景无独立技术问题。

### B.4 待代理人确认
- F2 是否可上位为「按请求特征分组」而不限于「聚类」
- L1 中 F5（准入判定）是否为常规手段，可否省略
```
