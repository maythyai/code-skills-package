# 现有技术检索与区别特征分析

**读这份文件的时机**：Step 3 开始检索之前。用 WebSearch 时按本文件的检索式模板构造查询，不要只搜一次就下结论。

## 零、先把立场摆正

> **找到最接近的现有技术不是坏事，是交底书最有价值的部分。**

发明人常见反应是「找到一篇很像的 → 那我们是不是不能申请了 → 干脆别写进交底书」。这是错的，而且错得很贵：

- 你不写，代理人不知道 D1 存在，会按错误的现有技术基础撰写，审查员一检就中，答复成本更高。
- 你写了，区别技术特征就是创造性的落点。绝大多数专利都不是「从零到一」的全新事物，而是「在 D1 基础上的一个非显而易见的区别」。
- 检索不到任何东西才是最坏情况：说明要么发明点表述太抽象（检索式无法构造），要么这个领域你根本不熟。

**交底书里必须出现的一句话**：「在本轮检索范围内，最接近的现有技术是 D1（编号 R_），本发明与 D1 的区别技术特征为 …… 」

## 一、检索什么

| 源类别 | 具体来源 | 能证明什么 | 注意事项 |
|---|---|---|---|
| **专利文献** | 各国/地区专利局官方公开检索系统（多数提供免费的申请公开全文库）；国际组织的全球专利数据库；企业订阅的商业专利检索平台 | 已申请/已授权的技术方案，含申请日与公开日 | **申请公开通常有 18 个月延迟**——最近 18 个月的申请大多查不到，这是「检索不到」的最常见原因 |
| **学术文献** | 学术论文库、预印本平台、会议论文集 | 技术方案的最早公开时间可能远早于专利 | 用 `csp-literature-review` 的方法做系统性检索 |
| **开源项目** | 公开代码托管平台的仓库、issue、设计文档（RFC/Design Doc）、CHANGELOG | 公开使用与公开实施的证据 | 代码本身可能构成公开；提交时间戳是关键证据 |
| **产品文档** | 厂商技术文档、白皮书、API 参考、发布会材料、开发者大会录像 | 公开销售/公开使用的证据 | 注意归档快照（历史版本文档） |
| **标准与规范** | 标准组织的公开文稿、提案、工作组纪要 | 标准必要专利相关，且公开时间明确 | 标准提案往往早于最终标准数年 |
| **其他公开** | 技术博客、行业分析报告、招标/投标文件、学位论文、专利失效公告 | 任何使公众能够得知技术内容的公开 | 内部文档不算公开，除非能证明外部可获取 |

**优先级**：先专利库（结构化、有时间戳、直接对应审查员会用的库）→ 再学术与开源（补时间线）→ 最后产品文档与博客（补公开使用证据）。

## 二、检索式怎么构造

### 三轮法（每轮都要记录，不要只在脑子里搜）

**第一轮：关键词扩展**

不要只搜一个说法。按下表把发明点拆成「问题域 / 手段域 / 效果域」三组，每组做中英同义扩展：

| 维度 | 发明点原文 | 中文同义/上位 | 英文同义/上位 |
|---|---|---|---|
| 问题域 | 限流误杀正常请求 | 流量控制、过载保护、请求准入、服务降级 | rate limiting, throttling, admission control, overload protection, load shedding |
| 手段域 | 按请求指纹聚类分桶 | 请求特征分组、流量画像、多维分组统计、聚类推导阈值 | request fingerprinting, traffic classification, per-key rate limiting, adaptive threshold, sliding window, token bucket |
| 效果域 | 阈值随流量结构变化自适应 | 动态阈值、自调整参数、反馈控制 | adaptive, dynamic threshold, self-tuning, feedback control |

构造查询时用「问题域 × 手段域」交叉，不要三域一起搜（命中率过低）：

```
("rate limiting" OR "throttling" OR "admission control")
AND ("adaptive threshold" OR "dynamic threshold" OR "self-tuning")
AND ("request fingerprint" OR "traffic classification" OR "per-key")
```

用 WebSearch 时把它压成自然语言查询，并**至少跑 4 个变体**：

```
1. adaptive rate limiting dynamic threshold request fingerprint
2. per-key rate limiting sliding window token bucket algorithm
3. 自适应限流 动态阈值 请求特征 分组
4. traffic classification overload protection admission control patent
```

**第二轮：分类号检索**

专利库支持按国际专利分类（IPC）或联合专利分类（CPC）检索。软件类常用入口（**具体号段随分类表版本变化，以库内分类表为准，此处只给检索思路**）：

| 大方向 | 检索思路 |
|---|---|
| 数字计算 / 数据处理 | IPC `G06F` 下的相关小类（内存管理、任务调度、错误恢复） |
| 数据传输 / 网络 | IPC `H04L` 下的相关小类（流量控制、拥塞控制、协议） |
| 机器学习应用 | IPC `G06N` + 应用领域分类号交叉 |
| 数据库 | IPC `G06F16/xx` |

做法：先找到 2–3 篇高度相关的专利，看它们的分类号，再用该分类号 + 关键词做二次检索。**这是提高召回率最有效的一步**，因为分类号能捞到用词完全不同但技术相同的文献。

**第三轮：引文追踪**

对找到的最相关的 3–5 篇：

- **向后追踪（backward）**：看它引用了谁 → 找到更早的现有技术，可能比 D1 更接近
- **向前追踪（forward）**：看谁引用了它 → 找到后续改进，其中可能已经有一篇和本发明相同
- **同族追踪**：同一发明的不同国家申请，可能有一族的说明书更详细
- **申请人追踪**：同一申请人在该方向的连续申请，往往勾勒出完整技术演进线

### 检索停止条件

满足以下全部即可停：

```
[ ] 三轮都跑过（关键词扩展 / 分类号 / 引文追踪）
[ ] 中英文各至少 4 组查询变体
[ ] 连续两组新查询没有产生新的高相关（★★★）命中
[ ] 已找到至少 1 篇可作为 D1 的文献；若确实没有，已记录「在本轮检索范围内未发现」并列出跑过的检索式
[ ] 检索记录表已填完，含每条的公开日
```

**不要追求穷尽**——穷尽检索是代理人在正式申请前做的事。交底阶段的检索目的是：给代理人一个起点，并把最明显的 D1 找出来。一般 30–60 分钟、10–20 条记录足够。

### 「检索不到」怎么写

**不要写**：「经检索，本发明具备新颖性和创造性。」（越界 + 无依据）

**要写**：

```markdown
本轮检索共执行 12 组检索式（见附录 A），覆盖专利公开库、学术预印本平台、
公开代码托管平台三类来源，检索时间 2026-10-14。

在本轮检索范围内未发现与本发明全部技术特征相同的单篇文献。最接近的
现有技术为 R3（相关度 ★★），其公开了 F1、F2，未公开 F3、F4。

已知局限：专利公开存在约 18 个月延迟，2025-04 之后的申请多数不可见；
本轮未覆盖 {PATENT_DB} 的全文语义检索。请代理人在正式检索中补充。
```

每条命中一行。**这张表直接附在交底书末尾，代理人会用它。**

| 编号 | 来源类型 | 标题 | 公开日 | 出处（库名/编号/URL 占位） | 相关度 | 披露的技术特征 | 与本发明的区别 |
|---|---|---|---|---|---|---|---|
| R1 | 专利 | 一种基于令牌桶的接口限流方法 | 2019-06-12 | `{PATENT_DB}` / 公开号 `[TBD]` | ★ | F1 令牌桶、F2 全局阈值 | 无分桶，无自适应 |
| R2 | 开源 | 某网关限流插件设计文档 | 2021-03-04 | `{CODE_HOST}` / `[TBD]` | ★★ | F1、F2、F3 按 key 分组 | 分组维度固定为单一 key，未按指纹聚类；阈值仍为静态配置 |
| R3 | 论文 | Adaptive Overload Control for Microservices | 2022-09 | `{PAPER_DB}` / `[TBD]` | ★★★ | F1、F2、F4' 反馈式动态阈值 | 阈值按全局延迟反馈推导，非按桶独立推导；无指纹聚类 |
| R4 | 产品文档 | 某云厂商 API 网关限流配置说明 | 2023-11 | `[TBD]` | ★ | F1、F2 | 仅描述配置项，未公开算法 |

**相关度打分标准**：

| 星级 | 定义 |
|---|---|
| ★★★ | 披露了本发明的核心技术手段，可直接作为 D1 |
| ★★ | 披露了部分必要技术特征，属于同一技术方向 |
| ★ | 同一应用领域但手段不同，仅作背景 |

**规则**：★★★ 的命中**必须**做区别特征三问；★★ 至少 2 条做三问；★ 只登记不分析。

## 四、区别特征三问

对每条区别（本发明有、D1 没有的技术特征）填这张表：

| 问 | 要求 | 合格示例 | 不合格示例 |
|---|---|---|---|
| **① 区别是什么** | 用技术特征语言，能被写进权利要求 | 「按请求指纹（方法+路径+参数哈希+客户端类型）对请求做聚类分桶，桶内独立维护滑动窗口统计量并独立推导阈值」 | 「更精准的限流」「智能化限流」 |
| **② 解决了 D1 解决不了的什么问题** | 必须对应 D1 的一个**具体失效条件** | 「D1（R3）按全局延迟反馈推导阈值，当流量中混杂两类结构差异大的请求（如批量导出与实时查询）时，全局延迟被批量请求拉高，导致实时请求被误杀；实测误杀率 12%」 | 「解决了限流不准确的问题」（没有失效条件，等于没说） |
| **③ 带来什么可量化技术效果** | 数值 + 测量口径 | 「同一压测脚本、同一混合流量数据集、4C8G × 3 节点：误杀率 12% → 1.8%，P99 时延 820ms → 210ms，吞吐 -3%（代价）」 | 「显著提升准确性」「性能大幅优化」 |

**第 ② 问是分水岭。** 答不出具体失效条件的区别，几乎必然是常规改进（例如「加了缓存」「用了更好的库」「参数调优」），写进交底书只会稀释真正的发明点。

**多区别的处理**：一份交底书通常有 1 条主区别 + 0–3 条次区别。主区别对应独立权利要求，次区别对应从属层次。若出现 2 条互不依赖的主区别 → 回到 Step 1 判断是否应拆成两件申请。

## 五、检索规避（Design-Around 记录）

检索中发现某篇文献**几乎覆盖**了本方案时，不要放弃，按下面顺序处理：

1. **精确定位覆盖到哪一步。** 逐特征比对：F1 ✓ / F2 ✓ / F3 ✗ / F4 ✗。
2. **判断未覆盖的特征是否是发明点的核心。** 若核心特征未被覆盖 → 正常写，把该特征作为主区别。
3. **若核心特征被覆盖** → 记录该文献为 D1，然后在第 9 节「可替代方案与扩展」里主动写出**规避路线**：换一种手段达到同一技术效果（例如把「聚类分桶」换成「基于哈希的一致性分组 + 桶内反馈控制」）。这既是给代理人的输入，也是防止竞品用规避设计绕开你。
4. **同时评估 FTO 风险**：若该文献是**有效专利**且本方案已实施，这已经不是交底书问题，而是侵权风险问题——**立即上报法务，不要自行判断**。本技能不做 FTO 分析。

**规避记录模板**：

```markdown
### 检索规避记录

| D1 编号 | 覆盖的特征 | 未覆盖的特征 | 处置 |
|---|---|---|---|
| R3 | F1 令牌桶、F2 滑动窗口、F4' 反馈式阈值 | F3 指纹聚类分桶、F5 桶级阈值独立推导 | 以 F3+F5 为主区别撰写；第 9 节补 2 条规避路线 |

法务上报：R3 为有效专利（权利状态待核实），本方案已在生产环境实施 → 已提交 FTO 评估请求，工单 `[TBD]`。
```
