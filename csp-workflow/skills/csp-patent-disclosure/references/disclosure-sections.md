# 交底书九节：逐节写作要求

**读这份文件的时机**：Step 5，逐节撰写时打开对照写。不要凭记忆。

九节顺序固定不可调：

```
1 技术领域      2 背景技术与现有技术缺陷   3 发明目的与要解决的技术问题
4 技术方案详述  5 有益效果                6 具体实施例
7 附图说明      8 关键术语定义            9 可替代方案与扩展
```

全篇贯穿一个示例（自适应限流方案），便于对照。**写作时换成你自己的方案，但保留同样的具体程度。**

## 第 1 节：技术领域

| 项 | 内容 |
|---|---|
| **目的** | 帮代理人确定 IPC/CPC 分类号，从而框定审查员的检索范围。分类号错了，审查员会检索到不相关的文献，或漏检相关文献 |
| **必填要素** | ① 一句话技术领域定位；② 所属技术分支（方法/系统/装置/存储介质）；③ 应用的具体技术场景 |
| **写作要点** | 句式：「本发明涉及 X 技术领域，特别涉及一种 Y 方法/系统/装置。」X 写到能定分类号的粒度（如「计算机网络流量控制」而非「互联网」）；Y 用技术手段命名，不用产品名、不用功能名 |
| **长度** | 2–4 句，不超过 80 字 |

**填好的示例**：

> 本发明涉及计算机网络数据处理技术领域，特别涉及分布式服务系统中的请求流量控制。具体地，本发明涉及一种基于请求特征分组的自适应准入控制方法及系统，可用于服务端在混合流量场景下的过载保护。

**常见错误**：

| 错误 | 为什么错 |
|---|---|
| 「本发明涉及一款面向电商平台的智能流量管理产品」 | 产品名 + 行业名不是技术领域；代理人无法定分类号 |
| 「本发明涉及人工智能、大数据、云计算领域」 | 堆砌热词，等于没说；三个方向对应完全不同的分类号 |
| 只写一句「涉及计算机技术领域」 | 粒度过粗，G06F 下有数千个小类 |
| 把应用场景当成技术领域（「涉及双十一大促场景」） | 场景属于第 2 节背景；技术领域要写技术手段所属的分支 |

## 第 2 节：背景技术与现有技术缺陷

| 项 | 内容 |
|---|---|
| **目的** | 为创造性论证搭台。审查员判断创造性时会看：本发明解决的问题在现有技术中是否已被认识、是否已被解决。这一节写不清，第 5 节的效果就没有参照系 |
| **必填要素** | ① 现有主流做法（**至少 2 种**，各自的原理一句话）；② 每种做法的**工作条件**；③ 每种做法的**失效条件**（在什么情况下会怎样失效）；④ **失效机理**（为什么会失效）；⑤ 对应的现有技术出处（来自 Step 3 检索记录表的编号） |
| **写作要点** | 每条缺陷必须写成四段式：「现有方案 X 在 **[条件]** 下会 **[失效现象]**，因为 **[机理]**，导致 **[可量化的后果]**。」缺陷条数与第 5 节效果条数**一一对应闭环** |

**填好的示例**：

> **现有做法一：全局固定阈值限流。** 服务端在请求入口处维护一个全局令牌桶，桶容量与填充速率由运维人员按历史峰值 QPS 静态配置（见检索记录 R1）。
>
> - 工作条件：流量结构稳定，请求类型单一，峰值可预测。
> - 失效条件：当流量中出现结构差异较大的多类请求混合时（例如批量导出请求与实时查询请求同时到达，前者单请求耗时长、占用连接时间约为后者的 40 倍）。
> - 失效现象与后果：全局令牌被长耗时请求快速消耗，短耗时的实时查询请求被拒绝。实测在某混合流量压测集（批量:实时 = 1:9）下，实时请求误杀率达 12.3%，而这些请求本身的资源占用仅占总量约 6%。
> - 失效机理：阈值按全局聚合量推导，无法区分不同请求类别的资源占用差异，即**统计口径与实际资源消耗口径不一致**。
>
> **现有做法二：基于全局延迟反馈的动态阈值。** 服务端周期性采样全局 P99 延迟，用反馈控制器调整准入阈值（见检索记录 R3）。
>
> - 工作条件：请求同质，延迟分布单峰。
> - 失效条件：流量结构突变（如某类请求占比从 5% 突增至 40%）。
> - 失效现象与后果：全局 P99 被新出现的高耗时请求类拉高，控制器收紧全局阈值，导致原本健康的低耗时请求类也被限流。实测该场景下误杀率 9.8%，且阈值收敛需要 3–5 个反馈周期（约 30s），期间服务处于错误限流状态。
> - 失效机理：**反馈信号是全局聚合量，控制作用也施加在全局，缺少按请求类别解耦的中间层。**
>
> **现有做法三：按单一固定 key 分组限流。** 网关按 `用户 ID` 或 `接口路径` 单一维度分组，每组独立配额（见检索记录 R2）。
>
> - 工作条件：分组维度与资源占用强相关，且分组基数可控。
> - 失效条件：资源占用由多个字段共同决定（方法 + 路径 + 参数规模 + 客户端类型），单维度分组无法刻画。
> - 失效现象与后果：同一 `接口路径` 下参数量级相差 10³ 的请求被划入同组，小组被大请求拖垮；同时按 `用户 ID` 分组会产生 10⁶ 量级的组，每组独立维护滑动窗口的内存开销约 2KB，总开销达 GB 级，不可承受。
> - 失效机理：**分组维度选择依赖人工经验且静态固定，无法随流量结构变化自适应，也无法在分组精度与状态存储开销之间取得平衡。**

**常见错误**：

| 错误 | 为什么错 | 改成 |
|---|---|---|
| 「现有技术效率低、体验差」 | 空话，无法作为创造性论证的参照系 | 具体失效条件 + 现象 + 机理 + 量化后果 |
| 「目前还没有很好的解决方案」 | 没有检索支撑的主观断言 | 引用检索记录编号 R_n，说明查到的具体方案及其局限 |
| 只写一种现有做法 | 单一对比容易被代理人认为参照系不足 | ≥2 种，覆盖不同技术路线 |
| 缺陷写了 3 条，第 5 节只回答 1 条 | 闭环断裂，创造性论证断链 | 每条缺陷必须有对应的效果行 |
| 在背景技术里夸本发明（「本发明巧妙地解决了……」） | 第 2 节只写现有技术，夸自己会削弱客观性 | 本发明的内容全部放第 3–6 节 |
| 把商业痛点当技术缺陷（「运营成本高」） | 商业痛点不是技术问题 | 翻译成技术语言：「人工配置阈值需每次流量结构变更后重新压测，平均耗时 2 人日」 |

## 第 3 节：发明目的与要解决的技术问题

| 项 | 内容 |
|---|---|
| **目的** | 把整份交底书锚定在一个可测量的技术问题上。这是后续所有特征分层判断（「去掉它还能解决这个问题吗」）的基准 |
| **必填要素** | ① 技术问题（一句话，可测量）；② 发明目的（要达到的技术状态）；③ **非目的**（明确排除的目标，帮助代理人划边界） |
| **写作要点** | 技术问题必须是**技术问题**，判据：能否用一个可测量的技术指标来定义「解决了」。目的要落在计算机系统自身指标上（时延、吞吐、误判率、内存、CPU、网络包数、功耗），不落在业务指标上（GMV、留存、转化率） |

**填好的示例**：

> **要解决的技术问题**：在多类结构差异较大的请求混合到达、且各类请求占比随时间变化的场景下，如何在**不显著增加状态存储开销**（单节点额外内存 ≤ 50MB）的前提下，把**低耗时请求类被误拒绝的比例**从现有技术的 9.8%–12.3% 降至 3% 以下，同时把**阈值收敛时间**从 30s 降至 5s 以内。
>
> **发明目的**：提供一种请求准入控制方法，使准入阈值的推导粒度与请求的实际资源占用模式对齐，并且分组数量可自动收敛到可控规模。
>
> **非目的（明确排除）**：
> - 不解决跨数据中心的多活流量调度问题（本案仅在单集群内生效）。
> - 不解决请求优先级排序问题（本案对同桶内请求采用先到先服务，不引入优先级）。
> - 不以提升业务转化率为目标；所述效果均为计算机系统层面指标。

**常见错误**：

| 错误 | 改法 |
|---|---|
| 「本发明的目的是提升系统性能和用户体验」 | 拆成可测量指标：哪个性能指标、从多少到多少 |
| 「目的是降低获客成本 / 提升 GMV」 | 业务目标不是技术问题；找到它背后的技术瓶颈（如「单请求成本」→「单位 QPS 的 CPU 占用」） |
| 技术问题写了 5 条 | 一份交底书一个发明构思 → 一个主技术问题；次要问题写成子问题并标明从属关系 |
| 没有「非目的」 | 加上。这是最省力的一条防越界措施，能避免代理人把权利要求写得过宽而被驳回 |
| 目的与第 2 节缺陷对不上 | 逐条核对：第 2 节每个失效机理都应在第 3 节有对应目的 |

## 第 4 节：技术方案详述（最重的一节）

**这一节写不到「本领域技术人员照着能实现」的程度，其余八节写得再漂亮也是废稿。**

| 项 | 内容 |
|---|---|
| **目的** | 满足「充分公开」要求：本领域技术人员阅读后**不需要创造性劳动**即可实现该方案。同时为代理人提供全部技术素材 |
| **必填要素** | ① 整体架构与数据流；② 完整编号步骤流程（含子步骤、判定条件、异常分支）；③ 系统模块划分与连接关系；④ 关键数据结构（字段/类型/取值范围/生命周期）；⑤ 参数与取值范围（默认值 + 边界 + 选取依据）；⑥ 可选实施例的并列方案 |
| **验收标准** | 把这一节交给一个没参与过项目的同领域工程师，他能否独立实现出功能等价的系统？不能 → 补 |
| **长度** | 通常占全文 40%–55%。少于全文 1/3 基本可以判定公开不足 |

### 4.1 整体架构与数据流

写清模块清单 + 每个模块的职责 + 模块间连接关系 + 数据流向。

**填好的示例**：

> 系统由五个模块构成，部署于服务网格的数据面 sidecar 与集群级协调器两层：
>
> | 标号 | 模块 | 部署位置 | 职责 | 输入 | 输出 |
> |---|---|---|---|---|---|
> | 101 | 指纹提取模块 | sidecar | 从请求元数据中提取多维字段，计算指纹 | HTTP 请求头 + 路由信息 + 参数摘要 | 指纹值（64-bit） |
> | 102 | 分桶模块 | sidecar | 按指纹将请求映射到桶；维护桶注册表 | 指纹值 | 桶 ID |
> | 103 | 桶级统计模块 | sidecar（本地）+ 协调器（聚合） | 每桶独立维护滑动窗口统计量 | 桶 ID + 请求耗时 + 结果码 | 桶状态记录 |
> | 104 | 阈值推导模块 | 协调器 | 按桶状态独立推导该桶准入阈值 | 桶状态记录 | 桶阈值 + 生效时间戳 |
> | 105 | 准入判定模块 | sidecar | 按桶阈值执行准入/拒绝 | 桶 ID + 桶阈值 | 放行 / 拒绝（含 429 与 Retry-After） |
>
> 数据流：请求 → 101 → 102 → 105（判定，使用 104 下发的当前阈值）→ 业务处理 → 103（回填实际耗时与结果）→ 周期性上报协调器 → 104 → 下发新阈值至 105。
>
> 102 与 104 之间存在一条控制回路：当桶总数超过上限 `B_max` 时，102 触发指纹字段重选（见步骤 S2.3），并将新桶注册表同步至 104。

### 4.2 编号步骤流程

**要求**：主步骤 `S1…Sn`，子步骤 `S1.1、S1.2`。每步写清**输入 / 处理 / 判定条件 / 输出 / 异常分支**。禁止「系统对数据进行分析」这类概念层描述。

**填好的示例（节选）**：

> **S1 指纹提取**
> - S1.1 从请求中提取候选字段集合 `C = {HTTP method, path 模板, 查询参数键集合的哈希, 请求体大小分档, 客户端类型}`。path 模板指路由匹配后的模板串（如 `/orders/{id}`），不含具体 id 值。
> - S1.2 请求体大小分档：按 `size ≤ 1KB → 0`、`1KB < size ≤ 64KB → 1`、`size > 64KB → 2` 三档编码。
> - S1.3 对 `C` 中每个字段做稳定哈希，按固定顺序拼接后取 64-bit 指纹 `fp`。
> - S1.4 **异常分支**：若 path 未匹配任何路由模板（404），`fp` 置为保留值 `0x0`，归入兜底桶 `B0`，不参与桶阈值推导，直接使用全局兜底阈值 `T_global`。
>
> **S2 分桶**
> - S2.1 查询桶注册表 `R`（哈希表，键为 `fp`，值为桶 ID）。命中则返回桶 ID。
> - S2.2 未命中时，若 `|R| < B_max`（默认 `B_max = 512`），分配新桶 ID，初始化桶状态。
> - S2.3 未命中且 `|R| ≥ B_max` 时，触发**字段重选**：
>   - S2.3.1 对 `C` 中每个字段计算区分度 `D(field) = H(该字段值分布) / log(取值数)`，其中 `H` 为按最近窗口统计的香农熵。
>   - S2.3.2 计算稳定性 `S(field) = 1 - (本窗口取值集合与上窗口取值集合的 Jaccard 距离)`。
>   - S2.3.3 打分 `score = 0.6·D + 0.4·S`，取 `score` 最高的 `k` 个字段（`k` 默认 3，取值区间 [2, 5]）构成新的候选集 `C'`。
>   - S2.3.4 用 `C'` 重算所有活跃请求的指纹，重建 `R`；旧桶状态按最近邻映射迁移（映射规则：旧桶的样本指纹在新 `C'` 下的众数桶）。
>   - S2.3.5 **约束**：字段重选每 `T_reselect`（默认 300s，区间 [60s, 3600s]）内至多触发一次，避免抖动。
> - S2.4 **异常分支**：重选后 `|R|` 仍 ≥ `B_max`，则按桶内请求数升序合并最小的两个桶，直至 `|R| < B_max`。
>
> **S3 桶级统计**（略，同格式）
> **S4 阈值推导**（略）
> **S5 准入判定**（略）

### 4.3 关键数据结构

**填好的示例**：

> **桶状态记录 `BucketState`**
>
> | 字段 | 类型 | 取值范围 / 约束 | 含义 | 生命周期 |
> |---|---|---|---|---|
> | `bucket_id` | uint32 | [1, B_max] | 桶标识 | 桶创建至淘汰 |
> | `fingerprint` | uint64 | — | 该桶对应的指纹值 | 同上；字段重选后重建 |
> | `window_counts` | uint32[W] | W 默认 10，区间 [5, 60] | 滑动窗口内各子窗请求数 | 每步长滚动 |
> | `window_cost` | float32[W] | ≥ 0 | 各子窗累计资源占用（按实测耗时的归一化值） | 同上 |
> | `ewma_cost` | float32 | ≥ 0 | 指数加权移动平均的单请求资源占用，衰减系数 α 默认 0.2，区间 [0.05, 0.5] | 持续更新 |
> | `threshold` | uint32 | [T_min, T_max]，默认 [50, 500] | 当前准入阈值（QPS） | 每次推导更新 |
> | `last_update_ts` | int64 | — | 最近更新时间戳（毫秒） | — |
> | `state_flag` | enum | {COLD_START, ACTIVE, IDLE, MERGED} | 桶生命周期状态 | — |
>
> 存储开销：单桶约 `4 + 8 + 4·W·2 + 4·3 + 8 + 1 ≈ 115 B`（W=10）。`B_max = 512` 时总计约 58KB，满足第 3 节「单节点额外内存 ≤ 50MB」约束（余量用于哈希表与索引）。
>
> **淘汰规则**：`state_flag = IDLE`（连续 `T_idle` = 600s 无请求）的桶在下次字段重选时不迁移，直接释放。

### 4.4 参数与取值范围

**铁律：不要只给一个值。** 单点值把保护范围钉死在一个数字上。

| 参数 | 符号 | 默认值 | 取值区间 | 选取依据 | 超出区间的后果 |
|---|---|---|---|---|---|
| 最大桶数 | `B_max` | 512 | [64, 4096] | 受单节点内存预算与聚类稳定性共同约束 | < 64 分组过粗，退化为全局限流；> 4096 状态开销与噪声桶比例上升 |
| 窗口子窗数 | `W` | 10 | [5, 60] | 需覆盖至少一个业务波动周期 | < 5 抖动大；> 60 收敛变慢 |
| 步长 | `Δt` | 1s | [0.5s, 10s] | 与统计上报周期一致 | > 10s 阈值滞后于流量变化 |
| EWMA 衰减系数 | `α` | 0.2 | [0.05, 0.5] | 平衡平滑度与响应速度 | — |
| 字段数 | `k` | 3 | [2, 5] | 区分度与信息冗余的折中 | k=1 退化为现有做法三 |
| 重选冷却时间 | `T_reselect` | 300s | [60s, 3600s] | 防止桶注册表抖动 | < 60s 观测到桶 ID 频繁变化，下游缓存失效 |
| 滞回区间 | `h` | 10% | [0%, 30%] | 避免阈值在边界反复调整 | h=0 时观测到阈值每秒抖动 |

### 4.5 可选实施例的并列方案

对同一发明构思给出**并列可行的实现路线**（不是替代发明点，而是同一发明点的不同实现）。这一小节直接决定保护范围会不会被钉死在一种实现上。

**填好的示例**：

> 指纹计算可采用以下任一方式，均落入本发明的构思：
> - **实施例 4-A**：字段拼接后取稳定哈希（如 SipHash-2-4），输出 64-bit。优点：状态小；缺点：不可解释。
> - **实施例 4-B**：将各字段编码为 one-hot 后做 SimHash，输出 64-bit。优点：相近请求指纹汉明距离小，可按汉明距离阈值合并相似桶；缺点：字段取值基数大时精度下降。
> - **实施例 4-C**：使用轻量聚类模型（如在线 Mini-Batch K-Means，`k = B_max`）对请求特征向量做分桶，指纹即簇 ID。优点：分桶边界自适应；缺点：引入模型训练开销，冷启动期分桶不稳定。
>
> 阈值推导可采用：
> - **实施例 5-A**：`threshold_i = C_budget × (1 / ewma_cost_i) / Σ_j(1 / ewma_cost_j)`，即按各桶单位资源占用反比分配全局预算 `C_budget`。
> - **实施例 5-B**：每桶独立跑一个 PI 控制器，设定值为该桶的目标排队时延。
>
> 部署形态可采用：集中式网关单层 / sidecar + 协调器两层（本实施例）/ 客户端 SDK 本地判定 + 服务端配额下发三层。

## 第 8 节：关键术语定义

| 项 | 内容 |
|---|---|
| **目的** | 消除歧义。专利文本里术语的含义决定保护范围；发明人内部黑话与行业通用含义不一致时必须显式定义 |
| **必填要素** | ① 自定义术语（≥3 个）；② 缩写全称；③ **与行业通用含义不同的用法**（最重要，最容易漏） |
| **写作要点** | 格式「【术语】：定义」。定义要可操作（能被判定是否满足），不要循环定义 |

**填好的示例**：

> - 【请求指纹（request fingerprint）】：由请求的多个元数据字段按固定顺序编码后计算得到的定长哈希值，用于将资源占用模式相近的请求映射到同一取值。**本案中专指由 S1.1 所述字段集合计算所得的 64-bit 值**，与「浏览器指纹」「设备指纹」等用于身份识别的含义不同。
> - 【桶（bucket）】：具有相同请求指纹值的请求集合，以及为该集合独立维护的统计量与准入阈值的统称。本案中的桶**不是**存储系统中的数据分片（shard），也不等同于负载均衡中的后端分组。
> - 【误杀率（false rejection rate）】：在准入控制生效期间，被拒绝的请求中「其所在桶的实际资源占用未超过该桶配额」的请求所占比例。判定依据为事后回放时该请求的实测耗时。**注意：本定义为本案自定义口径，与通用限流文献中的 reject rate 不同**（后者不区分是否应当被拒绝）。
> - 【资源占用（cost）】：单个请求对服务端造成的负载的归一化度量，本案中取「请求处理耗时（秒）/ 基准耗时（10ms）」。
> - 【阈值收敛时间】：自流量结构突变发生时刻起，至所有受影响桶的阈值进入其稳态值 ±h 区间并保持 3 个步长所需的时间。
> - EWMA：Exponentially Weighted Moving Average，指数加权移动平均。
> - PI 控制器：Proportional-Integral controller，比例-积分控制器。
> - sidecar：与服务实例同生命周期部署、承担流量治理职能的独立进程。本案中特指服务网格数据面代理。

**常见错误**：

| 错误 | 改成 |
|---|---|
| 只列缩写不列自定义术语 | 自定义术语优先级更高 |
| 循环定义（「桶就是分桶的结果」） | 写清构成条件与判定方法 |
| 内部黑话不解释（「走灰度」「打点」） | 换成技术描述或在术语表中定义 |
| 与行业通用含义冲突却不声明 | 显式写「本案中特指……，与通用含义 X 不同」——这一条能避免代理人和审查员误解保护范围 |

|---|---|
| **目的** | ① 防止独权被钉死在单一实现路线上；② 提前占住竞品可能采用的规避路线；③ 给代理人上位化的技术依据 |
| **必填要素** | ① **至少 2 条真实可行的替代技术路线**，每条含：技术路线描述 / 与本案差异 / 优缺点 / 是否仍解决同一技术问题；② 可扩展的应用场景（同一手段用于其他技术问题）；③ **明确不可行的替代**（帮助代理人划边界） |
| **写作要点** | 替代方案必须是真能跑的路线，不是「本领域技术人员可以想到其他实现方式」这种套话。判断标准：能否说出替代方案的一个具体缺点？说不出 → 你没真想过 |

**填好的示例**：

> **替代路线 A：用规则引擎替代聚类分桶**
> - 描述：不用 S2.3 的自动字段选择，改由运维配置一组分桶规则（如 `path 前缀 + 请求体大小档位`），规则以决策表形式下发。
> - 与本案差异：分组维度由人工静态配置，不随流量结构变化自适应。
> - 优点：可解释性强，无需重选开销，桶 ID 稳定。
> - 缺点：流量结构突变时仍需人工介入；规则数量随业务增长，实测 200+ 规则时求值耗时成为瓶颈。
> - 是否仍解决同一技术问题：部分解决（解决「按类别独立限流」，不解决「分组维度自适应」）。
>
> **替代路线 B：用一致性哈希分组替代指纹聚类**
> - 描述：S1 的指纹改为对 `path 模板 + 参数键集合` 做一致性哈希，映射到固定数量的虚拟节点（`N = B_max`）。
> - 与本案差异：桶数固定，无 S2.3 重选流程；桶边界由哈希环决定而非语义相近性决定。
> - 优点：实现简单，桶数恒定，状态开销可预测。
> - 缺点：资源占用模式不同的请求可能落入同一虚拟节点，分桶精度低于本案（预测试验中误杀率约 5.4%，高于本案 1.8% 但低于现有做法一 12.3%）。
> - 是否仍解决同一技术问题：解决主要问题，但效果劣于本案。
>
> **扩展场景（同一手段的其他应用）**
> - 同一「按资源占用模式分组后独立配额」的手段可用于：数据库连接池分组配额、消息队列消费者分组限速、批处理任务的 IO 预算分配、GPU 推理服务的请求分级排队。
> - 扩展时需替换的仅是 `cost` 的定义（本案中为归一化耗时，扩展为连接占用时长 / 消息处理时长 / IO 字节数 / GPU 显存占用）。
>
> **明确不可行的替代（划边界）**
> - 完全在客户端本地判定阈值而不经任何服务端聚合：无法获得跨实例的全局资源预算 `C_budget`，在实例数变化时阈值失配，实测误杀率回升至 8% 以上。此路线不落入本发明构思。
> - 按 TCP 连接维度而非请求维度分组：长连接复用场景下一个连接承载多类请求，分组失效。

**常见错误**：

| 错误 | 改成 |
|---|---|
| 「本领域技术人员可以想到其他实现方式」 | ≥2 条真实可行路线 + 各自差异 + 各自优缺点 |
| 替代方案写成「换个编程语言」「换个数据库」 | 那是 L3 实现细节，不是替代技术路线；替代要在手段层面 |
| 只写优点不写缺点 | 说不出缺点意味着没真想过；缺点也是划边界的依据 |
| 不写「明确不可行的替代」 | 加上。这是防止代理人过度上位化导致权利要求得不到支持的关键输入 |
| 替代方案与主方案解决不同技术问题 | 标明「是否仍解决同一技术问题」；不解决的部分应作为独立发明点回到 Step 1 |
