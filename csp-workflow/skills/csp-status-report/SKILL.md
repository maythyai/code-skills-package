# 状态报告（Status Report）

## 立场（本技能最重要的一条）

> **状态报告的唯一目的是让读者做决策，不是证明汇报人很忙。**

由这一条推出三条铁律，全篇每一句话都要过这三关：

| 铁律 | 含义 | 违反时的样子 |
|---|---|---|
| **① 坏消息必须和好消息同样显眼** | 风险与阻塞放在报告前 1/3，字号层级与进展一致，不许塞进第 8 段或附录 | 「风险」在文末一段两行，前面七段全是成果 |
| **② 数字必须有口径** | 同一指标在不同期报告里算法必须一致；改口径要**显式声明**并给新旧换算 | 上期「完成率」分母是任务数，本期悄悄换成人日 |
| **③ 不写无法被行动的信息** | 每段都要能回答「读者看完能做什么」。答不出就删 | 罗列 187 个提交、12 场会议、35 个评审 |

**自检问法**：写完每一段，问「如果删掉这段，读者会少做什么决定？」答不上来 → 删。

## 与 `csp-retro` 的分工（必须先分清，否则两份文档都写废）

| 维度 | **状态报告（本技能）** | **复盘 `csp-retro`** |
|---|---|---|
| 时机 | **周期性的、当下的**——本周/本双周/本月结束时 | **事后的、结束的**——项目或里程碑收尾后 N 周 |
| 目的 | **面向决策**：让读者批准资源、解除阻塞、在方案间选择 | **面向学习**：找出哪些押对了、哪些押错了、下次怎么改 |
| 时间指向 | 向前看：下期计划、待决策项、风险触发条件 | 向后看：当初的决策 vs 实际结果 |
| 读者 | 上级、跨团队、高管、团队成员 | 团队自己 + 下个项目的团队 |
| 内容重心 | 事实 + 差距 + 需要的动作 | 因果分析 + lessons learned |
| 长度 | 短（高管版一页内） | 长（可含完整因果链） |
| 是否含 blame | **绝不**——写「X 项连续两期未推进」，不写「谁没做」 | 对事不对人，但要写清决策失误的机理 |
| 失败模式 | 变成成果展览会 | 变成状态报告的加长版 |

**判据**：如果读者看完需要**在本期或下期做一个选择**，那是状态报告。如果读者看完只需要**记住一条经验**，那是复盘。

**边界补充**：

- 项目/里程碑收尾总结 → `csp-retro`
- 里程碑验收（是否达到 gate）→ `csp-audit-milestone` 命令（不是技能）
- 下期计划本身的编制 → `csp-plan-phase`；状态报告只**引用**上期计划并逐项交代，不重新编制计划
- 产品指标的深度分析 → `csp-product-metrics-review`；状态报告只取其中 1–3 个关键数字
- 会议行动项的提取 → `csp-meeting-action-extraction`；状态报告消费其产物作为事实源之一
- 路线图变更 → `csp-roadmap-update`；状态报告中的「待决策项」若被批准，交给它落地
- 让 Agent 自己感知"现在到哪了"以便决定下一步 → `csp-progress` workflow；那是给机器读的上下文，不是给人读的汇报，不要把它当模板用

## When to Use

- 周报 / 双周报 / 月报到期
- 领导问「现在到哪了」，需要一个能决策的回答而不是一段口头汇报
- 有阻塞需要升级，且要附带可选方案与截止时间
- 要建立一个新的汇报节奏，需要一份稳定的模板与口径定义
- 同一批事实要发给四类受众（上级 / 跨团队 / 高管 / 团队内部）

## When NOT to Use

- 项目已结束要做经验沉淀 → `csp-retro`
- 要判断里程碑是否达成 gate → 走 `csp-audit-milestone` 命令
- 要做产品指标的归因分析 → `csp-product-metrics-review`
- 要写技术方案或设计文档 → `csp-tech-solution-design`
- 只是要把会议记录变成任务 → `csp-meeting-action-extraction`
- 要做面向外部的营销/公关稿 → 本技能的立场（坏消息同样显眼）与之直接冲突，不要用

## 主流程

```
Step 0  确认周期、受众、上期报告位置
Step 1  数据采集（每个数字追到一条命令或一个查询）
Step 2  进展事实化（弱写法 → 强写法）
Step 3  主动挖风险（没有风险通常不是好消息）
Step 4  组装三段式骨架
Step 5  按受众裁剪出 N 个版本
Step 6  格式纪律自检 + 落盘
```

### Step 0：确认周期、受众、上期报告

必须先拿到三样东西，缺一样就先问：

| 输入 | 为什么必须 | 缺失时 |
|---|---|---|
| **周期边界**（绝对日期，如 2026-10-05 ~ 2026-10-11） | 所有采集命令的时间窗都基于它；「上周」不是边界 | 问清；不要猜 |
| **受众清单** | 决定裁剪成几个版本、每版多长 | 默认四版全出（见 Step 5） |
| **上期报告路径 + 上期计划清单** | 「上期计划本期必须逐项交代」这条规则的前提 | 用 Glob 找 `docs/analysis/STATUS-*`；找不到则本期显式声明「无上期基线，本期建立基线」 |

产物命名约定：`docs/analysis/STATUS-{团队或项目}-{周期}.md`

周期段写法（**用绝对标识，不用「本周」**）：

| 周期 | 写法 | 示例 |
|---|---|---|
| 周报 | `YYYY-Wnn` | `STATUS-payments-2026-W41.md` |
| 双周报 | `YYYY-Wnn-Wmm` | `STATUS-payments-2026-W40-W41.md` |
| 月报 | `YYYY-MM` | `STATUS-payments-2026-09.md` |

### Step 1：数据采集

**规则：报告里的每个数字都要能追到一条命令或一个查询。** 不能凭印象，不能「大概是」。

事实源与对应的采集方式（含可跑的 `git log` 命令模板、如何排除 merge 提交与自动化提交避免虚高、工单系统/发布记录/监控告警/会议纪要各取什么字段）见 `references/data-collection.md`——**动手采集前读它，命令直接从里面复制改参数**。

采集产出：一张「事实底稿」表，每行含 `指标 / 数值 / 来源命令或查询 / 采集时间 / 口径定义`。这张表不一定要发出去，但**必须存在**——它是铁律②（口径一致）的唯一保障。

### Step 2：进展事实化

把「推进了 X」翻译成「**X 从 A 状态到 B 状态，剩余 C**」。

| 弱写法 | 强写法 |
|---|---|
| 优化了性能 | P95 响应从 820ms 降到 210ms，覆盖 3 个核心接口，已在预发验证（压测脚本与口径见附录） |
| 推进了重构 | 订单模块从「双写未切流」到「灰度 10% 切流、错误率 0.02%」，剩余：全量切流 + 老表下线 |
| 跟进了对接 | 与结算系统的接口联调从「未开始」到「4/7 接口通过」，剩余 3 个阻塞在对方环境的证书问题（见风险 R2） |
| 完成了大部分开发 | 12 个任务中 8 个已合并主干、2 个在评审、2 个未开始（原因：依赖 R1） |

**完成度用可验证的里程碑，不用百分比。** 「70%」不可验证——分母是什么？如果一定要用百分比，必须写明分母（「12 个任务中 8 个已合并 = 67%，分母为本期计划任务数，不含新增插入项」）。

完整的弱写法/强写法对照表（14 组）与里程碑式完成度的写法见 `references/writing-patterns.md`（**Step 2 与 Step 4 都要读**）。

### Step 3：主动挖风险

> **没有风险不是好消息，通常是没看清。**

写「暂无风险」之前，必须按五个信号源各过一遍：

| # | 信号源 | 怎么查 | 命中即成为风险条目 |
|---|---|---|---|
| 1 | **依赖方的沉默** | 上期发出的对接请求/评审请求，本期有无回复？超过 5 个工作日无回复即为信号 | 「已发出 N 天未获回复，若继续沉默将在 {日期} 阻塞 {项}」 |
| 2 | **连续两期未推进项** | 对比上期与本期的事实底稿，状态未变的项 | 「{项} 连续 {N} 期状态未变，当前处于 {状态}」 |
| 3 | **单人关键路径** | 某条路径上只有一个熟悉的人；查代码托管平台的作者分布 | 「{模块} 本期 {N}% 的改动来自单一作者，无第二人熟悉」 |
| 4 | **无测试覆盖的高频改动区** | 本期改动最集中的目录 × 测试覆盖情况 | 「{目录} 本期 {N} 次改动、{M} 行变更，无对应自动化测试」 |
| 5 | **临近截止但完成度低** | 剩余工作日 vs 剩余里程碑数 | 「距 {日期} 剩 {N} 个工作日，剩余 {M} 个里程碑未达成，按本期速率需 {K} 个工作日」 |

每条风险必须有**五要素**，缺一条就不算写完：

```
风险描述 / 触发条件 / 影响 / 当前应对 / 需要什么支持
```

按严重度排序（阻塞当前周期 > 阻塞下个周期 > 影响质量 > 影响效率）。

### Step 4：组装三段式骨架

三段顺序固定：**进展 → 风险与阻塞 → 需要决策的事项**。

第三段是整份报告最有价值的部分。**不要只抛问题不给选项，也不要替读者做决定。** 每个决策项必须含：

```
背景一句 / 可选方案 2–3 个及各自代价 / 建议方案与理由 / 不决策的后果 / 决策截止时间
```

三段的完整写作要求与填好的示例见 `references/writing-patterns.md`（**Step 4 必读**）。

### Step 5：按受众裁剪

**同一份底层事实，四种裁剪。** 不是写四份报告，是从事实底稿里挑不同的行、用不同的粒度。

| 受众 | 关心什么 | 长度上限 | 必含 | 必不含 |
|---|---|---|---|---|
| **直接上级** | 细节 + 阻塞 + 需要的资源 | 2 页 | 逐项交代上期计划、全部风险五要素、资源请求 | 任务级流水账 |
| **跨团队** | 依赖与接口 + 时间点 + 影响他们的变更 | 1 页 | 接口/契约变更清单、需要他们配合的时间点、会影响他们的行为变化 | 内部实现细节、内部人事 |
| **高管** | 一页内看完能拍板 | **1 页（≤ 40 行）** | 目标达成度、三个关键数字、一个最大风险、一个待决策项 | 超过 3 个的任何列表 |
| **团队内部** | 任务粒度 + 认领 + 下期计划 | 不限但表格化 | 每个任务的负责人与下期动作、待认领项 | 对上级的措辞修饰 |

四个版本的字段级对照表与裁剪规则见 `references/audience-tailoring.md`（**Step 5 必读**）。

### Step 6：格式纪律自检 + 落盘

| 纪律 | 具体阈值 |
|---|---|
| 长度上限 | 高管版 ≤ 40 行；上级版 ≤ 120 行；跨团队版 ≤ 60 行 |
| 表格优先 | 3 条以上的并列信息一律用表格，不用段落 |
| 绝对日期 | 全篇禁用「上周」「近期」「尽快」「最近」；一律写 `2026-10-11` 或 `W41` |
| 形容词 | 禁用「显著」「大幅」「基本」「顺利」「持续」修饰成果；换成数值 |
| 术语 | 首次出现给一句定义，或用附录术语表 |
| 数字口径 | 每个数字后跟口径，或统一在附录列口径表 |
| 无 blame | 写事不写人；「{项} 连续两期未推进」而非「{某人} 没做」 |

周期与节奏（周报/双周报/月报各自放什么粒度）、跨期一致性规则、以及「上期计划必须在本期交代」为什么重要，见 `references/cadence-and-format.md`。

**落盘**：`docs/analysis/STATUS-{团队或项目}-{周期}.md`。四受众版本写在同一文件的四个小节里（共享一份事实底稿附录），除非受众之间需要保密隔离——那种情况拆成多个文件并在主文件里注明。

**落盘前自检**：

```
[ ] 三个铁律逐条过：坏消息在前 1/3 / 每个数字有口径 / 每段能被行动
[ ] 上期计划逐项交代，含「未完成」及原因（无上期基线则已显式声明）
[ ] 每条风险五要素齐全，按严重度排序
[ ] 每个决策项五要素齐全（背景/方案+代价/建议+理由/不决策后果/截止时间）
[ ] 没有「暂无风险」「请领导指示」「详见后续」
[ ] 每个数字能追到事实底稿里的一条命令或查询
[ ] 全篇无「上周/近期/尽快」，全部绝对日期
[ ] 口径与上期一致；若有变更已显式声明并给新旧换算
[ ] 无真实姓名（用角色）、无 blame 表述、无内部域名、无凭据
[ ] 高管版 ≤ 40 行且能独立成篇
[ ] 文件落在 docs/analysis/，不在仓库根目录
```

## Key Principles

1. **报告的唯一目的是让读者做决策。** 每段都要能回答「读者看完能做什么」，答不出就删。
2. **坏消息必须和好消息同样显眼。** 风险与阻塞放前 1/3，与进展同层级；藏在第 8 段的报告是失职。
3. **每个数字追到一条命令或一个查询。** 凭印象写出的数字在下期无法对比，等于没有。
4. **口径稳定优先于口径好看。** 换指标会让报告失去纵向可比性，等于每期都在重新开始；必须换时显式声明并给换算。
5. **进展是状态迁移，不是活动量。** 「X 从 A 到 B，剩余 C」；提交数、会议数、评审数不是成果。
6. **没有风险通常不是好消息。** 「暂无」之前必须过一遍五个信号源；连续两期「暂无」是审计信号。
7. **决策项必须带选项。** 只抛问题不给 2–3 个方案及代价，等于把分析工作推给读者；替读者做决定同样错。
8. **同一份事实，四种裁剪。** 高管一页内、跨团队只看接口与时间点、上级看细节与资源、团队内部看任务与认领。

## Anti-Patterns

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| **报喜不报忧** | 读者基于残缺信息做决策，风险在下一期变成事故；一旦发现，之后所有报告都会被折扣阅读 | 风险与阻塞放前 1/3，与进展同层级、同字号；坏消息写在第一屏 |
| **用工作量冒充成果**（列了 187 个提交、12 场会议） | 活动量无法推断进展；读者只能得出「很忙」，做不了任何决策 | 写状态迁移：「X 从 A 到 B，剩余 C」；活动量数据只放事实底稿附录 |
| **指标口径漂移**（上期算任务数，本期算人日） | 报告失去纵向可比性，等于每期从零开始；且看起来像刻意美化 | 口径写进附录并沿用上期；必须变更时显式声明「本期口径由 X 改为 Y，按新口径上期为 Z」 |
| **风险写成「暂无」** | 五个信号源（依赖方沉默/连续两期未推进/单人关键路径/无测试的高频改动区/临期低完成度）任一个查过都不会是「暂无」 | 逐信号源过一遍；确实没有则写「已查 5 个信号源，本期无新增；持续观察 {项}」 |
| **决策项写成「请领导指示」却不给选项** | 把分析工作推给读者；读者没有你手上的信息，给不出比你更好的判断 | 给 2–3 个方案 + 各自代价 + 建议与理由 + 不决策的后果 + 截止时间 |
| **替读者做决定**（「已按方案 A 执行」写在决策项里） | 决策项一旦被当成通知，读者失去了在代价可见时改变方向的机会 | 未决策前写「建议 A，理由 …，若 2026-10-18 前无异议将按 A 执行」；已决策的移到进展段 |
| **把上期内容复制粘贴改日期** | 「上期计划本期交代」失效，计划退化成许愿；读者会对比，一旦发现信任崩塌 | 从上期文件读计划清单，逐项写本期状态（完成/部分/未动 + 原因） |
| **用百分比掩盖没做完**（「完成 90%」） | 百分比不可验证，分母不明；90% 常年停在 90% | 用可验证里程碑：「12 个任务中 8 个已合并、2 个在评审、2 个未开始」；必须用百分比时写明分母 |
| **只讲自己模块不讲依赖方影响** | 跨团队读者找不到与自己相关的部分；接口变更未被识别会直接引发线上事故 | 单列「影响其他团队的变更」小节：契约/接口/行为/时间点的变化 |
| **时间用「上周」「近期」「尽快」** | 报告被转发或归档后无法定位；跨期对比时无法对齐 | 一律绝对日期 `2026-10-11` 或周标识 `W41`；截止用具体日期 |
| **形容词堆叠**（「显著提升了系统稳定性，大幅优化了用户体验」） | 不可验证，会被要求补正，且稀释真正重要的信息 | 换成数值 + 口径：「P99 从 820ms 降至 210ms，同一压测脚本，预发环境」 |
| **一份报告发四类受众** | 高管看不完、跨团队找不到相关部分、团队内部拿不到任务粒度 | 同一事实底稿裁剪四版；高管版 ≤ 40 行且能独立成篇 |
| **写人名与归责**（「X 没交付导致延期」） | 报告会被防御性阅读，下期起所有人只报好消息 | 写事不写人：「{交付项} 未在 {日期} 前完成，当前状态 {S}，需要 {支持}」 |

## 反合理化速查

| 你会想说的话 | 实际情况 |
|---|---|
| 「这期没什么进展，写短点」 | 没进展本身就是最重要的信息，要写清卡在哪一步、卡在谁那里、需要什么才能动 |
| 「风险还没确认，先不写」 | 未确认的风险正是要上报以求资源确认的；确认完再报通常已是事故报告 |
| 「数字不好看，换个指标」 | 口径漂移让报告失去纵向可比性，等于每期都在重新开始 |
| 「列提交数能体现工作量」 | 提交数是活动量不是成果，读者从中推断不出任何决策 |
| 「风险写『暂无』比较稳妥」 | 「暂无」不是结论是失职；先过五个信号源 |
| 「决策项写『请领导指示』最安全」 | 不给选项等于把分析推给读者；必须给方案、代价、建议、后果、截止时间 |
| 「四份太累，发同一份」 | 同一事实四种裁剪；发同一份等于四类受众都没被服务到 |
