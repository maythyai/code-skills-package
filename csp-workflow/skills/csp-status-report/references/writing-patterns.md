# 进展事实化与三段式骨架

**读这份文件的时机**：Step 2（改写进展）与 Step 4（组装三段式）。

## 一、进展的事实化写法

核心公式：

> **「X 从 A 状态到 B 状态，剩余 C」**

三段缺一不可：

| 成分 | 作用 | 缺失时的问题 |
|---|---|---|
| **A 状态**（起点） | 让读者知道起点在哪，判断这段位移有多大 | 只写 B 会让「已上线灰度 10%」听起来像完成，实际起点是「未开始」 |
| **B 状态**（当前） | 可验证的当前事实 | 只写「推进了」读者无法判断进度 |
| **剩余 C** | 让读者能估算还要多久、是否需要加资源 | 缺 C 就无法判断风险，也无法做决策 |

**状态必须可验证**：用系统里能查到的状态（已合并主干 / 已上预发 / 灰度 10% / 接口联调 4/7 通过 / 评审第 2 轮），不用主观描述（基本完成 / 差不多 / 收尾中）。

## 二、弱写法 vs 强写法对照表（14 组）

主干 Step 2 已给 4 组示例（优化了性能 / 推进了重构 / 跟进了对接 / 完成了大部分开发），此处不重复；下表是另外 **14 组**高频空话，按所在段落分四类。

**改写完成判据**：强写法里必须至少含 **数字 / 绝对日期 / 责任人角色 / 阻塞点** 中的一项。四项全无 = 这句还没改完，不许进报告。

### 2.1 进展类（4 组）

| # | 弱写法原句 | 为什么弱（缺什么信息） | 强写法改写 | 强在哪 |
|---|---|---|---|---|
| 1 | 本期进展顺利 | 无分母、无状态分布；「顺利」是主观形容，读者判断不了要不要介入 | 本期计划 12 项：8 项已合并主干、2 项在评审第 1 轮、2 项未开始（依赖 R1）；相对 W40 排期落后 1 个工作日，可在 W42 追回 | 有分母与状态分布 → 读者能自己算完成度；有偏差量与追平路径 → 能判断是否需要介入 |

| 3 | 修复了一些线上问题 | 无数量、无分级、无复发情况 | 修复 P2 缺陷 3 个（编号 `[TBD]`）、P3 缺陷 5 个；其中 1 个为回归缺陷，根因是无自动化测试覆盖（见风险 R4） | 数量 + 分级 + 根因，读者能判断质量趋势而不是「有在修」 |
| 4 | 上线了新功能 | 上线到什么范围？效果？下一步等什么？ | 功能 A 于 2026-10-09 发布 v1.4.0，灰度 5% 用户；灰度组错误率 0.02%（对照组 0.03%），核心转化率变化在置信区间内，暂不扩量 | 范围 + 对照组 + 「暂不扩量」的决策，读者知道当前在等什么条件 |

### 2.4 质量与下一步类（3 组）

| # | 弱写法原句 | 为什么弱（缺什么信息） | 强写法改写 | 强在哪 |
|---|---|---|---|---|
| 12 | 加强了测试 | 加强多少？范围？口径？ | 核心支付链路自动化用例从 42 增至 68，行覆盖率 51% → 63%（口径：`services/checkout` 目录，行覆盖，不含生成代码） | 分子分母与扫描范围齐全，「加强」可被第三方复算 |
| 13 | 代码质量有所提升 | 无指标；且读者会怀疑是换了工具 | 静态检查告警从 214 降至 89（同一规则集、同一扫描范围）；重复代码率 6.2% → 4.1% | 显式声明「同一规则集、同一范围」→ 环比有效，排除口径漂移的怀疑 |
| 14 | 下期继续推进 | 推进什么？到什么状态？谁负责？ | 下期目标（可验证）：① 灰度提至 50% 且错误率 ≤ 0.05%，负责角色 {后端负责人}，目标 2026-10-18；② 剩余 3 个接口在 mock 环境验证通过；③ `services/checkout/pricing` 行覆盖 ≥ 20% | 三条各有可验证判据 + 角色 + 日期 → 下期能逐条交代，计划不会退化成许愿 |

**改写练习法**：写完每一行，问三个问题——

1. 有没有数字？没有 → 能不能加？不能加 → 这行是不是根本不该出现在报告里？
2. 数字有没有口径？（时间窗、分子分母、测量环境、扫描范围）
3. 读者看完能做什么？（批准 / 派资源 / 解除阻塞 / 知情后无需动作）

## 三、完成度：用里程碑，不用百分比

**默认规则：完成度用可验证的里程碑表达，不用百分比。**

| 不要写 | 要写 |
|---|---|
| 完成 70% | 12 个任务中：8 个已合并主干、2 个在评审、2 个未开始 |
| 进度 85% | 5 个里程碑中：M1–M3 已达成（各有验收证据），M4 部分达成（3/5 子项），M5 未开始 |
| 重构完成度 60% | 重构 4 个阶段中，阶段 1–2 已完成并全量生效，阶段 3 已合并未切流，阶段 4 未开始 |

**为什么**：百分比的分母从来不明说。同一个「70%」可以是「7/10 个任务」也可以是「按人日估算的 70%」，两者的下期预测完全不同。而「90%」长期停在 90% 是软件项目最经典的现象——最后 10% 里藏着全部风险。

**如果一定要用百分比**（例如高管版需要一个单一数字），必须紧跟分母定义：

```
本期计划完成率 67%（分母 = 本期计划任务数 12，不含期内插入的 3 个紧急项；
分子 = 状态到达「已合并主干」的任务数 8。上期同口径为 91%）
```

三要素：分子定义、分母定义、上期同口径值。缺一个就是口径漂移的开端。

### 3.1 里程碑式完成度的三件套

写「完成度」时，三样必须同时出现，缺一样读者就得追问：

| 件 | 写什么 | 缺了会怎样 | 反面写法 |
|---|---|---|---|
| **① 已交付的可验证事实清单** | 每项带证据类型：合并记录 / 版本号 / 灰度比例 / 验收日期 / 指标数值 | 读者无法判断「已完成的」是否真完成 | 「大部分已完成」 |
| **② 剩余工作清单** | 每项带完成判据 + 负责角色 + 目标日期 | 读者无法估算还要多久、要不要加资源 | 「还剩一点收尾工作」 |
| **③ 完成日期的置信区间** | 三点估算（最早 / 最可能 / 最晚）+ 置信档 + 决定宽度的未知项 | 读者把「最可能」当成承诺，一旦滑期就是信任损失 | 「预计月底完成」 |

**置信档的判据**（跨期不变，写进附录口径表）：

| 档 | 判据（全部满足才够这一档） |
|---|---|
| **高** | 剩余项全部有负责角色与可验证判据；无外部依赖；按历史速率缓冲 ≥ 20% |
| **中** | 存在 1 个外部依赖（已升级且对方给了承诺日），或 1 项判据未定；缓冲 < 20% |
| **低** | ≥ 2 个外部依赖且无承诺日；或关键路径上有单人项（信号源 3）；或缓冲为负 |

**三点估算的写法**：

```
完成日期：最早 2026-10-24 / 最可能 2026-10-31 / 最晚 2026-11-07
置信档：中（依赖 R1，对方证书承诺日 2026-10-16）
最晚情形对应：R1 未在 2026-10-16 解除 → 联调窗口关闭，改走 D1 方案 A（+3 人日返工）
```

**区间宽度本身就是信息。** 最晚 − 最早 > 10 个工作日 → 说明估算依据不足，此时应在报告里写清「哪个未知项决定了这个宽度」，并把它列为决策项或风险，**不要通过收窄区间来显得确定**。

### 3.2 填好的示例

```markdown
**M4 定价链路迁移完成度（截至 2026-10-11）**

① 已交付（可验证）
- 双写全量生效：v2.13.0，2026-09-28 起，一致性校验 0 告警持续 13 天
- 灰度切流 10%：v2.14.0，2026-10-06 起，切流链路错误率 0.02%
- 读路径切换方案：2026-10-09 评审通过（评审记录 {路径}）

② 剩余工作
| 项 | 完成判据（可验证） | 负责角色 | 目标日期 |
|---|---|---|---|
| 灰度提至 50% | 50% 流量 + 一致性校验 0 告警持续 48h | 后端负责人角色 | 2026-10-18 |
| 全量切流 | 100% 流量 + 错误率 ≤ 0.05% 持续 24h | 后端负责人角色 | 2026-10-24 |
| 老表下线 | 只读观察 7 天后删除，回滚窗口关闭 | 后端负责人角色 + DBA 角色 | 2026-11-07 |

③ 完成日期：最早 2026-10-31 / 最可能 2026-11-07 / 最晚 2026-11-21
置信档：中。决定宽度的两个未知项：R2（灰度回退的校验修复，承诺 2026-10-15）、
DBA 角色的下线排期（尚无承诺日）。
```

这段里每一个状态都能被第三方复查——这就是不写「M4 完成 60%」的全部理由。

## 四、三段式骨架

顺序固定：**① 进展 → ② 风险与阻塞 → ③ 需要决策的事项**。

> **注意顺序的理由**：铁律①要求坏消息与好消息同样显眼。把风险放第二段（而不是文末）意味着它在第一屏或第二屏就能被看到。第三段是整份报告最有价值的部分——它决定读者要不要动手。

### 第 ① 段：进展

**写作要求**：

1. **对齐上期计划逐项交代。** 从上期报告读出计划清单，逐条写本期状态。**含「未完成」及原因**——未完成项不是脏数据，是本期最有信息量的部分。
2. 每条用「A → B，剩余 C」公式。
3. 关键指标变化用表格：指标 / 上期 / 本期 / 变化 / 口径。
4. 本期新增（计划外）的插入工作单列一行，说明来源与挤占了什么。
5. 不写活动量（提交数、会议数、评审数）——那些进事实底稿附录。

**填好的示例**：

```markdown
## 1. 进展（2026-10-05 ~ 2026-10-11，W41）

### 1.1 上期计划逐项交代

| # | 上期计划（W40 报告 §3） | 目标状态 | 本期实际状态 | 判定 | 原因 / 剩余 |
|---|---|---|---|---|---|
| P1 | checkout P99 降至 300ms 以下 | 预发验证通过 | 预发验证通过，P99 = 210ms | ✅ 完成 | 剩余：生产灰度（已排入 W42） |
| P2 | 订单模块双写切流至 50% | 灰度 50% | 灰度 10%，错误率 0.02% | ⚠️ 部分完成 | 切流脚本在 2026-10-08 触发一次数据不一致告警，已回退至 10% 并加校验；剩余：修复校验逻辑（W42 目标 30%） |
| P3 | 结算系统 7 个接口联调通过 | 7/7 | 4/7 | ❌ 未完成 | 3 个接口阻塞在对方环境证书过期，已提请求 6 个工作日无回复 → 见风险 R1 |
| P4 | pricing 目录补自动化测试至行覆盖 50% | 50% | 未开始 | ❌ 未开始 | 期内插入 2 个 P2 线上缺陷修复，占 3 人日 → 顺延至 W42，但见风险 R4（该目录本期改动 28 次仍无测试） |

### 1.2 本期计划外插入工作

| 项 | 来源 | 占用 | 挤占了 |
|---|---|---|---|
| 支付回调超时缺陷（P2） | 2026-10-07 线上告警 | 2 人日 | P4 |
| 对账文件格式变更适配 | 结算系统单方通知（2026-10-06） | 1 人日 | P4 |

### 1.3 关键指标变化

| 指标 | W40 | W41 | 变化 | 口径 |
|---|---|---|---|---|
| checkout P99 | 820ms | 210ms | −74% | 全接口聚合，含冷启动，预发环境 |
| 5xx 错误率 | 0.31% | 0.04% | −87% | 仅网关侧 5xx，不含业务错误码 |
| 计划完成率 | 91%（10/11） | 25%（1/4） | −66pt | 分母 = 本期计划任务数，不含插入项 |
| 主干人工变更数 | 28 | 34 | +21% | `--no-merges --first-parent`，排除 bot |
| 打开超 5 日的 MR | 2 | 4 | +2 | 创建日早于周期起始且仍 opened |

> **口径变更声明**：本期无口径变更。计划完成率的分母沿用 W38 起的定义（本期计划任务数，不含插入项）。
```

### 第 ② 段：风险与阻塞

**写作要求**：

1. **按严重度排序**：阻塞当前周期 > 阻塞下个周期 > 影响质量 > 影响效率。
2. 每条必须有**五要素**，缺一条不算写完：

| 要素 | 内容要求 | 反面例子 |
|---|---|---|
| **风险描述** | 客观事实 + 状态，不含 blame | 「结算团队不配合」（blame）→「结算系统接口联调请求已发出 6 个工作日无回复」 |
| **触发条件** | 什么情况下这个风险会变成问题（可观测的信号） | 「可能会有问题」→「若 2026-10-16 前未获证书更新，联调无法进行」 |
| **影响** | 影响到哪个交付项、哪个日期、多大量级 | 「影响进度」→「P3 无法完成，导致 2026-11-15 交付里程碑的联调窗口整体后移 5 个工作日」 |
| **当前应对** | 已经在做什么（不是打算做什么） | 「会持续跟进」→「已于 2026-10-09 通过 IM 与邮件双通道升级至对方负责人；已准备本地 mock 环境以并行推进 3 个接口的功能验证」 |
| **需要什么支持** | 具体到人/角色 + 具体动作 + 具体日期 | 「请领导协调」→「需上级在 2026-10-14 前与对方团队负责人确认证书更新时间；若无法确认，需批准启用 mock 方案（见决策项 D1）」 |

3. 严重度用固定标签：`[阻塞-本期]` `[阻塞-下期]` `[质量]` `[效率]`。
4. 每条风险编号（R1、R2…）**跨期沿用**——同一风险下期继续用同一编号，便于追踪。新增的用新号，已关闭的移到「本期关闭的风险」。

**填好的示例**：

```markdown
## 2. 风险与阻塞（按严重度排序）

### R1 `[阻塞-本期]` 结算系统接口联调停滞

- **风险描述**：3 个接口的联调请求于 2026-10-03 发出，截至 2026-10-11 已 6 个工作日无回复；对方环境证书于 2026-10-05 过期。
```

### 第 ③ 段：需要决策的事项

**这是报告最有价值的部分。** 每个决策项五要素：

```
背景一句 / 可选方案 2–3 个及各自代价 / 建议方案与理由 / 不决策的后果 / 决策截止时间
```

两条禁令：

- **不要只抛问题不给选项。** 「请领导指示」等于把分析工作推给读者——读者没有你手上的信息，给不出比你更好的判断。
- **不要替读者做决定。** 已经自己拍板并执行的事，属于进展段，不属于决策段。若确需先行，写成「建议 A；若 {日期} 前无异议将按 A 执行」，把否决窗口显式给出。

**方案对比要写代价，不只写好处。** 每个方案至少一条代价（成本、时间、风险、不可逆性）。没有代价的方案不是方案，是推销。


## 五、三段之间的引用完整性检查

```
[ ] 进展段的每个「未完成」项，都在风险段有对应条目或有明确原因说明
[ ] 风险段的每条「需要什么支持」，若需要上级动作，都在决策段有对应决策项
[ ] 决策段的每条都标注了关联的风险编号（R_n）或计划项编号（P_n）
[ ] 上期决策段的每条，本期都有归属：已决策（移入进展段的「已决策事项」表）/ 仍待决策（说明为什么又拖了一期）/ 已失效（说明原因）
[ ] 风险编号跨期沿用，已关闭的移入「本期关闭的风险」表
```

**最后一条最容易被忽略，也最致命**：一个决策项连续三期出现在报告里而没有进展，本身就是需要上报的元风险——「D2 已连续 3 期未决策，当前默认落在方案 B，累计影响 ……」。
