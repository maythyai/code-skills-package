# 按受众裁剪：同一份事实，四种版本

**读这份文件的时机**：Step 5。前提是 Step 1 的事实底稿与 Step 4 的三段式母版已经写完。

## 零、原则

**不是写四份报告，是从一份事实底稿里挑不同的行、用不同的粒度渲染四次。**

```
事实底稿（附录，全量数据 + 口径 + 来源命令）
        │
        ├─► 母版：三段式完整版（进展 / 风险 / 决策）
        │
        ├─► 版本 A：直接上级     ← 母版几乎全量 + 资源请求
        ├─► 版本 B：跨团队       ← 只取「与我有关」的行 + 接口/时间点
        ├─► 版本 C：高管         ← 4 个格子，≤ 40 行
        └─► 版本 D：团队内部     ← 任务粒度 + 认领 + 下期计划
```

**四条硬规则**：

1. **数字必须完全一致。** 四个版本里同一指标必须是同一个数、同一个口径。不一致一旦被读者发现（他们会对账），四份报告同时失去可信度。
2. **坏消息在每个版本里都在前 1/3。** 高管版尤其——不能因为篇幅短就把风险挤掉。风险挤掉的高管版是四个版本里最有害的一个。
3. **不因为受众而改变事实的性质。** 不能对内部说「阻塞」、对高管说「存在少量不确定性」。措辞可以简化，判断不能软化。
4. **每个版本都能独立成篇。** 不写「详见另一份」——读者不会去点开。

## 一、四版本字段级对照表

| 内容块 | A 直接上级 | B 跨团队 | C 高管 | D 团队内部 |
|---|---|---|---|---|
| 周期与范围声明 | ✅ 一行 | ✅ 一行 | ✅ 一行 | ✅ 一行 |
| 目标达成度（对季度/项目目标） | ✅ | ➖ 仅当影响他们 | ✅ **必含** | ✅ |
| 上期计划逐项交代（P1…Pn 表） | ✅ **全表** | ➖ 只列与他们相关的项 | ➖ 合并成一句 | ✅ **全表 + 任务级** |
| 计划外插入工作 | ✅ | ➖ | ➖ | ✅（用于解释排期挤压） |
| 关键指标变化表 | ✅ 5–8 行 | ➖ 只给影响他们的指标 | ✅ **恰好 3 个数字** | ✅ 可给更多技术细节 |
| 风险与阻塞（五要素） | ✅ **全部条目，五要素齐全** | ⚠️ 只列「需要他们动作」或「会影响他们」的，仍需五要素 | ✅ **恰好 1 个最大风险**，三句话讲完 | ✅ 全部条目 + 责任人角色 |
| 需要决策的事项 | ✅ 全部 + 建议 + 截止 | ⚠️ 只列需要他们参与决策的 | ✅ **恰好 1 个待决策项** + 建议 + 截止 | ⚠️ 只列团队内部可决定的 |
| 资源请求（人/预算/时间） | ✅ **必含，具体到数量与日期** | ➖ | ➖（隐含在决策项的代价里） | ➖ |
| 影响其他团队的变更（接口/契约/行为/时间点） | ➖ | ✅ **必含，这是 B 版的核心** | ➖ | ✅ |
| 需要对方配合的时间点 | ➖ | ✅ **必含，具体日期** | ➖ | ✅ |
| 任务粒度清单 + 认领 | ➖ | ➖ | ➖ | ✅ **必含** |
| 待认领项 | ➖ | ➖ | ➖ | ✅ **必含** |
| 下期计划（可验证目标） | ✅ | ⚠️ 只列影响他们的 | ➖ | ✅ **必含，任务级** |
| 事实底稿附录（命令 + 口径） | ✅ 折叠附上 | ➖ | ❌ **绝不附** | ✅ |
| 技术实现细节 | ⚠️ 仅当上级是技术背景 | ❌ | ❌ | ✅ |
| 内部人事/绩效相关信息 | ⚠️ 视组织规则 | ❌ | ❌ | ⚠️ 只写角色不写评价 |

图例：✅ 必含　⚠️ 条件包含　➖ 通常省略　❌ 禁止

## 二、长度上限与结构

| 版本 | 长度上限 | 结构 |
|---|---|---|
| **A 直接上级** | ≤ 120 行 | 三段式母版全量 + 资源请求段 + 附录（事实底稿） |
| **B 跨团队** | ≤ 60 行 | ① 影响你们的变更（表）② 需要你们配合的时间点（表）③ 我们的相关进展与风险（各 ≤ 5 行）④ 联系人角色 |
| **C 高管** | **≤ 40 行，一页内** | 固定四格：目标达成度 / 三个关键数字 / 一个最大风险 / 一个待决策项 |
| **D 团队内部** | 不限长度但**全表格化** | ① 上期计划逐项 ② 本期任务清单（含认领）③ 待认领 ④ 风险与责任人角色 ⑤ 下期计划 |

## 三、裁剪规则：从母版到高管版

**方向是单向的**：母版（A 直接上级版，三段式全量 + 事实底稿）→ B / C / D。**禁止反向扩写**（拿高管版补出上级版）——反向扩写会补出母版里不存在的细节，四版数字随即无法对账。

D 版不是「删」出来的，是**换粒度**：同一批事实下沉到任务级（`T-{nnn}`），并补上认领人与可验证判据。

### 3.1 删除顺序（A → C，8 步；每步做完数一次行数）

| 步 | 删什么 | 为什么可以删 | C 版留下的对应格 |
|---|---|---|---|
| 1 | 事实底稿附录、口径登记表、术语表、`[TBD]` 汇总 | 高管不复查过程；留一行指向完整版即可 | 脚注 1 行 |
| 2 | 任务级清单、待认领、内部技术指标（D 版全部内容） | 与「要不要拍板」无关 | — |
| 3 | 计划外插入工作表 | 它的作用是向上级解释排期挤压 | — |
| 4 | 上期计划逐项交代表 → 压成一句「{N} 项：{a} 完成 / {b} 部分 / {c} 未完成」 | 明细在 A 版；高管只要偏差量 | 摘要 1 行 |
| 5 | 风险条目只留 1 条：选「不决策就会自动变坏」的那条，其余删 | 多条同等严重时，取不可逆性最高的一条 | C.3 |
| 6 | 决策项只留 1 项：选截止时间最早的，其余删 | 一次只拍一个；其余留在 A 版或单独沟通 | C.4 |
| 7 | 关键指标从 5–8 个压到**恰好 3 个**（结果 / 质量 / 进度各 1） | 超过 3 个既记不住也无法横向比较 | C.2 |
| 8 | 进展段的解释性文字、技术背景、推导过程 | 只留状态与数值 | C.1 |

**删到第 8 步仍超 40 行**：继续删 C.1 的里程碑计数细节与解释句；**不许动 C.3 与 C.4**。

### 3.2 红线：任何版本都绝对不能删

| 红线 | 为什么 |
|---|---|
| **需要对方决策的事项**（方案 + 代价 + 建议 + 截止时间） | 这是报告存在的理由。删掉后报告退化成通知，读者失去在代价可见时改变方向的唯一机会 |
| **`[阻塞-本期]` 风险**（最短也要留一句：事实 + 触发日期 + 影响） | 铁律①。被裁掉的风险在下期变成事故；一旦发现漏报，此后所有报告都被折扣阅读 |
| **上期承诺未兑现的事实**（可压成一句，不可消失） | 「上期计划本期交代」一旦在某个版本失效，计划就退化成许愿 |
| **数字的口径**（可移入脚注或附录，不可省略） | 无口径的数字下期无法对比，等于没有 |
| **决策截止时间** | 没有截止时间的决策项会被无限期搁置，等于没写 |

**推论**：C 版最短可以到 12 行（状态灯 + 3 个数字 + 1 个风险 + 1 个决策项 + 截止 + 脚注），但不能再少。

### 3.3 需要保密隔离时拆文件

命中任一判据即拆：① 某受众不得看到另一受众的信息（外包/人力成本、未公开的范围裁剪）；② 跨团队版含尚未正式通知的契约变更；③ 组织规则禁止内部任务清单外发。

拆法：主文件仍为 `docs/analysis/STATUS-{团队或项目}-{周期}.md`，各受众拆为同名 + 后缀 `-{受众}.md`（`-exec` / `-cross-team` / `-internal`）；主文件首屏用 ≤ 8 行列出「包含哪几版、各自路径、事实底稿在哪一份」。**事实底稿只存一份**（放上级版），其余版本用一行指向它——多份底稿是口径漂移的头号来源。

## 四、各版本写法要点

### 版本 A：直接上级

上级要的是**能介入**。所以：

- **细节要给够**，但不要给技术实现的推导过程。给「什么状态、什么数值、什么口径」，不给「怎么算出来的」（那在附录）。
- **阻塞要给到可动作的粒度**：不要「需要协调」，要「需要你在 2026-10-14 前与对方团队负责人确认 X」。
- **资源请求要具体到数量与日期**：「W42 需要 3 人日用于补测试，若不批则 P4 顺延至 W44」。
- **给上级一个『他可以什么都不做』的默认路径**：每个决策项都写「不决策的后果」，让他知道沉默意味着什么。沉默的代价可见，才会不沉默。

**开头三行模板**（上级通常在 30 秒内决定读不读下去）：

```markdown
**W41 摘要（2026-10-05 ~ 2026-10-11）**
状态：🟡 有阻塞（1 项本期阻塞，需你在 2026-10-14 前决策 D1）
上期计划 4 项：1 完成 / 1 部分 / 2 未完成（原因见 §1.1）
```

状态灯只用三档且有明确定义（写进附录，跨期不变）：

| 灯 | 定义 |
|---|---|
| 🟢 | 上期计划 ≥ 80% 完成，且无 `[阻塞-本期]` 风险 |
| 🟡 | 上期计划 50%–80% 完成，或存在 `[阻塞-本期]` 风险但有应对方案 |
| 🔴 | 上期计划 < 50% 完成，或存在 `[阻塞-本期]` 风险且无可行应对，或里程碑已确定延误 |

**灯的定义必须固定。** 每期凭感觉给灯是另一种口径漂移——读者会学会忽略它。

### 版本 B：跨团队

跨团队读者只关心三件事：**你们改了什么会影响我 / 你们需要我在什么时候做什么 / 你们会不会拖累我**。

**结构**：

```markdown
## 跨团队同步：{项目名} W41（2026-10-05 ~ 2026-10-11）

### 1. 影响你们的变更
| 变更 | 类型 | 生效时间 | 影响范围 | 需要你们做什么 |
|---|---|---|---|---|
| 对账文件新增 `settlement_batch_id` 字段 | 契约变更（向后兼容） | 2026-10-20 | 所有消费对账文件的下游 | 无需改动；若做严格 schema 校验需加白名单 |
| checkout 接口 `/v2/orders` 的 P99 SLA 从 800ms 调整为 300ms | 行为变更 | 2026-10-18（灰度） | 依赖该接口超时配置的调用方 | 检查你们的超时设置是否 > 300ms 且 < 800ms |

### 2. 需要你们配合的时间点
| 事项 | 需要谁（角色） | 需要做什么 | 截止 | 逾期后果 |
|---|---|---|---|---|
| 结算系统测试环境证书更新 | 对方运维负责人角色 | 更新证书并通知 | 2026-10-16 | 3 个接口联调窗口关闭，11-15 里程碑后移约 5 个工作日 |

### 3. 我们的相关进展与风险（仅与你们有关的部分）
- 接口联调：7 个中 4 个通过，3 个阻塞（见上表）
- 灰度计划：checkout 优化于 2026-10-18 灰度 10%，若你们在该时段有压测计划请告知，避免互相干扰

### 4. 联系人
| 事项 | 联系角色 |
|---|---|
| 对账文件格式 | 后端负责人角色 |
| 联调排期 | 项目经理角色 |
```

**B 版禁令**：不写内部人事、不写内部排期争议、不写「我们团队很忙」、不写与对方无关的技术细节。

### 版本 C：高管（一页内，≤ 40 行）

**固定四格，不多不少。** 任何第五格都是噪声。

```markdown
# {项目名} 状态 — W41（2026-10-05 ~ 2026-10-11）

**总体：🟡 有阻塞，需一项决策**

## 1. 目标达成度
2026-11-15 交付里程碑：**风险中**。5 个里程碑已达成 3 个；按当前速率剩余 2 个需 21 个工作日，
可用 24 个工作日，缓冲 3 天（上期缓冲 8 天）。

## 2. 三个关键数字
| 指标 | 上期 | 本期 | 口径 |
|---|---|---|---|
| checkout P99 | 820ms | 210ms | 全接口聚合，预发环境 |
| 5xx 错误率 | 0.31% | 0.04% | 网关侧 5xx |
| 计划完成率 | 91% | 25%（1/4） | 分母 = 本期计划任务数 |

## 3. 一个最大风险
结算系统 3 个接口联调停滞 6 个工作日（对方环境证书过期，请求无回复）。
若 2026-10-16 前未解决，11-15 里程碑后移约 5 个工作日，缓冲归零。
已搭建本地 mock 可并行推进功能验证。

## 4. 一个待决策项
**是否启用 mock 方案保里程碑**（代价：约 3 人日返工 + 上线后 2 周存在未验证的端到端路径）。
备选：等待对方恢复（里程碑顺延 5–10 个工作日，影响 11-20 市场活动）或缩减范围（需产品同意裁剪）。
**建议：启用 mock。** 不决策则默认停在「等待」，里程碑在无人授权的情况下顺延。
**决策截止：2026-10-14 18:00**
```

**高管版规则**：

- **恰好 3 个数字**，不是 5 个也不是 10 个。选标准：① 与业务目标直接相关的结果指标 ② 质量/稳定性指标 ③ 进度指标。三者各一个。
- **恰好 1 个风险 + 1 个决策项。** 有 3 个同等严重的风险时，选「不决策就会自动变坏」的那个，其余留在 A 版。
- **决策项必须给建议。** 高管版里出现「请指示」是这四个版本中最严重的失败——高管的时间成本最高，把分析工作推给他的代价最大。
- **不附事实底稿。** 但要在文末一行写「数据来源与口径见完整版 §附录」（给想追查的人一条路径，不占正文）。
- **40 行是硬上限。** 超了就删第 1 格的解释性文字，不删第 3、4 格。

**可直接复制的一页模板（占位符版）**。行数预算：标题+状态灯 4 / C.1 6 / C.2 8 / C.3 8 / C.4 10 / 脚注 2 = **38 行**，留 2 行余量。

```markdown
# {项目名} 状态 — {周期标识}（{YYYY-MM-DD} ~ {YYYY-MM-DD}）

**总体：{🟢/🟡/🔴} {一句话结论：需一项决策 / 需知情无需动作 / 已确定延误}**

## 1. 目标达成度
{里程碑名}（{交付日期}）：**{正常 / 风险中 / 已延误}**。
{M} 个里程碑已达成 {m} 个；剩余需 {K} 个工作日，可用 {J} 个工作日，
缓冲 {J-K} 天（上期 {X} 天）。{缓冲 ≤ 0 时补一句：缓冲已耗尽，见 §4}

## 2. 三个关键数字
| 指标 | 上期 | 本期 | 口径 |
|---|---|---|---|
| {结果指标：与业务目标直接相关} | {值} | {值} | {分子 / 分母 / 时间窗} |
| {质量或稳定性指标} | {值} | {值} | {口径} |
| {进度指标} | {值} | {值} | {分母定义} |

## 3. 一个最大风险
{事实：什么停滞或恶化了多久，含绝对日期}。
{触发条件：若 {日期} 前未 {动作}，则 {可观测后果}}。
{影响量级：影响哪个交付项、哪个日期、多大范围}。
{已做的应对：含执行日期}。

## 4. 一个待决策项
**{决策问题}**（建议方案的代价：{人日 / 金额 / 时间 / 不可逆性}）。
备选：{方案 B + 代价} / {方案 C + 代价}。
**建议：{方案}。** 理由：{一句，指向代价对比}。
不决策则默认落在 {方案}，代价是 {具体后果}。
**决策截止：{YYYY-MM-DD HH:MM}**

> 数据来源、口径与完整三段式见 `docs/analysis/STATUS-{团队或项目}-{周期}.md` 版本 A 与其附录。
```

**填完后的三个同源检查**（防止四版数字打架）：

1. C.2 的 3 个数字必须能在 A.1.3 关键指标表里找到**同名同值同行**；找不到 → 说明是临时凑的，删掉换一个。
2. C.3 必须是 A.2 里严重度最高的那条（`[阻塞-本期]` 优先），不许另选一条「更好看的」。
3. C.4 的建议方案与截止时间必须与 A.3 完全一致；不一致说明母版本身没想清楚，先修母版。

### 版本 D：团队内部

内部版是**工作工具**，不是汇报材料。核心是「谁在做什么、下一步做什么、什么没人认领」。

```markdown
## 团队内部 W41（2026-10-05 ~ 2026-10-11）

### 1. 本期任务清单
| ID | 任务 | 负责角色 | 状态 | 备注 |
|---|---|---|---|---|
| T-101 | checkout P99 优化预发验证 | 后端 A 角色 | ✅ 已合并 | 210ms，见 §3 指标 |
| T-102 | 订单双写切流至 50% | 后端 B 角色 | ⚠️ 回退至 10% | 10-08 数据不一致告警；W42 先修校验 |
| T-103 | 结算接口联调（7 个） | 后端 C 角色 | ❌ 4/7 | 阻塞在对方证书，见 R1 |
| T-104 | pricing 补测试 | — | ❌ 未开始 | 被 T-105/T-106 挤占 |
| T-105 | 支付回调超时缺陷（插入） | 后端 A 角色 | ✅ 已修复上线 | P2，2 人日 |
| T-106 | 对账文件格式适配（插入） | 后端 C 角色 | ✅ 已完成 | 1 人日 |

### 2. 待认领
| 任务 | 预估 | 说明 |
```
