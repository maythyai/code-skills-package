# User Story Decomposition

Break down an Epic or large requirement into independently deliverable User Stories,
each with Acceptance Criteria (AC) and Story Point estimation. Every story is validated
against INVEST principles before output.

## When to Use

- A PRD has been approved and needs to be broken into development-executable stories
- An Epic is too large for a single sprint and needs splitting
- Sprint planning requires backlog grooming with properly sized stories
- The team needs clear acceptance criteria before starting implementation
- A product manager wants to validate story completeness before handoff

## When NOT to Use

- The requirement has not been decomposed into features yet (use `csp-requirement-decomposition` first)
- The user needs a full PRD, not story-level decomposition (use `csp-prd-generation`)
- The team is already in execution mode and stories exist (update stories directly, don't regenerate)

## Process

### Step 1: Input Collection

Collect the source material for decomposition:

| Input | Source | Required |
|-------|--------|----------|
| Epic or feature description | PRD, requirement doc, or verbal description | Yes |
| Target users and roles | From PRD or user's description | Yes |
| Business rules | From PRD or user's description | Yes |
| Existing system constraints | Team knowledge | If applicable |

If the input is a PRD generated by `csp-prd-generation`, read the feature modules from section 3 directly.

### Step 2: Story Identification

Identify user stories using the **Role-Action-Value** pattern:

```
As a [role], I want [action], so that [value].
```

**Splitting patterns** (apply when a story is too large):

| Pattern | When to Use | Example |
|---------|------------|---------|
| **Workflow steps** | Story spans multiple steps in a process | "Place order" -> "browse cart" + "enter address" + "select payment" + "confirm order" |
| **Business rule variants** | Story covers multiple rule branches | "Apply discount" -> "percentage discount" + "fixed amount discount" + "coupon code" |
| **User role variants** | Story involves multiple roles with different needs | "Manage users" -> "admin creates user" + "user edits profile" + "admin deactivates user" |
| **CRUD operations** | Story covers full data lifecycle | "Manage products" -> "create product" + "edit product" + "delete product" + "list/search products" |
| **Happy path vs. edge cases** | Story mixes normal flow with exceptions | "Process payment" -> "successful payment" + "failed payment handling" + "refund flow" |

**Story sizing target**: Each story should be completable within one sprint (typically 1-5 story points). If larger, split again.

### Step 3: INVEST Validation

Validate each story against INVEST principles:

| Principle | Check Question | Fix If Failing |
|-----------|---------------|----------------|
| **I**ndependent | Can this story be developed without waiting for another? | Remove dependencies or restructure scope |
| **N**egotiable | Is the implementation approach open to discussion? | Remove prescriptive implementation details |
| **V**aluable | Does this story deliver observable value to the user? | Reframe around user value, not technical task |
| **E**stimable | Can the team estimate the effort? | Add more detail or split further if ambiguous |
| **S**mall | Can it be completed in one sprint? | Apply splitting patterns from Step 2 |
| **T**estable | Can QA verify completion objectively? | Add concrete acceptance criteria |

### Step 4: Write Acceptance Criteria

For each story, write acceptance criteria in **Given-When-Then** format:

```
Given [precondition/context]
When [action/event]
Then [expected outcome]
```

**AC quality rules:**
- Each story has at least 3 ACs (happy path + 2 edge cases)
- ACs are concrete and verifiable (no "system should handle appropriately")
- Cover: normal flow, boundary conditions, error handling, permission constraints
- Use specific values where possible ("order total > $100" not "large orders")

**Example:**
```
Story: As a shopper, I want to apply a coupon code at checkout, so that I get a discount.

AC1: Given a valid coupon code "SAVE20" for 20% off,
     When I enter it at checkout and click "Apply",
     Then the order total is reduced by 20% and the coupon name is displayed.

AC2: Given an expired coupon code,
     When I enter it at checkout and click "Apply",
     Then I see an error message "This coupon has expired" and the total is unchanged.

AC3: Given a coupon that requires minimum order of $50,
     When my cart total is $30 and I apply the coupon,
     Then I see "Minimum order $50 required" and the coupon is not applied.

AC4: Given a coupon already applied to the order,
     When I try to apply a second coupon,
     Then the system replaces the first coupon with the new one (only one coupon per order).
```

### Step 5: Story Point Estimation

Estimate each story using relative sizing:

| Points | Meaning | Typical Scope |
|--------|---------|--------------|
| 1 | Trivial change | Config change, text update, simple bug fix |
| 2 | Small story | Single CRUD operation, simple UI component |
| 3 | Medium story | Standard feature with some business logic |
| 5 | Large story | Complex feature with multiple rules or integrations |
| 8 | Very large (consider splitting) | Multi-step workflow or cross-system integration |
| 13 | Too large (must split) | Epic-level, cannot be completed in one sprint |

Use **planning poker reference**: Compare each story to a known "3-point" baseline story from the team's history.

### Step 6: Generate Story Map

Output the stories organized by user activity and release:

```markdown
## Story Map

### Activity: User Management
| Priority | Story | Points | Release |
|----------|-------|--------|---------|
| P0 | Admin creates user account | 3 | v1.0 |
| P0 | User logs in with email/password | 2 | v1.0 |
| P1 | User resets password via email | 3 | v1.0 |
| P2 | Admin bulk-imports users from CSV | 5 | v1.1 |

### Activity: Order Processing
| Priority | Story | Points | Release |
|----------|-------|--------|---------|
| P0 | User adds product to cart | 2 | v1.0 |
| P0 | User completes checkout | 5 | v1.0 |
| P1 | User applies coupon code | 3 | v1.0 |
| P2 | User tracks order status | 3 | v1.1 |
```

### Step 7: Output

Save the story decomposition to `docs/stories/STORY-{epic-name}.md`:

```markdown
# User Stories: {Epic Name}

**Source**: {PRD reference or requirement description}
**Date**: {current date}
**Total Stories**: {count}
**Total Points**: {sum}

## Story List
(Detailed stories with ACs and estimates)

## Story Map
(Organized view by activity and release)

## Dependencies
(Cross-story dependencies, if any)

## Open Questions
(Unresolved items needing product/engineering discussion)
```

## Key Principles

- **One story, one value**: Each story delivers a single, observable user value. If it delivers two values, split it.
- **AC before implementation**: Acceptance criteria define "done" before anyone writes code. They are the contract between product and engineering.
- **Independent over optimized**: Stories should be independently shippable even if it means some initial redundancy. Dependencies between stories create scheduling risk.
- **Estimate relative, not absolute**: Story points measure relative complexity, not hours. A "5" is roughly twice a "3", not "5 days".
