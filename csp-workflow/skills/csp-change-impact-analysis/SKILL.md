# Change Impact Analysis

回答四个工程问题：**我改的这个东西，谁会受影响（影响面）？影响传多远（传导深度）？有多危险（风险分级）？要测哪些、怎么发、怎么回滚（回归与发布）？**

## 定位与分工边界

本技能处理**代码 → 代码/系统**链路的影响评估，与以下技能分工明确，不要混用：

| 技能 | 回答的问题 | 链路 | 何时用哪个 |
|------|-----------|------|-----------|
| `csp-prd-change-impact` | 需求变了，哪些文档/任务/代码要返工 | PRD → Feature → Spec → Task → Code（产品视角） | 变更源头是**需求文档** |
| **本技能** | 我要改这个代码/表/接口，会炸到哪里 | 代码 → 依赖方 → 契约 → 数据 → 部署 → 使用方（工程视角） | 变更源头是**一次具体改动**（改函数、改表、改配置、删接口） |
| `csp-code-graph` / `csp-graph-impact` | 基于已构建的代码图谱算函数级 blast radius | 图谱节点遍历 | 仓库已建图谱、只需代码级传导时优先用它，本技能的六维框架仍然适用（图谱只覆盖维度 1） |
| `csp-tech-risk-assessment` | 一个**技术方案**本身有哪些风险 | 方案 → 风险清单 | 评审设计阶段；本技能评审的是**具体改动**的落地影响 |

## 核心概念：正向影响 vs 反向依赖（最容易搞反）

```
          上游调用方 C ──依赖──> B ──依赖──> A（我要改的东西）
                                              │
                                              └──依赖──> D（A 依赖的库）
```

- **正向影响（forward impact）**：我改了 A，**谁依赖 A** 会受影响——沿"被依赖"边向**上游调用方**走（B、C）。做变更评估**主要看这个方向**。
- **反向依赖（reverse dependency）**：A 依赖了什么（D）——沿"依赖"边向**下游**走。改 D 会波及 A，但**改 A 不会波及 D**。

常见错误：改 A 时去分析"A 依赖的 D 会不会出问题"。那是改 D 的人才需要做的分析。判断口诀：**看"谁 import 我"，不是"我 import 谁"**。反向依赖只在两种情况下需要看：(1) 升级/替换 A 所依赖的 D 时；(2) 评估 A 的故障会不会因 D 的行为变化被放大时。

## 分析流程（五步，顺序执行）

1. **定义变更单元**：写清"改什么"——文件/函数/表/字段/接口/配置键/消息 schema，精确到符号级。一句话说不清变更单元的，先拆分。
2. **正向影响采集**：按六维度索引表（下节）逐维采集被依赖证据，每条结论必须附证据（命令 + 输出摘要），不允许"我记得"。
3. **传导深度截止**：按截止规则决定追到第几层（见"传导深度与截止规则"）。
4. **风险分级 + 回归范围推导**：填风险分级矩阵，推导最小必要回归集与完整回归集。
5. **产出报告**：写到 `docs/analysis/IMPACT-{change-slug}-{date}.md`，模板见 `references/report-template.md`。

## 六维度影响面索引

每个维度都要回答"受影响对象清单 + 证据 + 是否需改动"。详细命令库见 `references/impact-dimensions.md`（执行采集时逐维读取对应小节）。

| # | 维度 | 查什么 | 入口命令（示例） | 典型漏项 |
|---|------|--------|----------------|---------|
| 1 | 代码级 | 直接调用方、符号引用、**动态引用** | `grep -rn "funcName\|func_name" --include='*.{语言后缀}' .` | 反射/字符串路由/DI 抓不到，见下节 |
| 2 | 契约级 | API 请求响应结构、事件 schema、表结构与迁移、SDK/CLI 参数、配置键名 | `git diff --name-only -- '*/api/*' '*/schema/*' '*migration*' '*.proto' '*.yaml'` | 配置键名被外部脚本/运维手册引用 |
| 3 | 数据级 | 存量数据兼容、双写与回填、字段语义变化、缓存与索引失效 | 查 schema 迁移目录 + `grep -rn "{字段名}" --include='*.sql'` | **类型没变但含义变了**（最危险） |
| 4 | 运行时级 | 共享资源（连接池/线程池/内存/磁盘）、启动顺序与依赖就绪、定时任务与幂等 | `grep -rn "pool\|@Scheduled\|cron\|lock" --include='*.java'` 等 | 新代码抢占共享连接池拖垮邻居 |
| 5 | 部署级 | 多服务发布顺序、灰度与回滚能否独立、新老版本共存期兼容性 | 列出部署清单，逐个问"先发谁后发谁、能不能单独回滚" | 新老版本同时在跑时消息格式互不兼容 |
| 6 | 使用方级 | 下游团队/外部客户、文档与示例、监控看板与告警规则、埋点与报表口径 | `grep -rn "{接口路径}\|{事件名}" docs/ dashboards/ alerts/` | 报表口径依赖被改字段的旧语义 |

### 动态引用：静态搜索的盲区（必须单独排查）

grep 符号名只能抓到**编译期/文本可见**的引用。以下四类调用静态搜索抓不到，每一类都要用对应方法单独排查，排查结果（含"未发现"）写进报告：

| 动态引用类型 | 例子 | 查法 |
|-------------|------|------|
| 反射/按名加载 | `Class.forName(x)`、`importlib.import_module(x)`、`require(name)` | 搜索反射入口函数名，人工审查每个入口的 name 来源；对 name 的取值集合做二次 grep |
| 字符串路由/URL 映射 | 路由表 `"orders/create"`、事件名 `"user.signup"`、消息 topic | 用**字符串字面量**（路径、事件名、topic 名）而非函数名做全仓 grep，包括配置文件与测试数据 |
| 依赖注入/IOC | 容器按接口装配、插件机制、hook 注册 | 搜接口名/抽象类名的实现类清单（`grep -rn "implements {接口名}"`），再搜注册点（配置、注解、注册函数） |
| 构建期/外部引用 | CI 脚本、部署配置、其他仓库引用本仓库产物 | 在部署/CI 目录 grep 产物名、模块名；有 monorepo 工具时跑依赖查询（如 `nx graph`、`bazel query 'rdeps(//..., {target})'`） |

## 传导深度与截止规则

无限追溯会退化成"改一行影响全宇宙"，报告失去决策价值。可操作截止判据：

| 规则 | 内容 |
|------|------|
| R1 默认深度 | 代码级传导最多追 **2 层**（直接调用方 = 第 1 层，调用方的调用方 = 第 2 层） |
| R2 契约边界即停 | 传导命中**稳定契约边界**（公开 API、消息 schema、DB 表、发布产物）时停止向上追，记为"**需通知**"而非"需改动"——契约不变则边界外不受传导 |
| R3 契约变更则穿透 | 若本次变更**改了契约本身**，穿透该边界继续追外部使用方（维度 6），深度不限 |
| R4 高扇出强制追 | 某节点 fan-in ≥ 20（被 20+ 处直接引用）或属于共享基础库，强制追到第 3 层并单独列为高风险节点 |
| R5 每层去重 | 已出现过的节点不再展开，只标注"已列入"；环状依赖记一条并注明 |

产出格式：传导路径图（谁 → 谁 → 停在哪、为什么停），示例见 `references/report-template.md` 第 3 节。

## 风险分级矩阵

三轴评估，取每轴最高档后按下表定级：

- **影响范围**：单模块 / 跨服务 / 跨团队 / 对外（客户可见）
- **可逆性**：可热修（配置开关/代码回滚即可）/ 需发布回滚 / 需数据迁移才能回退 / 不可逆
- **检测难度**：有测试覆盖（CI 能拦住）/ 有监控告警（分钟级发现）/ 只有用户会发现

| 级别 | 判定条件（满足任一） | 强制动作 |
|------|---------------------|---------|
| **R0 禁改直发** | 无 | —— |
| **R1 常规** | 单模块 + 可热修 + 有测试覆盖 | 正常 CR + CI 通过即可 |
| **R2 谨慎** | 跨服务，或需发布回滚，或仅有监控无测试 | CR 需模块 owner 参与；列出回归清单；发布窗口避开高峰 |
| **R3 高危** | 跨团队，或需数据迁移才能回退，或只有用户会发现 | **设计评审 + 灰度发布 + 回滚预案演练 + 通知全部下游**；R3 变更不允许无灰度全量 |
| **R4 不可逆** | 命中"不可逆"任一形态（见下节） | R3 全部动作 + **扩展-收缩（expand-contract）改造为可逆** + 最短保留期承诺 + 不可改造时升级到架构负责人签字 |

分级样例：给订单表 `orders.status` 增加枚举值 = 跨服务（消费方多）+ 可热修（新增值兼容旧逻辑需验证）+ 仅监控 → **R2**；删除 `orders.legacy_flag` 列 = 跨团队 + 不可逆 + 只有用户会发现 → **R4**。

## 不可逆变更（先判定，再动手）

四类高频不可逆形态与一句话安全做法，完整手册（双写过渡、废弃标记、最短保留期、每类 checklist）见 `references/irreversible-changes.md`（**变更命中任一类时必读**）：

| 形态 | 安全做法（核心原则：扩展-收缩 expand-contract） |
|------|---------------------------------------------|
| DB 删列/改类型 | 先扩（加新列/双写）→ 迁移（回填 + 切读）→ 观察期（≥1 个发布周期）→ 收缩（删旧列），每步独立可回滚 |
| 删除公开 API | 先标废弃（返回头/文档/告警统计剩余调用量）→ 调用量连续 2 周为 0 → 才允许下线 |
| 重命名对外字段 | 新旧字段并存双写，读方切换完成后停写旧字段；禁止"一步改名" |
| 数据格式转换 | 转换必须可逆或保留原始数据备份；先转换副本验证，再动生产数据 |

## 回归范围推导

从影响面清单反推测试集合，区分两档：

| 集合 | 定义 | 何时跑 |
|------|------|--------|
| **最小必要回归集** | 断言直接覆盖受影响路径的测试 + 受影响契约的契约测试 + 维度 3/4 中每个"存量数据兼容""共享资源"结论对应的验证项 | 每次提交/合并前（CI） |
| **完整回归集** | 最小集 + 传导第 2 层节点的既有测试 + 受影响使用方的集成/端到端场景 | R2 及以上发布前；R3/R4 需在预发环境全量跑 |

**判断某个既有测试是否真的覆盖受影响路径：看断言，不看文件名。** 步骤：(1) 打开测试文件，找对被改符号/接口/字段的**断言**（assert/expect/should），不是找对被改函数的调用——调用了但没断言其行为的测试不提供保护；(2) 断言的是"旧行为"还是"新行为"？断言旧行为的测试会在变更后失败，属于"必须同步修改的测试"，要列入变更清单；(3) 找不到任何断言覆盖 → 该路径无测试保护 → 检测难度升一档（按"只有用户会发现"处理），并补测试或加监控。

## git 侧证据采集（速查）

完整命令库与输出解读见 `references/git-evidence.md`（需要定位作者、变更频率、符号历史时读取）。

| 目的 | 命令 |
|------|------|
| 改动形状（碰了几个文件、多少行、哪些模块） | `git diff --stat --find-renames origin/main...HEAD` |
| 文件真实作者与最近改动 | `git blame -L {起},{止} -- {file}`；`git log --follow --format='%an %ad %s' --date=short -- {file}` |
| 高频变更文件 = 高风险区 | `git log --since='12 months ago' --name-only --format= -- {dir} \| sort \| uniq -c \| sort -rn \| head -20` |
| 一个符号的完整历史（何时引入/谁改过/关联提交说明） | `git log -S'{symbol}' --oneline -- '*.ext'` |
| 重命名/移动后仍能追踪 | `git log --follow -- {file}` |

用法要点：高频变更 + 高 fan-in 的文件是 R3 候选；`git log -S` 找到符号历史后，读关联提交说明，常能发现"上次改这里炸过什么"。

## Key Principles

1. **变更评估看正向影响**：找"谁依赖我"，不是"我依赖谁"；方向搞反的分析全部作废。
2. **每条影响结论必须附证据**：命令 + 输出摘要；"我记得没人用"不是证据，三项搜索（符号名、字符串字面量、构建依赖）都为空才能写"未发现调用方"并注明盲区。
3. **动态引用单独排查**：反射、字符串路由、DI、构建期引用四类静态搜索抓不到，不排查等于影响面必漏。
4. **传导有截止**：默认 2 层，命中稳定契约边界即停并记"需通知"；契约本身变了才穿透边界。
5. **可逆性决定发布策略**：先判可逆性再谈灰度；不可逆变更必须先 expand-contract 改造成可逆，或升级签字。
6. **回归范围按断言推导**：测试绿不等于覆盖了受影响路径；看断言内容，不看文件名、不看通过率。
7. **报告面向决策**：六维表 + 分级 + 发布顺序 + 回滚 + 通知名单，缺任何一节都不算完成。

## Anti-Patterns

| 反模式 | 为什么错 | 正确做法 |
|--------|---------|---------|
| 只 grep 函数名就宣布影响面 | 漏掉反射/字符串路由/DI/外部仓库四类动态引用 | 符号名 + 字符串字面量 + 构建依赖三路搜索，动态引用单独一节 |
| 改 A 时分析 A 依赖的库的风险 | 方向反了，那是改库的人的分析 | 沿"被依赖"边向上游调用方追 |
| 无限追溯传导链 | 退化成"改一行影响全宇宙"，报告没人看 | 2 层截止 + 契约边界即停 + 高扇出强制追 |
| 用测试通过率证明没影响 | 断言不覆盖受影响路径时全绿也是假阴性 | 逐个打开候选测试检查断言对象与新旧行为 |
| 删"看起来没人用"的代码前只搜本仓库 | CI 脚本、部署配置、其他仓库可能在用 | 加搜部署/CI 目录与产物名，monorepo 跑反向依赖查询 |
| 一步重命名对外字段 | 新老版本共存期与外部读方直接断裂，且不可回滚 | expand-contract：新旧并存双写 → 切读 → 停写旧字段 |
