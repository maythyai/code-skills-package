# 不可逆变更手册

原则只有一条：**先改造成可逆，再执行**。手段是扩展-收缩（expand-contract，也叫 parallel change）：先扩展（新旧并存）→ 迁移（切流量/切读写）→ 观察期 → 收缩（删旧）。每一阶段独立发布、独立可回滚。

通用规则：

- **观察期最短 1 个完整发布周期，且不少于 14 天**（覆盖低频调用方：周批处理、月度对账、季度任务）。
- **废弃标记三件套**：代码内废弃注解/警告日志（记录调用方标识）+ 文档废弃公告（含下线日期）+ 调用量监控（剩余调用量看板/告警）。
- **下线判据**：剩余调用量连续 2 周为 0，且废弃公告期已过，两者同时满足。
- 任何一步失败的回滚动作必须提前写出来并演练过，"回滚 = 重新发布上一版本"在数据已写入后往往不成立。

## 1. 数据库删列 / 改类型

| 禁止 | 安全做法（四步，四次独立发布） |
|------|------------------------------|
| `ALTER TABLE t DROP COLUMN c` 与删代码同一次发布 | ① **扩**：加新列/新表（改类型场景：加目标类型的新列）；② **迁**：应用双写新旧列 + 后台回填存量（幂等 upsert，分批限流），回填完成后切读到新列；③ **观察**：≥14 天，验证新列数据一致（对账脚本比对新旧列）；④ **收**：停写旧列 → 下一次发布才 `DROP COLUMN` |

改类型的额外注意：

- 精度缩窄（decimal(18,4) → decimal(18,2)）、有符号 → 无符号、varchar 截短都会**静默丢数据**，必须先查存量数据分布：`SELECT max(length({field})), min({field}), max({field}) FROM {表}`。
- 锁表风险：大表 DDL 用在线变更工具（按仓库既有实践选择），并评估执行窗口。
- `NOT NULL` 加约束前必须先回填：`SELECT count(*) FROM {表} WHERE {field} IS NULL` 必须为 0。

回滚预案：①②③ 任一阶段回滚 = 回退应用版本，旧列仍在，无损。④ 执行后**不可回滚**（列已删），所以 ④ 必须单独发布且与 ③ 间隔一个观察期。

## 2. 删除公开 API（HTTP/RPC/SDK 方法）

流程：

1. **标废弃**：接口返回废弃标记（如响应头 `Deprecation: true` + `Sunset: {日期}`），SDK 方法加废弃注解，服务端打警告日志并**记录调用方标识**（appkey/UA/token 归属）。
2. **公告**：文档标注废弃与下线日期；通过既有渠道通知已知调用方；给出迁移指引（替代接口 + 示例）。
3. **监控剩余调用量**：建看板，按调用方分组；下线判据 = 连续 2 周为 0。
4. **软下线**：先返回 410/明确错误码（而非直接 404），保留 2 周——错误码能区分"已废弃"与"从来不存在"，方便漏网调用方自查。
5. **硬下线**：删除路由与实现代码。

注意：内部 API 也要走 2–4 步，只是公告范围小；"内部没人用"仍需日志证据，grep 只能证明本仓库没人用。

## 3. 重命名对外字段（API 响应字段、消息字段、导出文件列名）

禁止"一步改名"（新旧版本共存期与外部读方直接断裂）。安全做法：

1. 新字段与旧字段**并存双写**（响应同时含 `oldName` 与 `newName`）。
2. 公告 + 文档同时展示两字段，标注旧字段废弃日期。
3. 读方切换完成后（调用量/日志证据），停写旧字段——停写本身也是一次"删除公开 API"，走上一节流程。
4. 消息 schema 场景：schema 注册表中新版本 schema 必须向后兼容（只加不删），消费方全部升级后才发布删旧字段的 schema 版本。

## 4. 数据格式转换（序列化格式、编码、存储结构迁移）

规则：**转换必须可逆，或保留原始数据**。

1. 先转换**副本**验证：抽样 N 条（覆盖边界值：空值、超长、特殊字符、历史各版本格式），转换 → 反转/比对，全部通过才动生产。
2. 生产转换分批 + 保留原始数据（备份表/快照），保留期 ≥ 观察期。
3. 读路径先做**双格式兼容**（能读新也能读旧），再开始写新格式——顺序反了会在灰度期炸掉未升级实例。
4. 转换脚本幂等：重跑不产生二次转换（写入前检查格式版本标记）。

## 5. 其他准不可逆形态（速查）

| 形态 | 为什么难逆 | 安全做法 |
|------|-----------|---------|
| 删除枚举值/状态码 | 存量数据里还有该值，新代码遇到即报错 | 先停止产生新值 → 迁移存量 → 观察期 → 再删代码分支；读路径永久保留"未知值兜底" |
| 合并/拆分数据表 | 双写与回填窗口长，中途回滚成本高 | 同删列四步法；拆表时先建影子表双写，读切换用开关控制可秒级回切 |
| 变更 ID 生成规则 | 新旧 ID 共存，所有按 ID 关联的下游都受影响 | 新 ID 只用于新数据；禁止回填改写存量 ID；全链路 grep ID 消费点 |
| 降低数据保留期（TTL 缩短、日志清理） | 删掉的数据找不回 | 先导出归档再删；缩短前统计"最老被访问数据"的访问日志 |
| 权限/密钥轮转 | 旧凭证立即失效会切断存量调用方 | 双凭证并行期 ≥ 14 天，先监控旧凭证调用量归零再吊销 |

## 变更前 checklist（命中不可逆时逐项打勾）

- [ ] 已按 expand-contract 拆成 ≥2 次独立发布，每步单独可回滚
- [ ] 回滚动作已写出并演练（不是"回退版本"四个字）
- [ ] 存量数据分布已查（NULL/空串/边界值/旧格式样本计数）
- [ ] 双写/回填脚本幂等，可重跑
- [ ] 废弃标记三件套已就位（代码警告日志 + 文档公告 + 调用量监控）
- [ ] 观察期 ≥ 14 天且覆盖一个完整发布周期
- [ ] 下线判据明确（调用量连续 2 周为 0 + 公告期已过）
- [ ] 已知调用方通知清单（报告第 8 节）已发出并有确认记录
- [ ] R4 级：架构负责人已签字
