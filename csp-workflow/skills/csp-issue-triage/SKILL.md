# Issue Triage

处理**被动流入**的问题报告：一堆单子进来了，怎么判重、定级、判可复现性、派给谁、多久内响应、怎么关。

## 定位与分工边界

| 技能 | 方向 | 输入 | 何时用哪个 |
|------|------|------|-----------|
| **本技能** | 被动流入的分诊 | 工单系统里的报告（缺陷/报错/用户投诉） | 报告已经进来了，要判重定级派单 |
| `csp-defect-mining` | 主动挖掘 | 代码本身 | 没有报告，主动从代码里找潜在缺陷 |
| `csp-user-feedback-analysis` | 聚合找趋势 | 大批量反馈语料 | 跨周期分析反馈主题与优先级输入，不做单条分诊 |
| `csp-systematic-debugging` | 单条深挖 | 一个已确认的 bug | 分诊后需要定位根因时移交 |
| `csp-incident-commander` | 事故指挥 | 进行中的线上事故 | 分诊判定为 P0 且正在发生时移交 |

分诊只回答"**这是什么、多严重、归谁、多快**"，不在分诊阶段修 bug。

## 分诊流水线（顺序不可乱）

```
去重合并 → 分类 → 可复现性判定 → 定级 → 归属路由 → SLA 与响应 → 归档
```

每步依赖前一步的输出，乱序会产生具体错误：

| 顺序 | 为什么不能提前/推后 |
|------|-------------------|
| 1. 去重合并先做 | 不去重就分类定级 = 同一个 bug 被定级 N 次、派给 N 个人；且重复计数会虚增"激增"信号，触发错误的升级动作 |
| 2. 分类在定级前 | 需求/咨询/误报/环境问题不该进缺陷 SLA 通道；先分类才能只给真缺陷定级，否则缺陷统计被污染 |
| 3. 可复现性在定级前 | 可复现性影响处理策略（直接修 vs 先补证据），也影响检测难度评估；但**不影响严重度定级**（偶发的数据丢失仍是 P0） |
| 4. 定级在路由前 | 级别决定响应时限与主责方层级：P0 要拉事故指挥，P3 走常规排期；先派单后定级会导致 P0 躺在某人队列里 |
| 5. 路由在 SLA 前 | SLA 计时从"派给明确主责方"开始；无主单不存在有效的 SLA 起算点 |
| 6. 归档最后 | 归档动作 = 把本次分诊结果写入 `docs/analysis/TRIAGE-{date}.md`，为趋势分析留存结构化数据 |

## 第 1 步：去重合并

### 多信号判重（相似度不能只看标题）

五个信号，命中越多越可信；**指纹相同即可合并，指纹不同但其余四信号全同要人工复核**：

| 信号 | 内容 | 权重 |
|------|------|------|
| 报错指纹/堆栈签名 | 规范化后的异常类型 + 调用序列前 N 帧（提取规则见下） | 最强，单独命中即可初步合并 |
| 触发路径 | 用户操作序列/入口接口/任务名 | 强 |
| 影响版本 | 首次出现版本 + 当前版本区间 | 中（跨版本可能是同根因回归） |
| 受影响用户群 | 租户/地域/设备/账号特征 | 中 |
| 时间窗聚集 | 首次上报时间是否在同一窗口（如同日、同发布后 48h） | 弱（仅辅助） |

**堆栈签名提取**：去掉行号、内存地址、时间戳、请求 ID、UUID、用户 ID 等易变部分，保留异常类型 + 函数调用序列的**前 3–5 帧**（业务代码帧优先，框架帧靠后）。为什么必须去行号：一次无关的格式化提交让所有行号偏移，带行号的签名会把**同一个 bug 拆成几十个"不同"的单**。完整提取规则、各语言正则与示例见 `references/fingerprint-and-dedup.md`（执行判重时读取）。

### 合并而不是关闭

- **保留一个主单**：信息最全、最早创建、或讨论最多的那个；其余标记 `duplicate-of: {主单号}` 并建立双向链接，**不直接关闭**（关闭会切断报告者的追踪与通知链路）。
- **主单必须吸收副本的独有信息**：不同环境下的复现步骤、不同版本的堆栈、副本里独有的附件与用户群证据。合并 = 信息并集，不是删掉副本了事。
- 副本报告者自动订阅主单进展。

### "看起来像但不是同一个 bug"陷阱

同一条报错信息/同一个堆栈顶帧可能来自完全不同的根因（`Connection timeout`：连接池耗尽 vs 下游服务宕机 vs 网络分区）。防错规则：

1. 指纹相同但**触发路径或用户群明显不同**时，暂缓合并，标 `possible-duplicate` 观察 2–3 天；
2. 合并后若主单修复上线、副本场景仍复现，立即拆单并回溯合并记录；
3. 合并决定要留痕（谁、依据哪几个信号），便于拆单时复查。

## 第 2 步：分类

三个维度各自独立打标：

| 维度 | 取值 | 说明 |
|------|------|------|
| 类型 | 缺陷 / 需求 / 咨询 / **误报** / **环境问题** / 数据问题 | 误报与环境问题**必须单独成类**：混进缺陷会虚增缺陷率、扭曲 SLA 统计、让真缺陷的平均处理时长失真。误报多本身是产品可发现性问题，单独统计单独治理 |
| 模块归属 | 按代码模块/服务划分 | 依据堆栈所在代码 + 功能面，不依据报告者随手选的分类 |
| 影响功能面 | 登录/支付/报表/…（按产品实际功能域） | 用于第 7 步聚类：同功能面工单集中 = 趋势信号 |

分流规则：需求 → 移交需求评估流程（可用 `csp-requirement-prioritization`）；咨询 → 直接答复并沉淀到知识库/FAQ；环境问题 → 答复 + 判断是否暴露环境配置缺陷；数据问题 → 走数据修复流程，单独跟踪。只有**缺陷**继续走后面的分诊步骤。

## 第 3 步：可复现性判定（五级）

| 级别 | 判据 | 处理策略 |
|------|------|---------|
| A 总是复现 | 按步骤 100% 复现 | 直接进入定级路由；修复后以此步骤做验证用例 |
| B 高概率 | >50% 概率复现，条件大致可知 | 正常处理；记录触发条件假设，交 `csp-systematic-debugging` 收敛 |
| C 偶发 | <50%，无明确条件 | 定级**不降级**；加日志/埋点缩小条件空间；关联监控看是否持续发生 |
| D 仅报告者环境 | 只在特定账号/设备/数据下复现 | 提取环境差异清单（版本、数据特征、权限、网络）；尝试构造等价环境；构造不出则按 C 处理 |
| E 无法复现 | 信息不足或完全无法触发 | **不等于关闭**，见下 |

**E 级的正确做法**：标记 `待观察` → 补齐观测手段（该路径加结构化日志/埋点/错误上报，让下次发生时自动带全上下文）→ 设**复现窗口期**（建议 30 天）→ 窗口内再次上报即升级为 C 并关联前单 → 窗口期满且监控无该错误再关闭，关闭原因写"窗口期内无复现且监控未见"，**不写"无法复现"**。为什么不能直接关：直接关掉 = 消灭证据不消灭问题，同类问题会反复上报、每次从零开始，且丢失了跨报告的聚集信号（第 7 步趋势识别依赖这些关联）。

## 第 4 步：定级（严重度 × 影响面 → P0–P3）

**严重度由影响决定，不由报告者的情绪或职级决定。** 标题里的"紧急！！！"、报告者的职位、催促次数都不进定级输入；只认下表两个客观轴。

严重度（取最重一项）：

| 档 | 判据 |
|----|------|
| S1 数据丢失/资金损失 | 数据不可恢复、错账、多扣少扣、泄露 |
| S2 核心流程阻断 | 主流程走不通且无绕过方案（登录、下单、支付、核心任务） |
| S3 功能降级 | 有绕过方案，或非核心功能不可用，或明显性能劣化 |
| S4 体验瑕疵 | 文案、样式、非阻塞交互问题 |

影响面：

| 档 | 判据 |
|----|------|
| I1 全部用户 | 或全部租户/全部核心场景 |
| I2 部分用户 | 可刻画的用户群（某版本/某地域/某类账号） |
| I3 单用户 | 仅个别账号，且非数据/资金问题 |
| I4 内部 | 仅内部工具/测试环境 |

定级矩阵与 SLA（时限数字是默认基线，团队可按实际调整但必须显式写在分诊记录里）：

| | I1 全部用户 | I2 部分用户 | I3 单用户 | I4 内部 |
|---|---|---|---|---|
| **S1 数据/资金** | **P0** | **P0** | **P1** | P2 |
| **S2 核心阻断** | **P0** | **P1** | P2 | P3 |
| **S3 功能降级** | P1 | P2 | P3 | P3 |
| **S4 体验瑕疵** | P2 | P3 | P3 | P3 |

| 级别 | 响应时限 | 处理时限（修复或明确方案） | 热修 | 管理层通知 |
|------|---------|--------------------------|------|-----------|
| P0 | 15 分钟内有人接手 | 24 小时内止血（热修/回滚/降级开关），根因修复另立单 | 需要，走 `csp-hotfix`；正在发生的事故移交 `csp-incident-commander` | 立即通知 + 每日进展同步直至关闭 |
| P1 | 2 小时内 | 3 个工作日 | 视绕过方案有无决定 | 通知团队负责人，周报跟踪 |
| P2 | 1 个工作日 | 进最近一次迭代排期 | 不需要 | 周报汇总 |
| P3 | 2 个工作日 | 进需求/缺陷 backlog 按优先级排 | 不需要 | 月度汇总 |

注意：单用户 + 数据丢失 = P1 不是 P3——影响面小不豁免严重度；反过来全员 + 体验瑕疵也不低于 P2。可复现性 C/E 级**不参与降档**。

## 第 5 步：信息完整性检查（缺则先补再定级）

一份合格的缺陷单必须有六项：

1. 环境版本（应用版本、OS/浏览器/设备、部署环境）
2. 复现步骤（编号步骤，含入口与前置数据）
3. 期望 vs 实际（两句话分开写）
4. 证据附件（截图/录屏/日志片段/完整堆栈）
5. 影响范围（多少用户/哪些租户/是否持续发生）
6. 首次出现时间（用于关联发布窗口）

缺 1/2/3/4 任一项 → **先补信息再定级**（缺信息时定级必然失真）；缺 5/6 → 可先行定级并标记待补。补充请求用固定模板发出（见 `references/triage-templates.md` 第 1 节，可直接复制发给报告者），同时把单子标记 `待补信息` 并设 **3 个工作日**催办期；到期未补再标记 `信息不足挂起`（不是关闭），挂起单每 30 天批量复查一次。

## 第 6 步：归属路由

判定"派给谁"的三个证据，按优先级：

1. **模块 owner**：受影响模块的负责人表（CODEOWNERS 类文件或团队维护的 owner 清单）；
2. **堆栈所在代码**：堆栈最深处的**业务代码帧**（跳过框架帧）所属模块 → 该模块 owner；
3. **最近改动人**：`git log --since='30 days ago' --format='%an %s' -- {堆栈对应文件}` 的活跃改动者——问题在谁最近改过的代码里爆发，谁最有上下文（是"最该参与排查的人"，不必然是"责任归属"）。

**跨模块问题不能踢皮球**：必须指定一个**主责方**（通常是故障表现所在模块，或最近变更引入方）+ 若干**协作方**。主责方职责：推进到底（组织排查、汇总结论、驱动修复、负责关单），协作方职责：在被要求时限内提供本模块信息。规则：任何单子在 2 次转派后仍无主 → 升级到双方共同的上级指定主责方，**不允许第三次转派**。

## 第 7 步：批量聚类与趋势（激增识别）

单位时间（默认按天）对新单做三路聚类，任一命中即为激增信号。计数方法、阈值与升级动作细节见 `references/surge-and-clustering.md`（批量分诊 >20 单/天，或发现聚集迹象时读取）：

| 聚类路 | 激增判据（默认基线） | 典型含义 |
|--------|--------------------|---------| 
| 同一指纹计数 | 单指纹 24h 内 ≥5 单，或达前 7 天日均的 3 倍 | 一个具体 bug 在大面积发生 |
| 同一模块集中 | 单模块单日新增 ≥ 该模块前 7 天日均的 3 倍 | 模块级质量劣化或环境故障 |
| 发版时间窗关联 | 新版本发布后 48h 内，"首次出现版本 = 新版本"的单 ≥3 | 回归，发布引入 |

激增时的升级动作（按序评估，不是全做）：① 评估**暂停发布/继续灰度冻结**；② 评估**回滚**（若与发版窗口强关联且回滚可逆）；③ 成立专项（指定专人集中处理该聚类，暂停其常规迭代）；④ P0 级激增移交 `csp-incident-commander`。

## 第 8 步：闭环与防复发

- **关单三要素**：根因（一句话，到代码/配置/数据/流程层面）+ 修复动作（关联提交/变更单）+ 验证方式（谁用什么步骤验证的）。只写"已修复"不允许关单——那是状态不是结论。
- **重复触发治理**：同一指纹/同一根因类别的单在 90 天内第 **3** 次出现 → 不再逐单修，立根因治理项（进 backlog 按 `csp-requirement-prioritization` 排期）：补测试、加防御、改设计、加监控告警任选组合，目标是"下次发生时被机器拦住而不是被用户上报"。
- 关单时回填分诊记录（实际级别 vs 初判级别、实际耗时 vs SLA），供下一周期校准。

## 产物

分诊结果写到 `docs/analysis/TRIAGE-{date}.md`（如 `TRIAGE-2026-02-14.md`），**绝不写仓库根目录**。完整模板（新增单数 / 去重合并数 / 分级分布 / P0-P1 明细 / 待补信息清单 / 归属分派 / 趋势告警）见 `references/triage-templates.md` 第 3 节（每次批量分诊结束时读取并填写）。

## Key Principles

1. **先去重再一切**：重复计数会虚增定级工作量与激增信号；判重看五信号（指纹/路径/版本/用户群/时间窗），不看标题。
2. **合并是信息并集**：保留主单、副本标链接不关闭、主单吸收所有副本的独有复现信息。
3. **严重度由影响决定**：报告者情绪、职级、催促次数不进定级输入；单用户的数据丢失也是 P1。
4. **无法复现 ≠ 关闭**：待观察 + 补观测手段 + 30 天窗口期，期满且监控无异常才可关，关闭原因不写"无法复现"。
5. **缺信息先补再定级**：环境/步骤/期望实际/证据四项缺一即发补充模板，3 个工作日催办。
6. **跨模块必有主责方**：主责方推进到底，2 次转派后升级指定，不允许第三次转派。
7. **关单必须有根因**：根因 + 修复动作 + 验证方式三要素；同根因 90 天第 3 次出现即立治理项，不再逐单修。

## Anti-Patterns

| 反模式 | 为什么错 | 正确做法 |
|--------|---------|---------|
| 按标题相似度判重 | 同一报错不同根因被误合并；不同表述的同一 bug 漏合并 | 五信号判重，指纹优先；指纹同但路径/用户群不同则标 possible-duplicate 观察 |
| 重复单直接关闭 | 切断报告者追踪链路，副本独有信息（其他环境的复现步骤）丢失 | 标 duplicate-of + 双向链接 + 信息并入主单 |
| 堆栈签名带行号 | 一次无关提交让行号偏移，同一 bug 被拆成几十个单 | 签名去掉行号/地址/ID/时间戳，保留异常类型 + 前 3–5 帧业务调用序列 |
| 误报/环境问题计入缺陷率 | 缺陷统计失真，质量趋势无法判断，真缺陷被稀释 | 单独成类单独统计；误报率高本身作为产品可发现性问题治理 |
| 因为"偶发"把 P0 降成 P2 | 可复现性不是严重度轴；偶发的资金损失仍是 P0 | 定级只看严重度 × 影响面；可复现性只影响处理策略 |
| VIP 用户/领导转发的单一律 P0 | 定级被身份绑架后 SLA 全面失真，真正的 P0 反而被淹没 | 按矩阵定级；身份只影响"沟通频次"，不影响级别 |
| 无法复现直接关单 | 消灭证据不消灭问题，同类上报反复从零开始 | 待观察 + 加观测 + 窗口期 + 到期再判 |
| 无主单在队列里"等认领" | 无主 = SLA 无起算点 = 无人负责，P0 也能躺一周 | 派单必须有明确主责方；跨模块定主责 + 协作，2 次转派后升级指定 |
| 关单只写"已修复" | 无根因则无法判重下次同类单，无法触发防复发 | 关单三要素：根因 + 修复动作 + 验证方式 |
| 同一 bug 第 N 次逐单修 | 每次都在消耗处理成本，用户每次都在当检测器 | 90 天第 3 次出现立根因治理项：补测试/加防御/加告警 |
| 激增时先加班消化 | 激增是信号不是工作量：发版窗口关联的激增继续消化 = 放任回归扩散 | 先做三路聚类判激增类型，评估暂停发布/回滚/专项 |
