# 分诊模板集

三节：① 发给报告者的补充信息请求模板；② 规范化缺陷单模板；③ TRIAGE 分诊记录模板。复制即用，`{}` 为占位符，`>` 引用块是填写说明（交付时删除）。模板中的渠道词一律用中性表述（工单系统、IM、知识库）。

## 1. 补充信息请求模板（缺信息时发给报告者）

```markdown
你好，关于 {单号}《{原标题}》，为了尽快定位，请补充以下信息（标 * 为必填）：

1. *环境版本：应用/客户端版本号（在 {设置-关于} 中可查看）、操作系统及版本、
   浏览器及版本（如适用）、发生环境（生产/预发/测试）
2. *复现步骤：从 {入口页面/操作起点} 开始，按顺序编号每一步操作，
   包括使用的账号类型与关键输入数据（脱敏即可）
3. *期望结果 vs 实际结果：分开各写一句话
4. *证据：完整报错截图或日志片段（请包含时间戳与完整堆栈，不要只截一行）、
   如有录屏更好
5. 影响范围：只有你遇到，还是团队/其他用户也遇到？大约多少人？是否仍在持续发生？
6. 首次出现时间：第一次遇到是什么时候？此前同一操作是否正常？
   （用于关联最近的发布窗口）

补充方式：直接在本单评论回复即可。我们会在收到后 {1 个工作日} 内完成定级并同步进展。
若 {3 个工作日} 内未收到补充，该单将转入"信息不足挂起"（不会关闭，补充后随时恢复）。
```

要点：一次性列全，不分多轮挤牙膏；给出"怎么找版本号"的具体位置；明确不补充的后果是挂起而非关闭。

## 2. 规范化缺陷单模板（分诊后主单的标准结构）

```markdown
# {单号} {一句话标题：现象 + 触发场景，如"下单时优惠券叠加导致金额计算为负"}

## 分诊结论
- 类型：缺陷 ｜ 模块：{模块名} ｜ 功能面：{功能域}
- 可复现性：{A 总是 / B 高概率 / C 偶发 / D 仅报告者环境 / E 无法复现(待观察)}
- 定级：{P0-P3}（严重度 {S1-S4} × 影响面 {I1-I4}，依据：{一句话}）
- 主责方：{团队/人（role）} ｜ 协作方：{…} ｜ SLA：响应 {时限} / 处理 {时限}
- 指纹：{异常类型 @ 帧1 <- 帧2 <- 帧3}
- 合并记录：本单为主单，吸收 {副本单号列表}；或 duplicate-of {主单号}

## 环境与版本
{应用版本、环境、OS/浏览器、首次出现版本}

## 复现步骤
1. {…}
2. {…}
（来自 {副本单号} 的 {其他环境} 复现步骤：{…}）

## 期望 vs 实际
- 期望：{…}
- 实际：{…}

## 证据
{日志片段（含完整堆栈）/ 截图 / 录屏链接 / 错误上报平台的样本 ID}

## 影响范围
{受影响用户群与规模、是否持续发生、有无数据/资金影响、监控中的发生频次}

## 时间线
- {日期} 首次上报（{单号/来源}）
- {日期} 合并 {N} 个重复单
- {日期} 定级 {Px}，指派 {主责方}
```

填写自检：

- [ ] 总览数字与前 7 天基线有对比，异常有 ⚠ 标记
- [ ] 每个 P0/P1 有主责方与时限，无"待认领"
- [ ] 待补信息单都有催办期限（发出 +3 个工作日）
- [ ] 跨模块单写明了主责/协作与路由依据
- [ ] 三路聚类都填了观测值与阈值（未命中也要写数值，供下期基线）
- [ ] 关单类记录含根因三要素（根因/修复动作/验证方式）
