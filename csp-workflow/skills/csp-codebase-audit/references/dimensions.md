# Reference: Dimension Prompt Templates & Report Structure

本文件为 `csp-codebase-audit` 技能的参考资料，包含各维度代理的 prompt 模板和最终文档结构模板。

---

## 一、代理 Prompt 通用骨架

每个维度的代理 prompt 按以下结构组装：

```
你是{角色名}。只做研究，不写代码，不修改任何文件。对 {项目路径} 做"{维度名}"维度的彻底审查（very thorough）。

项目背景：{Phase 0 产出的 3-5 句摘要，含技术栈、核心子系统、规模、审查基线}。

重要：如代理环境对文件系统有访问限制，明确告知代理使用哪些工具/路径读取项目（如 mcp__local__* 工具、cwd、已禁用的内置工具等），避免代理尝试错误的工具。

请调查并回答：
1. {具体问题 1}
...
N. {具体问题 N}

输出格式要求：
- 按严重度分级：P0（安全红线/数据丢失）/ P1（高：功能不可用/架构腐化）/ P2（中：技术债/可维护性）/ P3（低：优化建议）
- 每条 finding 必须含：位置（file:line）+ 证据（代码片段/grep 结果）+ 后果（对用户/系统的影响）
- 对"宣称 vs 实际"的差异单独标注
- 最后给出该维度的一句话总结论 + 成熟度评级（A/B/C/D）
```

## 二、核心 5 维 Prompt 模板

### 维度 ① 功能模块完整性

角色名：产品功能审查研究员

调查问题模板：
1. 功能清单盘点：各子系统实际实现了什么功能？哪些"完整可用"，哪些"半成品/脚手架"（只有 models 没有业务逻辑、只有 TODO、大量 NotImplementedError/pass、正文 < 20 行）？
2. 宣称 vs 实际：README/CHANGELOG 宣称的功能在代码中是否真实存在且接线完整？找出"文档说有但代码没有"和"代码有但从未被调用"的情况。
3. 功能冗余：同一概念是否有多套并行实现？哪些是历史遗留可合并/删除？
4. 接口暴露面：有多少 API 端点/命令是真实可达的（被 router 挂载、被 CLI 注册）vs 死代码？
5. 配置复杂度：配置项总数、有多少无文档/无默认值/无测试覆盖？
6. 依赖健康度：核心外部依赖是否有已知 CVE、是否 pinned、是否有替代必要？
7. 悬空引用：skills/docs 引用的 reference/templates 路径有多少断链？抽样统计。

### 维度 ② 技术架构

角色名：资深软件架构审查研究员

调查问题模板：
1. 分层与依赖方向：模块间依赖是否清晰？有没有循环依赖、底层模块反向依赖上层？用 grep 检查 import 关系，找具体例子。
2. 模块规模失控：找出最大的 5 个文件/模块（行数），是否存在 God Object/God Module？
3. 抽象增殖：同一概念有几套抽象？（多个 base class 做同一件事、多个 registry 模式并存、多套元数据来源）
4. 接口设计质量：核心公共 API 的设计一致性（命名、错误处理、异步模式）；ABC/Protocol 的契约是否被实现者遵守？
5. 扩展点与插件机制：有没有清晰的扩展点？第三方/用户扩展是否可行？加新单元需要手改几处？
6. 错误处理策略：异常是吞掉还是传播？有没有统一错误处理层？静默失败（silent failure）有多少处？构建脚本失败是否 exit 非 0？

### 维度 ③ 数据管理

角色名：数据架构审查研究员

调查问题模板：
1. 存储清单：项目里有多少个独立的数据库/存储？（sqlite3、aiosqlite、.db 路径、向量库、PostgreSQL、JSON 持久化、registry/graph 等结构化数据文件）。每个存什么、归属哪个模块？
2. Schema 管理：有没有统一的 migration 机制？schema 变更如何追踪？有没有 schema_version / PRAGMA user_version？
3. 数据一致性：跨存储的数据有没有一致性保障？事务边界在哪？多处计数（如 registry vs 目录 vs 索引文档）是否一致？给出精确数字。
4. 备份与恢复：有没有备份机制？能否从备份恢复？加密状态如何？
5. 多租户/隔离：如果项目声称多租户，数据隔离在哪一层实现？是否可被绕过？
6. 数据生命周期：过期数据清理、容量增长控制、WAL/journal 管理。
7. 生成与手编冲突：生成数据是否被手编覆盖？.bak 文件暗示什么工作流？

### 维度 ④ 前端设计与交互

角色名：前端/产品设计审查研究员

调查问题模板：
1. 页面与路由盘点：有哪些页面/路由？每个页面功能是什么？哪些是真实实现的、哪些是占位（"coming soon"、空组件、TODO）？
2. 信息架构：导航结构是否清晰？用户能否直觉找到功能？有没有孤立页面（无导航入口）？
3. 设计系统一致性：有没有统一的 design tokens / 组件库？实际使用率多少？有没有大量 one-off 样式？
4. 状态管理：全局状态方案是什么？有没有 prop drilling / 状态不同步风险？
5. 国际化覆盖：i18n 覆盖率？有没有硬编码文案混在已翻译文案中？
6. 假控件与死交互：有没有看起来可点但无功能的按钮/链接/表单？
7. 响应式与可访问性：移动端适配状态；基础 a11y（键盘导航、aria 标签）覆盖。

### 维度 ⑤ 工程质量与安全

角色名：工程质量与安全审查研究员

调查问题模板：
1. 测试质量：测试组织结构；用例中有多少是真实断言 vs 快照/占位/stub pass？有没有大量 skip/xfail？是否过度 mock？关键路径的覆盖情况？`npm test`/`pytest` 当前是否真的绿？
2. CI 配置：workflow 是否真实阻断（检查 continue-on-error / `|| true`）？门禁是否有效？
3. 安全原语接线：加密/认证/授权模块的代码质量 vs 实际接线状态。有没有"实现了但从未被调用"的安全机制？输入校验是白名单还是黑名单（黑名单常可绕过）？
4. 认证与授权：auth 流程有没有绕过路径？token 验证是否完整？RBAC 是否可被 header 伪造绕过？
5. 密钥管理：secrets 存储方式、.env 处理、日志中是否泄漏敏感信息？install 脚本的环境变量注入向量分析。
6. 依赖安全：lock 文件审计（pip-audit / npm audit）；有没有 GPL 污染风险？
7. pre-commit / lint 门禁：ruff/mypy/eslint/shellcheck 是否真实执行且阻断？
8. 发布包卫生：`npm pack --dry-run` / `python -m build` 是否包含 .bak/缓存/敏感文件？

## 三、扩展 6 维 Prompt 模板

### 维度 ⑥ 前后端联动与契约

角色名：API 契约一致性审查研究员

1. 后端 API 全集：REST 路由全集（router 文件 + 挂载点）；WebSocket RPC 方法全集（注册表）。
2. 前端调用点全集：前端在哪些文件调用后端 API？用什么 client/方式？
3. 路径/方法名比对：前端调用的每个端点，后端是否真实存在且已挂载？有没有前端调了但后端没有的（404）？
4. 字段级比对：前端 TypeScript types vs 后端 pydantic models / response schema，逐字段对比关键实体。
5. 实时通路：WebSocket / SSE / 长轮询的连接、重连、心跳机制前后端是否对齐？
6. 版本兼容：API 有没有版本化？breaking change 如何通知前端？

### 维度 ⑦ 运行时启动与部署（主线执行，不派代理）

冒烟测试清单：
```bash
# 1. CLI 基本可用性
{cli_command} --version
{cli_command} --help
{cli_command} doctor  # 如果有

# 2. 服务启动
timeout 15 {start_command} &
sleep 5
curl -s http://127.0.0.1:{port}/health

# 3. 前端构建
cd {frontend_dir} && npm/pnpm run build

# 4. Docker（如果有）
docker build -t {name}-test .

# 5. 清理
kill %1
```

### 维度 ⑧ 性能与资源热点

1. 启动性能：初始化序列有多少阶段？哪些重量级 import 在启动时无条件加载？有没有懒加载？
2. 热路径低效：核心请求路径上有没有重复 IO（每次请求重读配置、重复建连接、重复编译正则）？
3. 无界内存增长：模块级缓存/字典有没有淘汰策略（LRU/TTL/maxsize）？有没有只 append 不清理的列表？
4. 并发与池化：HTTP client / DB 连接 / WebSocket 有没有池化和并发上限（Semaphore）？还是每次新建？
5. 大对象处理：大文件/大消息的处理方式（流式 vs 全量加载）；序列化/反序列化频率。
6. 前端性能：bundle size、代码分割、图片优化、不必要 re-render、列表虚拟化。

### 维度 ⑨ 可观测性与韧性

1. 日志体系：有没有统一 logging 配置（结构化？级别？rotation？）？敏感数据是否会进日志？
2. 指标与健康检查：有没有 /health /metrics 端点？有没有 Prometheus/OTel 集成？
3. 错误追踪：异常是否被记录且可追溯？有没有 Sentry 类集成？
4. 断线重连：外部连接（DB、消息平台、API）断开后的重连策略？有没有 backoff？
5. 崩溃恢复：进程崩溃后数据是否安全（WAL、事务）？有没有 graceful shutdown（signal handler、连接排空）？
6. 告警接线：有没有告警通道（webhook、email）？还是只有日志？

### 维度 ⑩ 打包发布与版本治理

1. 打包内容审计：sdist/wheel/npm pack 包含与排除规则——内部文档、测试、.env 模板是否会泄漏进发布包？
2. 版本同步：版本号在几处定义？有没有同步检查脚本？是否在 CI 强制？
3. Release 流水线：从 tag 到发布的全流程；有没有自动化 changelog？签名？
4. 分发渠道：PyPI/npm/Homebrew/Docker Hub 各渠道的发布状态与一致性。
5. 依赖锁定：发布包是否 pin 了依赖？用户安装时会不会拉到不兼容版本？

### 维度 ⑪ 合规与文档可用性

1. 隐私宣称 vs 实际：PRIVACY.md/隐私政策声称的数据处理 vs 代码中实际的数据流（有没有偷偷发外部请求？telemetry 是否可关闭？）
2. LICENSE 完整性：LICENSE 文件与代码头声明一致？NOTICE 文件的第三方归属完整？
3. GPL 污染：依赖树中有没有 GPL/AGPL 组件与项目 LICENSE 冲突？
4. Quickstart 照走：按 README 的 quickstart 步骤逐步走，每一步能否成功？卡在哪？链接是否 404？
5. 文档时效性：文档中的代码示例能否在当前版本运行？截图/版本号是否过期？中英文文档是否同步？

## 五、严重度定义速查

| 级别 | 定义 | 典型场景 |
|------|------|----------|
| P0 | 安全红线 / 数据丢失风险 | 认证绕过、注入、密钥泄漏、数据可被未授权访问 |
| P1 | 功能不可用 / 架构腐化 | 宣称功能实际不工作、循环依赖、核心路径断裂、测试红 |
| P2 | 技术债 / 可维护性 | 代码重复、缺测试、文档过期、命名混乱 |
| P3 | 优化建议 | 性能微优化、DX 改善、代码风格统一 |

## 六、成熟度评级速查

| 等级 | 含义 | 判定标准 |
|------|------|----------|
| A | 生产就绪 | 核心路径完整、有测试、有监控、可对外承诺 SLA |
| B | 功能完整 | 主流程可用，有已知但可控的技术债，不影响日常使用 |
| C | 骨架可用 | 关键路径有缺口，需要 workaround，不适合生产依赖 |
| D | 名义存在 | 代码存在但实际不可用/未接线/纯模拟，不应对用户暴露 |
