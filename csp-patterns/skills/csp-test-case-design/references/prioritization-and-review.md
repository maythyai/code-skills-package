# 优先级、裁剪与用例评审

## 1. P0 / P1 / P2 判定标准

按六个维度逐项对照，**取命中的最高级**（短板决定，不是打分求和）。任一维度落在 P0 列，该用例即为 P0。

| 维度 | P0 | P1 | P2 |
|---|---|---|---|
| **阻断主流程** | 用户无法完成核心任务（提交/支付/登录/审批） | 不阻断，但有明确功能损失 | 不阻断，仅体验或边缘路径受损 |
| **资损 / 数据丢失 / 数据错乱** | 会产生金额错误、重复扣减、数据丢失或静默写坏 | 可能产生脏数据，但可清理、可对账 | 无数据影响 |
| **安全 / 合规 / 权限越界** | 越权访问、数据泄露、审计缺失、隐私暴露 | 提示信息泄露内部细节（错误栈、内部ID） | 无 |
| **有无 workaround** | 无，用户只能放弃或联系客服 | 有，但成本高（重启 / 清缓存 / 换设备 / 手工补偿） | 有，且成本低（重试一次 / 换个写法） |
| **影响用户比例** | > 20%，或影响全部用户 | 5%–20% | < 5% |
| **能否被自动发现** | 否——静默失败、结果错但不报错 | 部分——有报错但错误码/文案不对 | 是——明确报错且用户能理解 |

### 判定示例

| 用例ID | 阻断主流程 | 资损/数据 | 安全合规 | workaround | 影响比例 | 可自动发现 | **判定** | 命中维度 |
|---|---|---|---|---|---|---|---|---|
| TC-FLOW-E2（连点提交 3 次） | 否 | **有**：重复工单 + 重复通知 | — | 无 | 5–20% | 否（静默重复） | **P0** | 资损 + 幂等 |
| TC-ST-ILL-07（CLOSED 被 reopen） | 否 | **有**：已关闭工单重开导致重复处理/重复计费 | — | 无 | <5% | 否 | **P0** | 资损（比例低不降级） |
| TC-EXP-04（无权限导出被拒） | 否 | — | **有**：数据泄露 | 无 | <5% | 否 | **P0** | 合规 |
| TC-TITLE-E1（标题缺失被拒） | 否 | 无 | 无 | 有（明确提示） | 100% | 是 | **P1** | 覆盖面广但可自恢复 |
| TC-DUE-E1（截止日 ≤ today 被拒） | 否 | 无 | 无 | 有 | 20–40% | 是 | **P1** | 校验分支 |
| TC-DUE-TZ-01（跨时区 today 判定） | 否 | 可能：截止日算错一天 | 无 | 有 | <5% | 否 | **P1** | 静默但有 workaround |
| TC-TITLE-CP-04（emoji 80 码点） | 否 | 无 | 无 | 有（改用普通字符） | <5% | 是 | **P2** | 边缘输入 |
| TC-TITLE-TRIM-01（首尾空格入库） | 否 | 无 | 无 | 有 | 10–20% | 是 | **P2** | 数据整洁度 |
| TC-FLOW-A7（成功后不跳转留在列表） | 否 | 无 | 无 | 有（手动刷新） | <5% | 是 | **P2** | 体验路径 |

**注意"影响用户比例 < 5% 但判 P0"**：TC-ST-ILL-07 与 TC-EXP-04 都触发频率极低，但资损/合规维度直接命中 P0。**频率不能稀释严重度**——这是优先级判定最常见的错误。

### 预算比例

| 优先级 | 占用例总数 | 自动化要求 | 执行时机 |
|---|---|---|---|
| P0 | 15%–25% | **100% 自动化** | 每次构建（冒烟集），失败即阻塞 |
| P1 | 45%–55% | 目标 ≥ 70% | 每日回归 / 每次合入主干 |
| P2 | 25%–35% | 可选 | 大版本回归 / 手工抽测 |

比例异常的解读：

- **P0 > 30%** → 判定过松。"什么都重要 = 什么都不重要"，冒烟集会膨胀到跑不完，最终没人跑。强制复审：把每条 P0 的"命中维度"写出来，写不出具体维度的降级。
- **P0 < 10%** → 要么判定过严，要么这个需求本身低风险（纯展示类改动）。若是后者，记录下来作为放行依据。
- **P2 > 45%** → 用例集里堆了大量低价值用例（通常是全组合未压缩、或等价类未合并）。先做合并压缩，再谈裁剪。

## 2. 时间不够时的裁剪顺序

**顺序是固定的。从第 1 步开始砍，砍够预算立刻停，不许跳步、不许凭感觉挑。**

| 步 | 砍什么 | 为什么它排在这里 | 必须留下的记录 |
|---|---|---|---|
| **1** | Pairwise 表的尾部行；全部 3-wise 加强行（**来源 = 历史缺陷的加强行除外**） | 组合覆盖的边际收益最低；单因子与双因子交互仍由前面的行保证 | 被砍的行号 + 因此失去覆盖的 pair 清单 |
| **2** | 1-switch 连续迁移用例（**保留全部 0-switch**） | 两步连击缺陷的概率显著低于单步迁移缺陷 | 被砍的迁移对列表 |
| **3** | 同一等价类内的冗余代表（一类只留 1 条） | 等价类的定义就是"类内任取一值等价"；多条只增加执行时间不增加覆盖 | 保留的代表用例ID + 被砍的同族用例ID |
| **4** | 判定表 don't-care 维度的抽样补充用例（`TC-EXP-01a` 这类） | 合并后的主规则用例已覆盖该规则；补充用例只防"实现偷偷依赖了被合并掉的条件" | 被放弃验证的 don't-care 维度 |
| **5** | 纯提示文案类用例（错误信息措辞、i18n 文本、空态引导语） | 文案错误不影响功能正确性，改动成本低、回归快 | 被砍的文案用例ID + 对应文案 key |
| **6** | P2 用例中的边界 in-point（**保留 on point 与 off point**） | in-point 与 on point 走同一代码分支，信息量重叠；off point 是唯一能验证比较运算符的那一刀 | 被砍的 in-point 用例ID |

**砍完第 6 步仍超预算 → 停止裁剪，改为分批执行**：本轮跑 P0 + P1，P2 顺延到下一轮，并在放行评审上把"P2 未执行"登记为**已知风险**（写明谁批准、何时补跑）。继续砍就会开始破坏覆盖。

### 绝不可砍的四类

| 类别 | 砍掉的后果 |
|---|---|
| 全部 P0 用例 | 资损 / 合规 / 数据丢失缺陷直接进入生产 |
| 每个无效等价类的代表用例 | 该无效分支覆盖率归零，且报告上看不出缺口 |
| 每条非法状态迁移用例 | 状态机可被非法事件打穿（CLOSED 被重开、已删除记录被修改） |
| 任一 AC 的最后一条用例 | 直接制造"未覆盖 AC"，把追溯校验从 PASS 打成 FAIL |

### 裁剪后的强制复检

```bash
# 1. 重跑双向追溯校验——裁剪最容易制造未覆盖 AC
bash docs/analysis/check-traceability.sh \
  docs/requirements/<feature>.md \
  docs/analysis/test-cases-<feature>.md
# 退出码必须为 0

# 2. 重算覆盖率指标，与裁剪前对比
#    等价类覆盖率 / 迁移覆盖率 / 非法迁移覆盖率 / pair 覆盖率 必须仍为 100%
#    （第 1、2 步砍的是"加强项"，不应影响这些基础指标；若下降了，说明砍错了）

# 3. 确认 P0 用例数未变
grep -cE '^\|[[:space:]]*TC-.*\|[[:space:]]*P0[[:space:]]*\|' docs/analysis/test-cases-<feature>.md
```

### 裁剪记录表模板

写到 `docs/analysis/case-pruning-<feature>.md`。**没有这张表，裁剪就等于偷偷降低质量标准。**

```markdown
# 用例裁剪记录：<feature>

| 项 | 值 |
|---|---|
| 裁剪前用例数 | 96（P0 18 / P1 51 / P2 27） |
| 目标用例数 | 72 |
| 裁剪后用例数 | 73（P0 18 / P1 48 / P2 7） |
| 批准人 | <角色>，<日期> |
| 追溯校验 | PASS（无未覆盖 AC、无孤儿用例） |

| 被砍用例ID | 原优先级 | 砍序步骤 | 原因 | 失去的覆盖 | 风险承担人 | 补测计划 |
|---|---|---|---|---|---|---|
| TC-COMB-11, TC-COMB-12 | P2 | 1 | pairwise 尾部行，pair 已由 1–10 行覆盖 | 无（pair 覆盖率仍 100%） | — | 不需补 |
| TC-COMB-H1 | P1 | **未砍** | 加强行来源 = 历史缺陷 #4821（低配+RTL+弱网首屏白屏） | — | — | 保留 |
| TC-ST-1S-08 … 1S-13 | P2 | 2 | 1-switch 非高风险迁移对 | 6 对连续迁移（RESOLVED→OPEN→…） | 测试负责人 | v2.1 回归补跑 |
| TC-TITLE-E2 | P1 | 3 | 与 TC-TITLE-E3（全空白）同属"trim 后为空"路径，保留 E3 | 空串 `""` 与全空白串 `"    "` 的区分 | 开发 | 若 trim 逻辑改动则立刻补回 |
| TC-EXP-01a | P2 | 4 | M1 规则 don't-care 维度抽样补充 | "实现是否偷偷依赖 C1/C2" 的验证 | 测试负责人 | 权限模块任何改动时补回 |
| TC-MSG-03 … 07 | P2 | 5 | 错误提示文案用例 | 5 条 i18n 文案 | 产品 | 文案变更后单独走查 |
| TC-TITLE-B2, TC-TITLE-B79 | P2 | 6 | 边界 in-point，与 on point 同分支 | 2 个 in-point | — | 不需补 |
```

第 3 步那行是最需要警惕的：`TC-TITLE-E2`（空串）与 `TC-TITLE-E3`（全空白）**是否真等价取决于实现顺序**。若代码是"先校验长度再 trim"，两者走不同分支，砍掉 E2 就是真丢覆盖。裁剪时必须打开实现确认，不能只看需求。

## 3. 用例评审清单

评审前把用例集与追溯矩阵发给全体参与人预读。会上按下面六块逐项过，任何一项不通过即记为待补。

### A. 可追溯性

- [ ] 每条用例的"关联AC"列非空，且不是 `-` / `TBD` / `N/A` / `无`
- [ ] 每条 AC 在正向追溯表中至少有 1 条用例
- [ ] 每条 P0 AC 同时具备正常 / 边界 / 异常三类用例
- [ ] 不存在"幽灵 AC"（用例引用了需求文档里没有的 AC 编号）
- [ ] 用例ID 唯一、稳定、非自增行号，删除的 ID 未被复用
- [ ] `check-traceability.sh` 退出码为 0

### B. 技术覆盖

- [ ] 每个有界输入维度都有 on point / off point / in point 三点
- [ ] 区间开闭已从需求原文判定（"晚于" = 开、"不超过" = 闭），on/off 点未错位
- [ ] 每个无效等价类都有独立用例，且该用例只含一个无效输入
- [ ] 长度/数值类用例已注明计量单位（码点 / 字节 / UTF-16 unit；元 / 分；秒 / 毫秒）
- [ ] 判定表已做规则合并，合并后规则数 < 原始 `2^n`
- [ ] 判定表中的 IMPOSSIBLE 规则**保留在表里**，附理由与证据来源，且有防御性用例
- [ ] 状态迁移 0-switch 覆盖率 = 100%（含守卫失败行）
- [ ] 非法迁移覆盖率 = 100%，未抽样；总数用 `状态数 × 事件数 − 合法迁移数` 核对
- [ ] 涉及金额 / 权限 / 对外通知的状态机做了 1-switch 覆盖
- [ ] Pairwise 表 pair 覆盖率 = 100%（生成后已验证，不是"应该没问题"）
- [ ] Pairwise 手工加强行标注了来源（历史缺陷编号 / 风险分析条目）
- [ ] 场景法三类流齐全：基本流 1 条 + 每个分叉点的备选流 + 每个失败点的异常流
- [ ] "回到基本流"的备选流有回归路径用例（覆盖回到点之后的全部剩余步骤）
- [ ] 有备选流叠加用例
- [ ] 涉及写操作的需求有并发用例与幂等用例
- [ ] 时间相关逻辑（超时、窗口期、定时任务、过期）有可控时钟方案

### C. 可执行性

- [ ] 前置条件可复现：账号与角色、feature flag、DB 初始数据、系统时区、当前时间锚点都写明
- [ ] 没有"某个已有工单""之前的数据"这类模糊前置
- [ ] 步骤有序，每步可独立执行，步骤内不含条件分支
- [ ] 依赖外部服务失败的用例写明了故障注入方式（mock / 断网 / 关停依赖 / 代理改包）
- [ ] 手工用例的执行时间估算已给出，总时长在排期内
- [ ] 自动化用例可单独运行（`pytest -k TC-XXX` / `go test -run 'TestX/TC-XXX'`）

### D. 断言质量

- [ ] 预期结果含具体可观察值：HTTP 状态码 + 业务错误码 + 返回字段值 + DB 行内容 + 界面精确文案
- [ ] 全文搜索不到"显示正常""不报错""成功""正确"这类不可判定表述
- [ ] 写操作用例断言了副作用（通知是否发出、审计是否写入、文件是否落盘、关联表行数）
- [ ] 非法路径用例断言了"状态不变 + 无副作用"（快照对比），不只是断言错误码
- [ ] 失败请求断言了"未产生脏数据"
- [ ] 列表/分页用例断言了返回条数与排序，不只是"有数据"

### E. 优先级与预算

- [ ] P0 占比在 15%–25% 区间；超出则每条 P0 都能指出命中的具体维度
- [ ] P0 用例 100% 有自动化计划
- [ ] 优先级不是按"测试者觉得重要"给的，而是按六维度判定的
- [ ] 若已裁剪，裁剪记录表存在，砍序步骤正确，四类绝不可砍用例完好

### F. 数据与环境

- [ ] 测试数据不依赖生产数据，不含真实个人信息（姓名 / 手机号 / 证件号一律用生成数据）
- [ ] 用例之间无执行顺序依赖，可乱序、可并行
- [ ] 每条用例执行后能自动清理，或明确写出残留内容与清理方式
- [ ] 多语言 / 多时区 / 多币种 / RTL 用例已标明环境要求
- [ ] 需要特定设备或系统版本的用例已标明设备矩阵行号（移动端见 `csp-mobile-device-testing`）

### 抽样规则与打回标准

| 项 | 规则 |
|---|---|
| 抽样比例 | 随机抽 **10%**，且**至少 8 条** |
| 强制包含 | 全部 P0 用例的 20%（向上取整）；**每种使用过的设计技术至少 1 条** |
| 打回标准 | 抽到的用例中 **≥2 条不合格** → 整个用例集打回重做，**不做逐条修补** |
| 有条件通过 | 恰好 1 条不合格 → 记为待补，48 小时内补齐并复核，不阻塞其他部分开工 |

逐条修补是个陷阱：抽样发现 2 条不合格，说明未抽到的 90% 里大概率有 10+ 条同类问题，逐条修补的成本高于重做。

### 评审会议流程

| 环节 | 时长 | 参与人 | 产出 |
|---|---|---|---|
| 会前预读 | 异步 | 全体 | 每人标注疑问点，会前提交 |
| 追溯矩阵走查 | 15 min | 需求方 + 测试 | 未覆盖 AC / 孤儿用例清单，当场定处置 |
| 抽样深读 | 30 min | 全体 | 按抽样规则逐字段过，判定合格/不合格 |
| 边界与非法路径专项 | 20 min | 开发 + 测试 | 开发指出"这个分支其实还有第三种情况"，补漏清单 |
| 优先级与预算确认 | 15 min | 产品 + 测试负责人 | 裁剪授权：谁批准砍哪些、风险由谁承担 |
| 结论 | 5 min | 全体 | 通过 / 有条件通过 / 打回，写入追溯报告 |

**开发必须参加"边界与非法路径专项"**。测试者从需求推边界，开发从实现推边界，两者不重合的部分就是缺陷藏身处——尤其是需求没写但实现里存在的隐式分支（例如"超过 100 条时走批量路径"）。

## 4. 常见评审驳回理由（Top 8）

| # | 驳回理由 | 出现频率 | 一次性修法 |
|---|---|---|---|
| 1 | 预期结果不可判定（"显示正常""提交成功"） | 高 | 用四件套重写：状态码 + 错误码 + 字段值 + 精确文案；再加副作用断言 |
| 2 | 一条用例含多个无效输入 | 高 | 按无效等价类拆开，其余维度全部取有效值 |
| 3 | 缺 off point（只测了 min/max 本身） | 中高 | 把边界矩阵逐格过一遍，空格必须填理由 |
| 4 | 非法迁移只抽样测了几条 | 中 | 用 `状态数 × 事件数 − 合法迁移数` 算总数，全枚举——每条断言成本只有三行代码 |
| 5 | 用例ID 不稳定（自增行号 / 中文标题当 ID） | 中 | 改为 `TC-<模块>-<序号>`，只追加不复用 |
| 6 | 前置条件写"无" | 中 | 逼问六项：账号？角色？flag？时区？当前时间？已有数据？ |
| 7 | 表驱动里塞 lambda / 闭包断言 | 低中 | 断言上移到函数体唯一一处，表只留值；差异用枚举字符串表达 |
| 8 | Pairwise 表未验证 pair 覆盖率 | 低 | 生成后必须跑覆盖校验，100% 才算表；加过约束的要重新验证 |

驳回理由 1 和 2 合计占绝大多数返工量。它们都源于同一个习惯：**先写代码再补用例文档**。顺序反过来（先表后码）能一次性消除这两类问题。
