## 5. 因果图（Cause-Effect Graphing）

### 适用场景

- 条件之间存在**互斥、依赖、唯一、至少一个**这类约束，直接建判定表会产生大量现实不可达的规则。
- 一个原因组合会同时触发多个结果（输出 + 副作用）。
- 需求文本是"如果…并且…或者…则…；但若…则不允许…"这种带连接词的复合句。

条件 ≤3 且相互独立 → 跳过因果图，直接建判定表（更快）。条件 ≥4 且有约束 → 先画因果图。

### 逻辑符号与约束符号

| 符号 | 名称 | 含义 |
|---|---|---|
| `→` | 恒等 | c 为真 ⇒ e 为真 |
| `¬` | 非 | c 为假 ⇒ e 为真 |
| `∨` | 或 | c1 ∨ c2 ∨ c3 ⇒ e |
| `∧` | 与 | c1 ∧ c2 ⇒ e |
| **E** | Exclusive 互斥 | 约束的原因中**至多一个**为真 |
| **I** | Inclusive 包含 | 约束的原因中**至少一个**为真 |
| **O** | One and only one 唯一 | 约束的原因中**恰好一个**为真 |
| **R** | Requires 要求 | a 为真 ⇒ b 必须为真（a 依赖 b） |
| **M** | Mask 屏蔽 | 该原因在任何场景下都不出现，直接从表里删掉 |

约束标在**原因之间**，不是标在结果之间。结果之间的互斥（例如"拦截"与"返回列表"不能同时发生）属于动作桩的一致性检查，在判定表阶段验证。

### 构造步骤

1. **拆句**：把需求文本按分句切成"原因"（输入值、前置条件、上下文）与"结果"（输出、状态变化、副作用），分别编号 `C1..Cn` / `E1..Em`。**副作用（写日志、发通知、扣库存）必须列为独立结果**，否则永远不会被断言。
2. **抽中间节点**：多个结果共享的条件组合抽成 `M1..Mk`，避免图退化成完全二部图。
3. **连边标逻辑符**：原因 → 中间节点 → 结果，每条边标 `→ / ¬ / ∨ / ∧`。
4. **在原因之间标约束**：逐对检查是否有 E/I/O/R/M。**漏标约束是因果图的主要失效模式**——它会让判定表里混进不可达规则，然后测试者按不可达规则写用例，最后发现根本构造不出来。
5. **转判定表**：每条从原因集到结果集的可执行路径成为一列。用约束删除不可达列，并在被删列上标 `IMPOSSIBLE` + 引用的约束编号。
6. **可构造性验证**：每条留下的规则都要能在真实系统里构造出来。构造不出来的规则 = 约束标错了，回到第 4 步。

### 填好的示例：工单搜索筛选

需求原文：

> 用户在搜索页可以输入关键词、选择分类筛选。若关键词命中违禁词库，系统拦截本次搜索并提示违规，不返回任何结果。访客（未登录）执行关键词搜索时要求先登录，但按分类浏览无需登录。所有搜索与拦截行为都写入行为日志。无任何输入条件时展示空态与推荐引导。

**原因 / 中间节点 / 结果编号**

| 编号 | 内容 | 类型 |
|---|---|---|
| C1 | 提供了搜索关键词 | 原因 |
| C2 | 关键词命中违禁词库 | 原因 |
| C3 | 选择了分类筛选 | 原因 |
| C4 | 当前用户为访客（未登录） | 原因 |
| M1 | 触发合规拦截 = `C1 ∧ C2` | 中间 |
| M2 | 需要执行检索 = `C1 ∨ C3` | 中间 |
| M3 | 需要登录 = `C1 ∧ C4 ∧ ¬C2` | 中间 |
| E1 | 返回结果列表 | 结果 |
| E2 | 返回空态 + 推荐引导 | 结果 |
| E3 | 合规拦截，提示违规 | 结果 |
| E4 | 写行为日志 | 结果（副作用） |
| E5 | 要求登录后继续 | 结果 |

**约束**

| 约束 | 涉及 | 类型 | 理由 |
|---|---|---|---|
| X1 | C1, C2 | **R**（C2 ⇒ C1） | 违禁词判定只在有关键词时发生；`C1=N ∧ C2=Y` 不可达 |
| X2 | E1, E2, E3 | 结果互斥 | 三者不能同时为真；E4 可与任意一个共存 |
| X3 | C3, C4 | 无约束 | 访客可以按分类浏览 |

**因果图（文本表示）**

```

    │                 ↑
C3 ─┴─────────────────┘
C1 ──∧── C2 ──→ M1 ──→ E3
C1 ──∧── C4 ──∧── ¬C2 ──→ M3 ──→ E5
(M1 ∨ M2 ∨ M3 ∨ 任意) ──→ E4          # E4 无条件触发
¬M2 ──→ E2                              # 无检索需求 → 空态
约束: C2 ──R──> C1
```

### "结果为空"是数据依赖，不是条件依赖

`E1 返回结果列表` 与 `E2 返回空态` 在 M3/M4 下都可能发生——取决于**库里有没有匹配数据**，而不是取决于 C1–C4。因果图表达不了这种依赖。处理方式：在 M3、M4 下各按数据等价类再拆两条：

| 用例ID | 规则 | 数据前置 | 预期 |
|---|---|---|---|
| TC-SRCH-03a | M3 | 库中存在 ≥1 条匹配工单 | E1，列表长度 = 匹配数 |
| TC-SRCH-03b | M3 | 库中无匹配工单 | E1 且 `items == []`，展示"无匹配结果"文案（**不是** E2 的推荐引导） |
| TC-SRCH-04a | M4 | 该分类下有工单 | E1 |
| TC-SRCH-04b | M4 | 该分类下无工单 | E1 且 `items == []` |

区分"无结果"（E1 空列表）与"未搜索"（E2 空态引导）是这类需求最常见的实现缺陷。

### 常见漏测点

| 漏测点 | 后果 |
|---|---|
| 副作用没列为独立结果 | E4 行为日志从不被断言，合规审计缺失到上线才发现 |
| 约束漏标 R | 生成 4 条不可达用例，执行时构造不出来，测试者私自跳过 → 判定表可信度崩塌 |
| 约束过度标注 | 把实际可达的组合标成 IMPOSSIBLE，等于主动放弃一块覆盖 |
| 结果互斥未校验 | E1 与 E3 同时为真的实现缺陷（返回了列表又提示违规）无人发现 |
| 忽略"数据依赖"维度 | 只测有数据的情况，空结果分支零覆盖 |
| 中间节点抽太多 | 图不可读，评审时没人能验证逻辑等价性；中间节点控制在 3–5 个 |

## 6. Pairwise / 正交实验（Combinatorial Testing）

### 为什么全组合会爆炸

| 因子集 | 水平数 | 全组合 | 单条 15 分钟手工执行的总耗时 |
|---|---|---|---|
| 浏览器 3 × OS 3 × 主题 2 × 网络 2 | 3,3,2,2 | **36** | 9 小时 |
| OS版本 3 × 密度 3 × 内存 3 × 语言 3 × 主题 2 × 网络 2 | 3,3,3,3,2,2 | **324** | 81 小时 |
| 真实设备矩阵：OS 6 × 分辨率 5 × 内存档 4 × 语言 3 × ROM 5 | 6,5,4,3,5 | **1800** | 450 小时 |

全组合的增长是**乘法**的，加一个 3 水平因子就把用例数 ×3。这不是"多花点时间"的问题，是根本不可能执行的问题。

### 为什么 pairwise 能覆盖大多数交互缺陷

- 单因子缺陷（某个水平本身就坏）：pairwise **100% 覆盖**，因为每个水平都至少出现一次。
- 双因子交互缺陷（只在 `深色主题 + RTL 语言` 同时出现时坏）：pairwise **100% 覆盖**，这是它的定义保证。
- 三因子及以上交互缺陷：pairwise **不保证**。

业界长期经验是绝大多数交互型缺陷由 1 阶或 2 阶交互触发，常见引用区间在 **70%–95%**。**这是经验值，不是定理**，直接搬到你的项目上是不负责的。正确做法是用自己的历史缺陷数据校准：

```
校准步骤（一次性，约半天）
1. 取最近 100 个已定位的线上/测试缺陷
2. 对每个缺陷标注：复现它需要同时固定几个因子？（1 阶 / 2 阶 / 3 阶 / 更高）
3. 统计分布
4. 若 3 阶占比 ≤ 10%  → 全量 pairwise（2-wise）足够
   若 3 阶占比 10–20% → pairwise + 对高风险因子组做定向 3-wise 加强（加 3–8 条）
   若 3 阶占比 > 20%  → 说明因子之间存在结构性耦合，应重新划分因子（合并成一个复合因子）
                        而不是盲目上 3-wise
5. 把统计结果写进 docs/analysis/combinatorial-strategy.md，作为下一轮裁剪的依据
```

第 4 步最后一条最重要：**3 阶缺陷多通常意味着因子建模错了**。例如 `OS版本` 与 `ROM` 与 `芯片档位` 高度相关，把它们当三个独立因子会生成大量无意义组合；合并成一个"设备档位"因子（低端/中端/旗舰，各带确定的 OS+ROM+芯片）后，因子数从 3 降到 1，用例数骤减且覆盖更真实。

### 构造步骤

1. **列因子与水平**：每个因子必须是被测系统的真实自由度。写不出"这个水平坏了会怎样"的因子，删掉。
2. **先做因子归约**：合并强相关因子（见上）；删除不存在的组合（`Safari × Android`）——不存在的组合不要靠约束排除，直接从因子定义里剔除或合并因子。
3. **生成 pairwise 集**：≤4 个因子可手工贪心；≥5 个因子用工具（见下）。
4. **加约束**：业务上禁止的组合用工具的条件语法排除，排除后**重新检查 pair 覆盖率**——约束会静默吃掉某些 pair。
5. **手工加回高风险组合**：从缺陷库/风险清单里挑 2–5 条必须出现的完整组合，用工具的 seed/强制行功能钉进去，并在表里标注"手工加强：来源 = 缺陷 #NNNN"。
6. **验证覆盖率**：pair 覆盖必须 100%，否则表是错的。
7. **每行落到一个真实执行路径**：pairwise 行不是用例，它是一组**环境参数**。必须把它塞进一个具体的场景（基本流）里执行，见 `#7 场景法`。

### 工具与命令

**PICT**（微软开源，支持约束与加权，输出最紧凑）

模型文件 `docs/analysis/pairwise-model.txt`：

```
OS:      A10, A12, A14
Density: xhdpi, xxhdpi, xxxhdpi
RAM:     3GB, 6GB, 12GB
Lang:    zh-CN, en-US, ar-SA
Theme:   Light, Dark
Net:     WiFi, Weak4G

# 约束：A10 设备不存在 12GB 内存档
if [OS] = "A10" then [RAM] <> "12GB";
# 强制行：历史缺陷加强
if [Lang] = "ar-SA" and [Theme] = "Dark" then [RAM] in {"3GB","6GB","12GB"};
```

```bash
pict docs/analysis/pairwise-model.txt /o:2 > docs/analysis/pairwise-2wise.tsv   # 2-wise
pict docs/analysis/pairwise-model.txt /o:3 > docs/analysis/pairwise-3wise.tsv   # 3-wise（行数会显著增加）
```

**正交表（Orthogonal Array）**：`L9(3^4)`、`L18(2^1×3^7)`、`L27(3^13)` 等。正交表比 pairwise 更强——它不仅覆盖所有 pair，还**均衡**覆盖（每对组合出现次数相同），因此对高阶交互有部分覆盖能力。代价是要求水平数规整（`L9` 只支持 4 个 3 水平因子）。混合水平时用 mixed-level OA，或直接用 pairwise 工具并接受其弱一点的高阶覆盖。

### 常见漏测点

| 漏测点 | 后果 |
|---|---|
| 因子建模错误（强相关因子当独立因子） | 生成大量不存在的组合，靠约束排除后 pair 覆盖率下降，且 3 阶缺陷率升高 |
| 生成完不验证 pair 覆盖率 | 手写/半自动生成的表常漏 5–15 个 pair，且没人知道漏了哪几个 |
| 加了约束不重跑覆盖检查 | 约束静默吃掉 pair，覆盖率从 100% 掉到 85% 而无告警 |
| pairwise 行当成用例直接执行 | 一行只有环境参数没有操作路径，执行者不知道要点什么；必须绑定到一个具体场景 |
| 不做手工加强 | 已知的高危 3 因子组合（缺陷库里有记录）恰好不在 pairwise 表里 |
| 因子水平数失衡时不做加权 | 主流机型（占比 40%）和边缘机型在表里各出现相同次数，投入产出比失衡；PICT 的 `[weight]` 语法可修正 |
| 每次回归都重跑全部 pairwise 行 | pairwise 是**设计期**工具；日常冒烟只跑 H2 基线行 + 变更影响的因子，全表留给大版本回归 |

## 7. 场景法 / 用户流程（Scenario / Use-Case Flow）

### 适用场景

需求以流程叙事写（"用户可以…然后…如果…则…"）、跨多个页面/服务、涉及多角色协作、有事务性副作用（下单、支付、审批、退款、同步）。

场景法是**骨架技术**：它决定用例的执行路径，其他六种技术决定路径上每一步的输入取值。两者是正交的——先有场景，再把等价类/边界值/判定表填进场景的每一步。

### 三种流

| 流类型 | 定义 | 用例数规则 |
|---|---|---|
| **基本流**（Basic / 主成功场景） | 一切顺利时从起点到目标的路径，无分支无失败 | 恰好 1 条，且必须是可独立执行的最短完整路径 |
| **备选流**（Alternative） | 从基本流某步分叉，走一条**合法的**不同路径，可能回到基本流或直接结束 | 每个分叉点至少 1 条；分叉点数量 = 基本流步骤中"用户可以选别的"的位置数 |
| **异常流**（Exception） | 从基本流某步分叉，因**失败/错误/外部故障**离开正常路径 | 每个可能的失败点至少 1 条 |

### 构造步骤

1. **写基本流**：编号 1..n，每步一个动作，不含条件判断。写完检查：能否照着一步步手工执行？不能就是粒度错了。
2. **逐步扫描找分叉点**：对每一步问三个问题——"用户可以不做这步吗？"（备选流）、"这步可能失败吗？"（异常流）、"这步可以被中断吗？"（异常流）。
3. **给每个分叉写流**：标注分叉点步号、触发条件、流内步骤、结束方式（`结束` 或 `回到基本流第 k 步`）。
4. **补回归路径用例**：每个"回到基本流"的备选流，额外一条覆盖 `回到点 → 基本流末尾` 的**全部剩余步骤**。这条最容易被漏，因为设计者认为"回到主流程后就跟基本流一样了"——实际上回到后的状态已经变了（草稿已存在、附件已上传、幂等键已消耗）。
5. **补叠加用例**：2–3 个备选流在同一次执行中同时出现的组合（例如"不上传附件 + 切换为 P0 + 校验失败后修改再提交"）。
6. **异常流必测状态残留**：每条异常流的断言里必须包含"中断点的状态"检查（见下表）。

### 填好的示例：工单提交流程

**基本流 B1**

| 步 | 动作 |
|---|---|
| 1 | 用户进入"新建工单"页 |
| 2 | 填写标题 |
| 3 | 选择优先级 |
| 4 | 选择截止日期 |
| 5 | 上传附件 |
| 6 | 点击提交 |
| 7 | 系统校验通过，创建工单，状态 = OPEN |
| 8 | 系统通知受理组 |
| 9 | 用户看到成功提示并跳转到工单详情页 |

**备选流**

| 流ID | 分叉点 | 触发条件 | 步骤 | 结束方式 | 断言重点 | 用例ID |
|---|---|---|---|---|---|---|
| A1 | 2 之后 | 用户点"存草稿" | 保存 → 状态 = DRAFT | 结束 | 草稿可在列表中找到；再次打开时字段值完整保留 | TC-FLOW-A1 |
| A2 | 5 | 用户不上传附件 | 跳过步骤 5 | 回到 6 | 工单创建成功；`attachments == []`；详情页不显示附件区块（不是显示空区块） | TC-FLOW-A2 |
| A3 | 5 | 用户删除已上传的附件 | 删除 → 附件存储被释放 | 回到 6 | 工单创建成功；**对象存储里该附件已被删除或标记孤立**，不产生存储泄漏 | TC-FLOW-A3 |
| A4 | 6 之后 | 校验失败，展示字段级错误 | 用户修改 → 重新提交 | 回到 6 | 错误定位到具体字段；修改后提交成功；**只创建 1 条工单**，不产生第一次失败的残留 | TC-FLOW-A4 |
| A5 | 7 之后 | 提交人立即撤回 | 撤回 → 状态回 DRAFT | 结束 | 受理组通知被撤回或标记失效；撤回操作写审计 | TC-FLOW-A5 |
| A6 | 3 | 用户把优先级改为 P0 | 触发加急通道 | 回到 4 | 加急标记落库；受理组收到的是加急通知模板（与普通模板不同） | TC-FLOW-A6 |
| A7 | 9 | 用户不跳转，留在列表页 | 关闭成功提示 | 结束 | 列表页已包含新工单（无缓存导致的延迟）；刷新后仍在 | TC-FLOW-A7 |

**异常流**

| 流ID | 分叉点 | 故障 | 预期 | **状态残留断言** | 用例ID |
|---|---|---|---|---|---|
| E1 | 6 | 提交请求超时 | 提示"提交失败，请重试"；不自动重试或最多重试 1 次 | DB 中**不存在**半成品工单；附件未孤立；幂等键**未被消耗**（重试可成功） | TC-FLOW-E1 |
| E2 | 6 | 用户连点提交 3 次（间隔 < 200ms） | 只创建 1 条工单 | 后续两次返回同一工单ID 或 `409 DUPLICATE`；受理组只收到 1 条通知 | TC-FLOW-E2 |
| E3 | 5 | 某附件超过大小上限（例如 > 20MB） | 拒绝该文件并提示；其余文件保留 | 已成功上传的文件状态不变；表单其他字段不被清空 | TC-FLOW-E3 |
| E4 | 8 | 通知服务不可用（503） | 工单创建**仍然成功**（通知非关键路径） | 通知进入重试队列；队列条目带工单ID；通知服务恢复后补发且**只补发一次** | TC-FLOW-E4 |
| E5 | 2–6 任意步 | 会话过期 | 跳转登录；登录后回到表单 | 已填字段值完整保留（含未上传的附件选择被清空时要有明确提示）；不静默丢失用户输入 | TC-FLOW-E5 |
| E6 | 7 | DB 写入失败（唯一约束冲突 / 连接断开） | 返回 `500`，事务回滚 | 无孤立附件、无孤立通知、无孤立审计行；重试可成功 | TC-FLOW-E6 |
| E7 | 6 | 同一用户在两个标签页同时提交 | 一条成功，一条冲突或被幂等去重 | 最终 DB 中恰好 1 条工单；不出现 2 条通知 | TC-FLOW-E7 |

**回归路径用例（第 4 步产物）**

| 用例ID | 覆盖链 | 为什么必须单独测 |
|---|---|---|
| TC-FLOW-R1 | A4（校验失败修改）→ 6 → 7 → 8 → 9 全链 | 第一次失败可能已消耗幂等键 / 已上传附件 / 已写草稿；重新提交走的是**不同状态**下的同一段代码 |
| TC-FLOW-R2 | A1（存草稿）→ 从草稿重新打开 → 2..9 全链 | 从草稿提交时 `submit` 的起点状态是 DRAFT 而非新建，状态机迁移路径不同（T3→T1） |
| TC-FLOW-R3 | A6（改 P0）→ 4 → 5 → 6 → 7 → 8 → 9 | 加急通道改变了步骤 8 的通知模板与路由，必须验证后续步骤未被加急标记污染 |

**叠加用例（第 5 步产物）**

| 用例ID | 组合 | 断言 |
|---|---|---|
| TC-FLOW-S1 | A2 + A6 + A4 | 无附件 + P0 加急 + 首次校验失败后修改重提 → 最终工单：`attachments==[]`、`priority==P0`、`urgent==true`、状态 OPEN、恰好 1 条加急通知 |
| TC-FLOW-S2 | A3 + E1 | 删除附件后提交超时 → 附件已释放且**不可恢复**；重试提交时不因附件缺失而 500 |

**用例总数**：基本流 1 + 备选流 7 + 异常流 7 + 回归路径 3 + 叠加 2 = **20 条**。

### 与其他技术的组合方式

场景法给出 20 条执行路径，但路径上每一步的**输入取值**还没定。用 §1 的等价类表填充步骤 2/3/4：

| 场景用例 | 步骤 2 标题取值 | 步骤 3 优先级取值 | 步骤 4 截止日期取值 |
|---|---|---|---|
| TC-FLOW-B1（基本流） | V-T1 典型值（40 码点） | V-P1 = `P1` | V-D1 = `today+180` |
| TC-FLOW-A4（校验失败后修改） | 首次 E-T4（81 码点）→ 修改为 V-T1 | V-P2（缺省） | V-D1 |
| TC-FLOW-E2（连点 3 次） | V-T1 | V-P1 = `P0` | E-D1（`today`）→ 首次即校验失败，验证连点不产生脏数据 |

规则：**场景用例只用有效类取值**（除专门测校验失败的），无效类的穷举交给等价类/边界值用例集，那些用例通常是接口级而非流程级，成本低一个数量级。

### 常见漏测点

| 漏测点 | 后果 |
|---|---|
| 只写基本流 | 备选流与异常流才是线上事故高发区；基本流是最不容易坏的部分 |
| 备选流只测分叉本身，不测分叉后的剩余路径 | "回到主流程"之后的状态已变，回归路径缺陷（TC-FLOW-R1/R2/R3）全部逃逸 |
| 异常流不断言状态残留 | "返回了 500"通过，但 DB 里留了半条工单 + 孤立附件 + 已发通知 |
| 中断点只选一个 | E5（会话过期）在步骤 2 和步骤 6 发生的后果完全不同（有无已上传附件）；至少测首、中、末三个中断点 |
| 忽略并发异常流 | E7 这类"两个 actor 同时"的场景在单人手工测试里永远走不到 |
| 场景步骤里塞了条件判断 | "如果校验通过则…否则…"不是步骤，是两条流；混写会让用例不可执行 |
| 把场景用例和输入穷举混在一起 | 20 条场景 × 17 条等价类 = 340 条，执行不动；正确做法是分层（场景走有效值，输入穷举走接口层） |
