# 黑盒用例设计技术 I：等价类 / 边界值 / 判定表 / 状态迁移

四种技术的完整构造步骤与填好的示例。统一使用同一个被测需求，方便对照。

## 贯穿全文的示例需求（工单系统 · 新建工单）

> **AC-01** 标题必填，长度 1–80（按 Unicode 码点计），首尾空白自动去除后再校验。
> **AC-02** 优先级取值必须为 `P0` / `P1` / `P2`；未提供时默认 `P2`。
> **AC-03** 截止日期选填；若提供，必须晚于今天且不晚于今天 + 365 天。
> **AC-04** 导出权限：管理员可导出全部字段；所有者或同团队成员可导出脱敏字段；其余拒绝。所有尝试写审计日志。
> **AC-05** 工单状态机：DRAFT → OPEN → IN_PROGRESS → RESOLVED → CLOSED，RESOLVED 可在 14 天内由提交人 reopen 回 OPEN。

## 1. 等价类划分（Equivalence Partitioning）

### 适用场景

- 输入域大但可归类：字符串、数值、枚举、日期、文件、集合。
- 需要快速把"无穷输入"压成"有限条用例"，作为其他技术的第一道工序。
- 表单校验、API 入参校验、解析器、配置加载。

不适用：输入之间存在强耦合（一个输入的合法取值依赖另一个输入）——那时等价类会漏，要上判定表或因果图。

### 构造步骤

1. **列全输入维度**，包括隐式输入：path 参数、query、header、body、cookie、上下文时间（"今天"）、当前用户角色、feature flag、系统语言/时区。漏掉隐式维度是等价类失效的第一大原因。
2. **按"处理逻辑是否相同"划类**：同一类中任取一个值，代码走同一条路径。划分依据是实现分支，不是值的语义相似度。
3. **分标 V-（有效）与 E-（无效）**。无效类必须按**失败原因**细分——"非法标题"不是一个类，"为空""超长""类型错""含控制字符"是四个类。
4. **有效类尽量合并**：一条用例覆盖尽可能多的有效类（多域联合有效）。
5. **无效类一类一条**：该维度取无效值，其余全部维度取有效值。
6. **编号入表**，用例标题必须带等价类编号，便于反查。
7. **交叉校验**：每个 `E-` 编号在用例集中出现恰好一次（除非需求明确要求聚合校验，见下）。

### 填好的等价类表

| 输入维度 | 有效等价类 | 编号 | 无效等价类 | 编号 |
|---|---|---|---|---|
| 标题 | 1–80 码点的非空白文本 | V-T1 | 字段缺失 / `null` | E-T1 |
| | | | 空串 `""` | E-T2 |
| | | | 全空白串（trim 后为空，如 `"    "`） | E-T3 |
| | | | 81 码点及以上 | E-T4 |
| | | | 非字符串类型（数字 / 对象 / 数组） | E-T5 |
| | | | 含控制字符 `\u0000`–`\u001F` | E-T6 |
| 优先级 | `P0` / `P1` / `P2` 之一 | V-P1 | 空串 `""` | E-P1 |
| | 字段缺失（走默认 `P2`，属有效路径） | V-P2 | 大小写不符 `p0` / `P 0` | E-P2 |
| | | | 枚举外取值 `P3` / `URGENT` | E-P3 |
| | | | 非字符串 `0` / `1` / `true` | E-P4 |
| 截止日期 | `today+1` … `today+365` | V-D1 | 早于或等于 `today` | E-D1 |
| | 字段缺失（不设截止，属有效路径） | V-D2 | 晚于 `today+365` | E-D2 |
| | | | 日历上不存在的日期 `2026-02-30` | E-D3 |

**用例数计算**：有效类 5 个（V-T1, V-P1, V-P2, V-D1, V-D2）→ 合并成 2 条（一条"全提供且有效"覆盖 V-T1+V-P1+V-D1；一条"最小必填"覆盖 V-T1+V-P2+V-D2）。无效类 15 个 → 15 条。**合计 17 条。**

### 为什么每个无效等价类必须单独一条用例

不是洁癖，是三个可验证的技术后果：

| 后果 | 机制 |
|---|---|
| **覆盖假象** | 校验器通常顺序执行、首个失败即 `return 400`。一条同时含 E-T1（标题空）与 E-D1（截止日过期）的用例，只有标题校验分支被执行；截止日期校验分支的代码覆盖率为 **0**，但报告上显示"该用例已通过"。 |
| **错误码断言被稀释** | 预期结果只能写"返回 400"，无法断言 `error_code` 是 `TITLE_REQUIRED` 还是 `DUE_DATE_INVALID`。"错误码写反""错误信息串台"这类缺陷直接逃逸。 |
| **回归失效** | 修完标题校验后这条用例变绿，之后截止日期校验被改坏，没有任何用例会红。 |

**唯一例外**：需求明确要求"一次返回全部字段错误"（表单聚合校验）。此时另建一类用例，且预期结果必须**逐字段列出**全部错误码，例如 `errors == ["TITLE_REQUIRED", "DUE_DATE_PAST"]`（顺序也要断言，否则前端展示顺序会漂）。这类用例是**补充**，不能替代单无效类用例。

### 常见漏测点

| 漏测点 | 说明 |
|---|---|
| 隐式维度没进表 | "今天"依赖服务器时区；同一份请求在 UTC+8 与 UTC−5 下 AC-03 判定结果不同 |
| 有效类被当成无效类 | "字段缺失走默认值"（V-P2 / V-D2）常被误归为无效，导致默认值逻辑零覆盖 |
| 无效类粒度太粗 | 只写"非法标题"一条，把 E-T1…E-T6 六条合并 → 五类分支零覆盖 |
| 前后端双重校验只测一层 | 前端拦掉的值后端可能从未被验证；必须能绕过前端直接打 API |
| 空白与空串混淆 | `""` 与 `"   "` 在"先 trim 再校验"的实现下是同一条路径，但在"先校验长度再 trim"的实现下是两条 |
| 幂等/重复提交没归类 | "同一请求提交两次"是一个独立等价类，不属于任何输入维度 |

## 2. 边界值分析（Boundary Value Analysis）

### 适用场景

任何带范围的输入：长度、数值、日期、数量、金额、页码、分页大小、超时时间、数组长度、文件体积、重试次数。等价类划完之后，对**每个有界的等价类**再跑一遍边界值。

### on / off / by-1 三点法

对每个边界，取三个点，不是两个：

| 点 | 定义 | 闭区间 `[min, max]` | 开区间 `(min, max)` |
|---|---|---|---|
| **on point**（边界点） | 恰好落在边界上 | `min` 与 `max` | 最接近边界的**合法**值：`min+1` 与 `max` |
| **off point**（越界点） | 刚好越界的最近不合法值 | `min−1` 与 `max+1` | `min` 与 `max+1` |
| **in point**（内侧点，by-1） | 边界内侧邻近值 | `min+1` 与 `max−1` | `min+2` 与 `max−1` |

**开闭区间搞错是边界值的第一杀手。** AC-03 写的是"晚于今天"（开区间）+ "不晚于 today+365"（闭区间），所以：
- on point = `today+1`（不是 `today`）
- off point = `today`（不是 `today−1`）
- 另一端 on point = `today+365`，off point = `today+366`

如果实现写成 `>= today`，`today` 这条 off point 用例会立刻变红——这正是它的价值。

### 构造步骤

1. 从等价类表里挑出所有**有界**维度。
2. 对每个维度，从需求原文判断区间开闭（"晚于"=开、"不超过"=闭、"至少"=闭、"小于"=开）。
3. 按三点法生成 6 个边界点，再加 1 个典型值（区间中点附近）。
4. 加维度特有的退化值：`null`、空集合、类型错、单位错（元/分、秒/毫秒、字符/字节/码点）。
5. 填边界矩阵，逐格判定"这条要不要写"，不写的格子写明理由。
6. 边界用例之间**不合并**——每个边界点独立一条，理由同无效等价类。

### 填好的边界矩阵

| 输入维度 | 约束（开闭） | off(min) | on(min) | in(min+1) | 典型 | in(max−1) | on(max) | off(max+1) | null | 空 | 类型错 | 用例数 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 标题长度（码点） | `[1, 80]` 闭 | `0` → 拒 | `1` → 收 | `2` → 收 | `40` → 收 | `79` → 收 | `80` → 收 | `81` → 拒 | 拒 | `""` 拒 | 非串 拒 | 9 |
| 截止日期（相对天） | `(today, today+365]` | `today` → 拒 | `today+1` → 收 | `today+2` → 收 | `today+180` | `today+364` → 收 | `today+365` → 收 | `today+366` → 拒 | 收（选填） | — | 非日期 拒 | 8 |
| 优先级枚举 | 有序枚举 | — | `P0` | `P1` | `P2` | — | — | `P3` → 拒 | 收（默认P2） | `""` 拒 | 非串 拒 | 6 |
| 分页 `page` | `[1, 总页数]` | `0` → 拒 | `1` → 收 | `2` → 收 | 中页 | `N−1` | `N` → 收空列表 | `N+1` → 收空列表 or 拒（需求须明确） | 拒 | — | 负数/浮点 拒 | 8 |

> `min−1` 那格在开区间下是 `min`，所以"off(min)"列对截止日期填的是 `today`。**表格列头必须跟着区间开闭走，不要机械填 min−1。**

### 特殊边界：trim 与码点

AC-01 有"首尾空白自动去除后再校验"，这产生两条极易漏的边界：

| 用例 | 输入 | trim 后 | 期望 |
|---|---|---|---|
| TC-TITLE-TRIM-01 | `"    服务器无法登录    "`（前后各 4 空格，内容 6 码点） | `"服务器无法登录"`（6 码点） | 收，且入库值不含首尾空格 |
| TC-TITLE-TRIM-02 | `"        "`（8 个空格） | `""`（0 码点） | 拒，`TITLE_REQUIRED` |
| TC-TITLE-TRIM-03 | 79 个 ASCII + 1 个 emoji `🙂`（80 码点 / 81 字节 / 80 UTF-16 code unit？`🙂` 是 U+1F642，占 2 个 UTF-16 code unit） | — | 码点计 = 80 收；若实现按 UTF-16 length 计 = 81 拒 → **这条用例专门用来暴露计量单位错误** |

第 3 条必须在需求评审时就把计量单位钉死（码点 / UTF-16 code unit / 字节），否则前后端和数据库（`VARCHAR(80)` 在 MySQL utf8mb4 下是 80 字符，在 Oracle 下默认是 80 字节）会给出三种不同答案。

### 常见漏测点

| 漏测点 | 后果 |
|---|---|
| 只测 min / max，不测 min−1 / max+1 | `>` 写成 `>=` 无人发现 |
| 开闭区间判断错 | on/off 点整体错位一位，边界用例全部失效但全绿 |
| 只测数值边界，不测**日期语义边界** | 跨月末（1/31 + 1 月）、闰年 2/29、夏令时切换日、时区跨日、`today` 在 23:59:59 执行 |
| 长度按 char 计，忽略码点/字节 | emoji、CJK 扩展区、组合字符（`e` + `\u0301`）导致前后端判定不一致 |
| 边界只作用于单维度，忽略维度乘积 | 标题 80 码点 × 20 个附件 × 每个 5MB 的总请求体上限没人测 |
| 忽略"刚好等于容量"的集合边界 | 空数组、1 个元素、上限个元素、上限+1 个元素四档常只测中间两档 |
| 浮点用相等断言 | `0.1 + 0.2 == 0.3` 为假；金额边界必须用最小货币单位（分）整数比较或指定容差 |
| 边界值与默认值混淆 | "未提供"走默认路径，不是边界；两者都要有独立用例 |

## 3. 判定表（Decision Table）

### 适用场景

≥3 个条件共同决定一个输出，且条件之间是**布尔独立**的（没有互斥/依赖）。典型：费率计算、权限判定、可见性、路由选择、优惠叠加、告警触发规则、字段脱敏策略。

条件之间有互斥/依赖 → 先用因果图（见 `combinatorial-and-scenario.md`）再转判定表。
条件数量多但只需覆盖两两交互 → 用 Pairwise 而不是判定表。

### 构造步骤

1. **写条件桩（condition stub）**：每个条件必须能取真/假二值。取值多于二值的条件先拆成多个布尔条件（`优先级 ∈ {P0,P1,P2}` 拆成 `is_P0` / `is_P1`，或用多值判定表但规则数按水平数乘算）。
2. **写动作桩（action stub）**：所有可能的输出/副作用，包括"写日志""发通知""什么都不做"。"无动作"也是一个动作，必须显式列出。
3. **列全规则**：n 个条件 → `2^n` 条规则，一列一条，用 Y/N 填满条件桩。**先填满再删，不要一开始就跳列**——跳列就是漏测的来源。
4. **填动作**：逐列按业务规则填动作桩。填不出来的列就是需求歧义，标 `?` 并在评审时提问，禁止自己猜。
5. **合并规则**：两条规则若**只差一个条件**且**动作完全相同**，则该条件标 `-`（don't care）并合并。反复合并直到无法再合。
6. **标注不可能规则**：现实中不可达的组合标 `IMPOSSIBLE` + 一句理由，**保留在表里**，不删行。
7. **一规则一用例**：合并后的每条规则至少一条用例；`IMPOSSIBLE` 规则要有一条用例断言"该组合无法构造"（例如 API 层拒绝、DB 约束报错）。

### 填好的判定表：工单导出权限（AC-04）

条件桩 / 动作桩 + 完整 8 条规则：

| | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 |
|---|---|---|---|---|---|---|---|---|
| C1 查看者是工单所有者 | Y | Y | Y | Y | N | N | N | N |
| C2 查看者与所有者同团队 | Y | Y | N | N | Y | Y | N | N |
| C3 查看者持管理员角色 | Y | N | Y | N | Y | N | Y | N |
| A1 导出全部字段 | X | | X | | X | | X | |
| A2 导出脱敏字段 | | X | | X | | X | | |
| A3 拒绝导出 | | | | | | | | X |
| A4 写审计日志 | X | X | X | X | X | X | X | X |

**合并**（动作完全相同 + 只差一个条件 → 该条件标 `-`）：

- R1(Y,Y,Y) + R3(Y,N,Y) → (Y,-,Y)；R5(N,Y,Y) + R7(N,N,Y) → (N,-,Y)；(Y,-,Y) + (N,-,Y) → **(-,-,Y)**
- R2(Y,Y,N) + R4(Y,N,N) → **(Y,-,N)**
- R6(N,Y,N) 无法与 R8(N,N,N) 合并（动作不同）→ 各自保留

合并后判定表（8 → 4 条规则，即 4 条用例）：

| | M1 | M2 | M3 | M4 |
|---|---|---|---|---|
| C1 是所有者 | - | Y | N | N |
| C2 同团队 | - | - | Y | N |
| C3 管理员 | Y | N | N | N |
| A1 全字段导出 | X | | | |
| A2 脱敏导出 | | X | X | |
| A3 拒绝 | | | | X |
| A4 审计日志 | X | X | X | X |
| 用例ID | TC-EXP-01 | TC-EXP-02 | TC-EXP-03 | TC-EXP-04 |

`-` 表示 don't care：**但 don't care 不等于不用测**。M1 的 `-,-,Y` 覆盖了 R1/R3/R5/R7 四条原始规则，实现若错误地依赖了 C1，只有部分子组合会失败。对高风险规则（涉及权限、金额），在 don't care 维度上**各补一条抽样用例**（如 TC-EXP-01a：非所有者 + 非同团队 + 管理员），并在用例备注写明"验证 M1 的 don't care 维度确实无关"。

### 不可能规则标注示例（四条件）

条件：C1 用户已登录、C2 用户持管理员角色、C3 请求来自受信网络、C4 请求携带一次性令牌。

| | R? | 标注 |
|---|---|---|
| C1 已登录 = N 且 C2 管理员 = Y | 8 条规则 | **IMPOSSIBLE** — 角色绑定在会话上，未登录会话不可能持有角色。理由：需求 §3.2 + 代码 `AuthContext` 构造器约束。 |

16 条规则中 8 条标 IMPOSSIBLE，可执行规则降到 8 条。**标注必须附理由与证据来源**（需求章节号 / 代码位置 / DB 约束名），否则评审无法判断这是"真不可能"还是"设计者没想到"。

对每条 IMPOSSIBLE 规则补一条**防御性用例**：尝试构造该组合（例如伪造一个 `user_id` 为空但 `role=admin` 的 token），断言被认证层拒绝且返回 `401` 而不是 `403`——若返回 403，说明"不可能"其实可达，标注就是错的。

### 常见漏测点

| 漏测点 | 后果 |
|---|---|
| 条件桩写成多值（"优先级 = P0/P1/P2"当一个条件） | 规则数被低估，P1 分支零覆盖 |
| 忘列"无动作"动作桩 | "所有条件都不满足时应该什么都不做"这条规则没人测，实现里常留一个 else 分支做了意外的事 |
| 一开始就跳列 | 跳掉的那列恰好是唯一失败列 |
| 动作填 `?` 时自己猜一个 | 需求歧义被掩盖，评审失去发现机会 |
| 合并后不检查 don't care 维度 | 实现偷偷依赖了被合并掉的条件，用例全绿 |
| IMPOSSIBLE 规则直接删行 | 双方对约束的理解从未对齐；约束一旦松动（新加了一种登录方式）无人察觉 |
| 只测规则，不测规则**顺序** | 多条规则同时命中时以哪条为准（first-match vs best-match）需求常未写明 |
| 忽略副作用的幂等 | A4"写审计日志"在重试时写两条，规则表覆盖不到，需另加幂等用例 |

## 4. 状态迁移（State Transition Testing）

### 适用场景

数据有生命周期字段（`status` / `state` / `phase` / `step`），或需求含"流转""审批""退款""重连""恢复""归档""激活/停用"。也适用于连接状态机、播放器状态、向导多步表单、分布式事务补偿。

### 构造步骤

1. **画状态表**：列出所有状态 + 含义 + 进入条件 + 是否终态 + 该状态下允许的事件全集。
2. **画迁移表**：每行一条迁移，含 `当前状态 / 事件 / 守卫条件 / 下一状态 / 副作用 / 用例ID`。**守卫条件失败也是一种结果**，必须单列一行（下一状态 = 当前状态）。
3. **列非法迁移**：状态表的"允许事件全集"之外，每个 `(状态, 事件)` 组合都是非法迁移。用 `状态数 × 事件数 − 合法迁移数` 算出总数，逐个写断言。
4. **定覆盖级别**：
   - **0-switch**：每条合法迁移至少被覆盖一次。用例数 = 合法迁移数。这是**最低门槛**。
   - **1-switch**：每对**连续**迁移（前一条的终态 = 后一条的起态）至少被覆盖一次。用例数 = 合法迁移的后继对数。用于有副作用累积或缓存的状态机。
   - **2-switch** 一般只在安全关键系统用，成本高。
5. **非法迁移全覆盖**：不做抽样。非法迁移数通常远大于合法迁移数，但每条断言成本极低（一次调用 + 两个断言：状态不变、无副作用）。
6. **补并发与时序用例**：同一状态两个事件并发到达、事件乱序、超时自动迁移与人工迁移竞争。

### 1-switch 覆盖

前一条迁移的终态 = 后一条的起态，即构成一对可连迁移。从迁移表推：

| 前 | 后继（可连） | 对数 |
|---|---|---|
| T1 (→OPEN) | T4, T5, T6 | 3 |
| T3 (→DRAFT) | T1, T2, T3 | 3 |
| T4 (→IN_PROGRESS) | T7, T8 | 2 |
| T7 (→RESOLVED) | T9, T10 | 2 |
| T9 (→OPEN) | T4, T5, T6 | 3 |
| T2 / T5 / T6 / T8 / T10 | 进入终态或删除态，无后继 | 0 |

**1-switch 用例数 = 13。** 每条用例是一次多步操作序列，例如 TC-ST-1S-07 = `T7 → T9`：解决工单后在 14 天内 reopen，断言状态回到 OPEN **且** `assignee_id` 已被清空（T9 的副作用）——这个副作用只在连续迁移时才暴露。

对高风险状态机（涉及金额、权限、对外通知）做 1-switch；对纯展示状态（tab 切换）只做 0-switch。

### 填好的非法迁移用例（全枚举，不抽样）

事件全集 = {submit, delete, edit, assign, resolve, close, auto_close, reopen}（8 个），状态 5 个 → 40 个 `(状态, 事件)` 组合；合法 + 守卫失败共 14 个 → **非法迁移 26 个**。

抽样展示（其余按同一模板批量生成）：

| 当前状态 | 非法事件 | 期望 HTTP | 期望错误码 | 断言 |
|---|---|---|---|---|
| DRAFT | assign | 409 | `INVALID_TRANSITION` | 状态仍 DRAFT；`assignee_id` 仍为空；无通知发出 |
| DRAFT | resolve | 409 | `INVALID_TRANSITION` | 状态仍 DRAFT；`resolved_at` 仍为空 |
| DRAFT | reopen | 409 | `INVALID_TRANSITION` | 状态仍 DRAFT；审计日志无新增行 |
| OPEN | submit | 409 | `INVALID_TRANSITION` | 状态仍 OPEN；通知受理组**不重复发送** |
| OPEN | resolve | 409 | `INVALID_TRANSITION` | 状态仍 OPEN |
| OPEN | edit | 403 | `LOCKED_AFTER_SUBMIT` | 标题未被修改 |
| OPEN | delete | 403 | `NOT_DELETABLE` | 记录仍存在；附件未被释放 |
| IN_PROGRESS | submit | 409 | `INVALID_TRANSITION` | 状态仍 IN_PROGRESS |
| IN_PROGRESS | delete | 403 | `NOT_DELETABLE` | 记录仍存在 |
| IN_PROGRESS | reopen | 409 | `INVALID_TRANSITION` | 状态仍 IN_PROGRESS；`assignee_id` 未被清空 |
| RESOLVED | assign | 409 | `INVALID_TRANSITION` | 状态仍 RESOLVED |
| RESOLVED | resolve | 409 | `ALREADY_RESOLVED` | `resolved_at` **保持原值**（不被刷新） |
| RESOLVED | submit | 409 | `INVALID_TRANSITION` | 状态仍 RESOLVED |
| RESOLVED | delete | 403 | `NOT_DELETABLE` | 记录仍存在 |
| CLOSED | reopen | 409 | `TERMINAL_STATE` | 状态仍 CLOSED；审计日志无新增行 |
| CLOSED | close | 409 | `TERMINAL_STATE` | 审计日志**不新增第二条**（幂等） |
| CLOSED | edit / assign / resolve / delete / submit / auto_close | 409 / 403 | 按事件 | 记录完全不变 |
| *(已删除)* | 任意事件 | 404 | `NOT_FOUND` | 不返回 500，不泄露工单内容 |

每条非法迁移用例的断言固定三件套：**① 返回预期的错误码/状态码；② 状态字段未变；③ 副作用未发生**（无通知、无审计行、无关联记录写入）。只断言①的用例价值减半——实现完全可能"返回 409 但状态已经改了"。

### 常见漏测点

| 漏测点 | 后果 |
|---|---|
| 只做 0-switch | 连续两步的副作用（reopen 清空 assignee、二次 close 重复审计）漏测 |
| 非法迁移抽样 | 状态机被非法事件打穿的路径恰好是没抽到的那条 |
| 忘测守卫失败 | 守卫条件（14 天窗口、同团队）被改坏时无人发现 |
| 只断言状态，不断言副作用 | "状态对了但通知发了两次"这类缺陷逃逸 |
| 忽略超时/自动迁移 | T6 auto_close 是定时任务触发，人工用例永远走不到；需可注入时钟或缩短阈值 |
| 并发事件没测 | 提交人 reopen 与受理人 close 同时到达 → 状态取决于加锁顺序，可能出现 CLOSED→OPEN 的非法迁移 |
| 状态回退后的"再前进"没测 | RESOLVED→OPEN(T9)→IN_PROGRESS(T4) 这条链上，旧的 `resolved_at` 是否被清理 |
| 终态判定错 | CLOSED 被当成非终态，导致定时任务反复扫描已关闭工单 |
| 状态与展示层不一致 | DB 状态已变但列表页缓存未刷新，用户看到旧状态——需跨层验证，见 `csp-cross-layer-testing` |
