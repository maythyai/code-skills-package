# Test Case Design — 用例设计技术

给定一条需求 / 一个 AC / 一个函数签名，回答三个问题：**测哪些输入组合、要多少条、我漏了什么**。

## 0. 边界：本技能不管什么

| 问题 | 归属 |
|------|------|
| 该用单测 / 集成 / 契约 / E2E / 属性测试里的哪一种 | `csp-test-methodology`（方法谱系与盲点互补） |
| 提测前要不要放行、六道验证怎么跑 | `csp-verification` |
| 一次动作跨 UI/API/DB 怎么对齐证据 | `csp-cross-layer-testing` |
| 用例放在哪一层、用什么框架写 | `csp-qa-test-engineering` / `csp-test-spec` |
| **具体怎么把一条需求枚举成 N 条用例** | **本技能** |

方法谱系告诉你"用哪种测试"，本技能告诉你"这种测试里到底放哪些用例"。不要在这里重复写测试金字塔。

## 1. 决策路由：需求特征 → 技术组合

先读需求/代码，抓信号词，再选技术。**主技术决定用例骨架，必补技术决定不漏测。**

| 需求里能看到的信号 | 主技术 | 必补技术 | 用例量级 |
|---|---|---|---|
| 出现范围/长度/日期约束（"1–80 字符""不超过 365 天""金额 > 0"） | 边界值分析 | 等价类（先划类，类内取边界） | 每个输入维度 6–9 条 |
| 输入是枚举/下拉/开关/必填项，校验分散在多处 | 等价类划分 | 场景法（1 条基本流把字段串起来） | 有效类合并 1–2 条 + 每个无效类 1 条 |
| ≥3 个条件用 `&&`/`||`/嵌套 `if` 共同决定一个输出（费率、权限、可见性、是否包邮） | 判定表 | 边界值（条件里的每个阈值） | 合并后 4–12 条 |
| 条件之间有互斥/依赖/唯一约束（"选了 A 就不能选 B""必须先登录"） | 因果图 | 判定表（因果图 → 判定表） | 去掉不可能规则后的可执行规则数 |
| 数据有 status/state/phase 字段，或需求含"流转""审批""退款""重连""生命周期" | 状态迁移 | 判定表（每条迁移的守卫条件）+ 非法迁移 | 迁移数（0-switch）+ 非法迁移数 |
| 环境/配置因子 ≥4 个且水平数不等（机型 × 系统 × 语言 × 网络 × 主题） | Pairwise / 正交 | 场景法（把组合塞进主流程执行） | 全组合的 5–15% |
| 需求以用户故事/操作流写（"用户可以…然后…若失败则…"） | 场景法 | 等价类（流程里每个输入步）+ 状态迁移（若流程改状态） | 基本流 1 + 备选流 n + 异常流 m |
| 纯函数/无 UI 的转换、解析、计算 | 等价类 + 边界值 | Pairwise（多参数）+ 幂等（同输入两次） | 视输入维度，通常 10–30 条 |
| 分页/游标/批量接口 | 边界值（page=0/1/N/N+1、size=0/1/max/max+1） | 判定表（排序 × 过滤 × 分页组合） | 12–20 条 |

**反向约束**：需求里没有状态字段，就不要硬造状态迁移表；只有一个输入条件，就不要建判定表（2^1 规则没有意义）。技术是工具不是仪式。

## 2. 七种技术速览

| # | 技术 | 一句话适用 | 最容易漏的那一刀 |
|---|------|-----------|-----------------|
| 1 | 等价类划分 | 输入域大、可归类，先用最少用例覆盖最多域 | 把两个无效类塞进同一条用例（第二条校验分支永远不执行） |
| 2 | 边界值分析 | 任何有范围的输入 | 只测 on point，不测 off point（刚好越界那一步） |
| 3 | 判定表 | 多条件 → 一个决策 | 不做规则合并，2^n 条用例写不完；不标注不可能规则 |
| 4 | 状态迁移 | 有生命周期的数据 | 只测合法迁移，不测非法迁移与 1-switch（连续两步） |
| 5 | 因果图 | 条件之间有互斥/依赖 | 忘记约束标注，导致生成一堆现实不可能出现的用例 |
| 6 | Pairwise/正交 | 因子多、组合爆炸 | 压完不手工加回高风险 3 因子组合 |
| 7 | 场景法 | 需求是流程叙事 | 只写基本流；备选流"回到主流程之后"的后续步骤没人测 |

## 4. 工作流

```
Step 1  抽取被测对象     读需求/AC/函数签名 → 列出所有输入维度、输出、状态、约束
Step 2  路由技术         用 §1 表选主技术 + 必补技术（通常 2–3 种，不超过 4 种）
Step 3  枚举用例         读对应 reference，按构造步骤填表 → 得到候选用例清单（先不删）
Step 4  合并与压缩       有效类合并、判定表规则合并、pairwise 压缩；标注不可能规则并保留证据
Step 5  落地与追溯       写 8 字段用例 → 建 AC 双向追溯矩阵 → 抓出孤儿用例与未覆盖 AC
Step 6  定级与裁剪       P0/P1/P2 → 按固定顺序砍 → 留裁剪记录
Step 7  评审             过评审清单 → 产出 docs/analysis/test-cases-<feature>.md
```

Step 3 之前不要写代码。先有表，再有代码——表是可评审的，代码不是。

### 4.1 路由示例：一条 AC 走完 Step 1–4

以一条常见 AC 为例，演示怎么从文本推导出用例量级（完整表格在 references 里）。

> AC-01：工单标题为必填，长度 1–80 字符（按码点计），首尾空白自动裁剪，裁剪后为空视为未填写；
> 标题包含被禁词时拒绝创建并返回 `TITLE_FORBIDDEN`。

| Step | 动作 | 结论 |
|---|---|---|
| 1 抽取 | 找输入维度/输出/状态/约束 | 输入维度：`title`（字符串）；约束：必填、长度 1–80、裁剪规则、禁词；输出：创建成功 / 4 种错误码；无状态字段 |
| 2 路由 | 抓信号词"1–80""必填""裁剪后为空" | 主技术 = **边界值**；必补 = **等价类**（禁词、空白串、非法类型各成一类）。**不选状态迁移**（无状态字段），**不选判定表**（只有 1 个决策条件） |
| 3 枚举 | 读 `references/blackbox-techniques.md` §1 §2 | 等价类：有效 2 类 + 无效 6 类；边界点：0/1/2/79/80/81 + 裁剪前后各一组 → 9 条 |
| 4 合并压缩 | 有效类合并为 1 条代表用例；无效类**不合并** | 合计 **17 条**（2 有效 + 15 无效/边界），每条独立可执行 |

关键判断：`首尾空白自动裁剪` 让"长度"这个维度出现了**两个边界**——输入串长度和裁剪后长度。
`"   "`（3 个空格，输入长度 3 合法）裁剪后长度 0 非法，这条用例只有同时读懂两条约束才会写出来，
是这条 AC 上最典型的漏测点。

## 5. 用例模板（8 字段）

每条用例必须填满 8 个字段，缺一项即为不合格用例。字段定义、填好的样例、CSV/Markdown 模板见
`references/case-artifacts.md`（当要把用例落成文档或代码时读取）。

| 字段 | 硬要求 |
|------|--------|
| 用例ID | 稳定不变，是追溯主键；格式 `TC-<模块>-<序号>`，禁止用自增行号 |
| 标题 | 一句话说清"什么条件下做什么，期望什么"，禁止"测试标题功能" |
| 前置条件 | 数据库/账号/开关/时间等可复现初始状态；写不出前置 = 用例不可复现 |
| 输入 | 精确值 + 类型 + 单位；禁止"一个较长的字符串" |
| 步骤 | 有序、每步可独立执行、每步不含判断分支 |
| 预期结果 | 可观察的断言（返回值/状态码/DB 行/界面文案），禁止"正常工作""显示正确" |
| 优先级 | P0 / P1 / P2，判定标准见 `references/prioritization-and-review.md` |
| 关联AC | ≥1 个 AC ID；无 AC 即孤儿用例，必须处理 |

## 6. 表驱动 / 参数化

用例表 → 代码的映射规则（骨架代码见 `references/case-artifacts.md`）：

- **一行数据 = 一条用例 = 一个独立 subtest**，subtest 名字直接用用例ID，失败可反查到表。
- **数据与断言分离**：表里只放 `input` + `expected`（含 expected error code / expected state），断言逻辑写在循环体外统一一处。禁止在表里塞 lambda/闭包当断言。
- **表驱动不等于设计**：表是载体，行必须由 §1 的技术推导出来。凭空写的表只是"看起来系统化"。
- 新增一条用例的成本 = 加一行，不是加一个函数。如果加用例需要改断言逻辑，说明表设计错了。

## 7. AC 双向追溯

两个方向都要查，只查一个方向会漏一半缺陷：

| 方向 | 规则 | 违反时的缺陷名 | 处置 |
|------|------|---------------|------|
| AC → 用例 | 每条 AC 至少 1 条用例；P0/P1 的 AC 至少覆盖正常+边界+异常三类 | **未覆盖 AC** | 阻塞放行（P0/P1）；补用例或让需求方明确降级 |
| 用例 → AC | 每条用例至少映射 1 条 AC | **孤儿用例** | 二选一：删掉；或说明这是需求缺口，反向补 AC |

追溯矩阵表、反向索引表、自动校验脚本骨架见 `references/case-artifacts.md`（当用例数 > 20 或需要 CI 校验时读取）。

放行前必须算的四项覆盖率（完整 10 项指标与公式见同一文件 §3）：

| 指标 | 公式 | 放行阈值 |
|------|------|---------|
| AC 覆盖率 | 有用例的 AC 数 / AC 总数 | 100%（P0/P1 的 AC 必须含正常+边界+异常三类） |
| 等价类覆盖率 | 有代表用例的等价类数 / 等价类总数 | 100%，其中无效类不得合并 |
| 迁移覆盖率 | 已覆盖迁移数 / 迁移表迁移数（含守卫失败行） | 100%（0-switch）；高风险状态机 1-switch 也要 100% |
| Pair 覆盖率 | pairwise 表已覆盖因子对 / 全部因子对 | 100%（用脚本验证，不靠手工核对） |

四项都是 100% 不等于测够了——它们只保证"推导出的候选集没有掉项"，不保证候选集本身抽对了维度。
维度抽错的风险由 §1 路由表和评审清单兜住。

## 8. 优先级与裁剪

时间不够时的砍序是固定的，不许凭感觉砍。判定标准、砍序、裁剪记录表模板见
`references/prioritization-and-review.md`（当排期压缩或用例数超预算时读取）。

绝不可砍的四类：

1. 全部 P0 用例
2. 每个无效等价类的代表用例（砍掉 = 该分支零覆盖）
3. 每条非法状态迁移用例（砍掉 = 状态机可被打穿）
4. 任一 AC 的最后一条用例（砍掉 = 制造未覆盖 AC）

| 产物 | 路径 |
|------|------|
| 用例集（Markdown/CSV） | `docs/analysis/test-cases-<feature>.md` |
| AC 追溯矩阵 | `docs/analysis/traceability-<feature>.md` |
| 裁剪记录 | `docs/analysis/case-pruning-<feature>.md` |
| 表驱动测试代码 | 项目既有测试目录（不新建顶层目录） |

禁止把用例集写到仓库根目录，禁止散落成 `test-cases.md` 这类无 feature 后缀的文件。

## Key Principles

1. **先表后码**：所有用例先在表里枚举完并通过评审，再落成代码。表可评审，代码不可评审。
2. **枚举要拆到最细可判定单元**：每个输入维度独立算 on point（边界本身）/ off point（刚好越界的最近不合法值）/ in point（边界内侧邻近值），缺 off point 等于没测校验；每个无效等价类单独一条用例——多个无效输入同框时程序在第一个校验就短路返回，其余分支永不执行，覆盖率是假的。
3. **不可能规则要标注不要删除**：判定表/因果图里现实不可达的组合标 `IMPOSSIBLE` 并让需求方签字确认，而不是悄悄少写一行——漏标与误标的后果完全不同。
4. **非法迁移是必须测的正向资产**：迁移表里每个不存在的 (状态, 事件) 组合都要有一条用例断言"被拒绝 + 状态不变 + 无副作用"。
5. **组合爆炸用 pairwise 压，不用抽样躲**：压到全组合的 5–15%，然后手工加回 2–5 条高风险 3 因子组合，并记录为什么是这几条。
6. **双向追溯零容忍**：孤儿用例和未覆盖 AC 都是缺陷，不是风格问题。发布前必须两个方向都跑一遍校验。
7. **裁剪有顺序且留痕**：按固定砍序执行，每条被砍用例记录 ID / 原因 / 风险承担人 / 补测计划。

## Anti-Patterns

| 反模式 | 为什么错 | 正确做法 |
|--------|---------|---------|
| 只测 happy path + 一两个"想到的"异常 | 用例集来自记忆而非推导，覆盖度不可知也不可复现 | 走 §1 路由，用技术生成候选全集，再合并压缩 |
| 边界只测 min 和 max，且默认用字符数当长度单位 | 校验逻辑写错成 `>` 还是 `>=` 时，min/max 两条都过，缺陷逃逸；而含 emoji / 组合字符时"80 字符"在字符数、码点数、字节数上结果完全不同 | on/off/by-1 三点法：min−1, min, min+1 … max−1, max, max+1；并明确边界计量单位（char / code point / byte），三类各出一条边界用例 |
| 一条用例塞多个无效输入 | 第一个校验短路返回，其余无效分支零覆盖，报告却显示"已测" | 每个无效等价类单独一条用例，标题写明违反的是哪条约束 |
| 判定表列满 2^n 条规则直接写用例，写不完就悄悄删掉不可达组合 | n=6 就是 64 条，评审不动；而静默删除等于双方对约束的理解从未对齐，漏标与误标的后果完全不同 | 填完整表 → 合并只差一个条件且动作相同的规则（用 `-` 表示无关条件）→ 剩余不可达组合标 `IMPOSSIBLE` + 一句话理由，评审时逐条确认 |
| 状态迁移只测 0-switch | 两步连击（RESOLVED→REOPENED→CLOSED）的副作用往往和单步不同 | 高风险状态机做 1-switch 覆盖：每对连续迁移至少一条用例 |
| 全组合跑不完就随机抽 20 条 | 抽样不保证任何一对因子被覆盖，可能整对因子从未同框 | Pairwise：保证任意两因子的所有水平组合至少出现一次，再手工加高风险三因子组合 |
| 场景法只写基本流 | 备选流与异常流才是线上事故高发区，基本流反而是最不容易坏的部分 | 每个分叉点至少一条备选流；每个异常流一条；异常流后必测"状态是否残留" |
| 预期结果写"显示正常""不报错" | 不可判定，执行时全靠主观，回归时无法比对 | 写具体可观察断言：状态码、返回字段值、DB 行数、界面精确文案 |
| 用例ID 用自增行号 | 中间插一条就全体错位，追溯矩阵瞬间失效 | 稳定 ID `TC-<模块>-<序号>`，只追加不复用，删除的 ID 保留占位并标 DEPRECATED |
| 表驱动里把断言写成 lambda 塞进表 | 数据与断言耦合，加一行可能要改断言逻辑，表失去可评审性 | 表只放 input + expected；断言在循环体统一一处；subtest 名 = 用例ID |
| 用例数当成质量指标（"我们写了 800 条"） | 数量与覆盖无关，重复覆盖同一等价类的 800 条不如正交的 80 条 | 报覆盖率指标：AC 覆盖率、等价类覆盖率、迁移覆盖率、pair 覆盖率 |
| 时间不够时整块砍掉某个技术 | 砍掉的往往正是唯一覆盖某类缺陷的技术（比如全部边界值） | 按固定砍序：先砍组合加强行 → 再砍同类冗余代表 → 再砍纯文案类；四类绝不可砍 |
