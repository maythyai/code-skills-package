# 用户体系设计检查清单

> 本文是 `csp-user-system-design` 的深度参考文档，提供结构化的设计评审检查清单，适用于新系统设计评审和现有系统架构评估。

## 使用方式

- **新系统设计**：逐项确认，在 `[ ]` 中标记 `[x]` 已完成或 `[-]` 不适用
- **现有系统评审**：标记 `[PASS]` / `[FAIL]` / `[N/A]`，FAIL 项需记录差距和修复计划
- **审计/合规**：FAIL 项必须提供修复时间线和责任人

---

## 一、标识符与数据模型

### 1.1 主键设计
- [ ] 主键使用 UUID（或等价不可变、不可猜测的方案）
- [ ] **不**使用邮箱/手机/用户名做主键
- [ ] 主键生成策略支持分布式部署

### 1.2 唯一约束
- [ ] `username` 有唯一索引
- [ ] `email` 有唯一索引
- [ ] 允许用户名/邮箱变更（变更时有审计日志）

### 1.3 表结构分离
- [ ] 认证信息（`users`）与展示信息（`user_profiles`）分表
- [ ] 偏好独立表（`user_preferences`），核心偏好独立列 + JSONB 兜底
- [ ] 敏感字段（密码/2FA secret）与常规字段隔离

### 1.4 扩展性
- [ ] 角色/状态/类型等枚举字段使用 `VARCHAR` 而非数据库 ENUM
- [ ] 核心表预留 `metadata JSONB` 扩展字段
- [ ] JSONB 不存储需要索引查询的核心业务字段

### 1.5 软删除
- [ ] 支持软删除（`deactivated_at` / `deleted_at`）
- [ ] 软删除有明确的保留期配置
- [ ] 保留期后有清理策略（物理删除或匿名化）

---

## 二、认证

### 2.1 多通道统一
- [ ] 所有认证入口（Web / API / Mobile / CLI / SSR）统一解析为 `user_id`
- [ ] 上层业务代码不感知认证通道差异
- [ ] 认证中间件按固定优先级尝试各通道

### 2.2 密码安全
- [ ] 密码使用 bcrypt（cost ≥ 12）或 argon2id 哈希
- [ ] 密码强度策略可配置（最小长度/字符组合/禁止常见密码）
- [ ] 密码永不以明文形式存储、传输、记录日志

### 2.3 登录保护
- [ ] 登录限流：per-username + per-IP，Redis 分布式计数
- [ ] 锁定机制：超过阈值后临时锁定
- [ ] 登录失败不暴露用户是否存在（统一响应消息）

### 2.4 双因素认证
- [ ] 支持 TOTP（基于时间的一次性密码）
- [ ] 生成并安全存储恢复码（SHA-256 哈希）
- [ ] `failed_attempts` + `locked_until` 防暴力破解 TOTP

### 2.5 会话管理
- [ ] 访问令牌短有效期（≤ 24 小时）
- [ ] 支持即时撤销（黑名单/缓存失效）
- [ ] 用户可查看和撤销自己的活跃会话
- [ ] Cookie 设置：`Secure; HttpOnly; SameSite=Lax`

### 2.6 API Key
- [ ] API Key SHA-256 哈希存储，明文仅返回一次
- [ ] API Key 有权限范围（read / read_write）
- [ ] API Key 有过期时间
- [ ] API Key 可撤销

### 2.7 代理认证
- [ ] 仅在可信网络内启用代理认证
- [ ] 使用 HMAC 签名 + 常量时间比较验证
- [ ] 攻击者无法通过伪造头绕过认证

---

## 三、授权与权限

### 3.1 角色设计
- [ ] 全局角色与资源级角色是两个独立维度
- [ ] 角色字段使用 `VARCHAR(50)` 而非数据库 ENUM
- [ ] 每个角色的权限明确定义（权限矩阵文档化）

### 3.2 权限检查
- [ ] 权限检查在 API 层（中间件/依赖注入），而非仅前端
- [ ] 每个 API 端点独立声明所需权限
- [ ] 默认拒绝——未显式授权的操作一律禁止

### 3.3 套餐与权限分离
- [ ] 套餐 Feature Flag（SEO/SSO/API访问）独立于角色权限
- [ ] 角色检查不混入套餐判断
- [ ] 套餐变更不改变角色（反之亦然）

### 3.4 数据层隔离
- [ ] 所有核心业务查询默认带 `team_id` 过滤
- [ ] 数据层隔离不依赖上层传入参数（中间件自动注入）
- [ ] 全局管理员不自动获得团队内部权限

### 3.5 权限缓存
- [ ] 权限缓存以 `user_id` 为 key
- [ ] 角色变更时主动 invalidate 缓存
- [ ] 缓存 TTL 合理（建议 ≤ 5 分钟）

---

## 四、安全

### 4.1 时序安全
- [ ] 密钥/签名比较使用常量时间函数（`hmac.compare_digest`）
- [ ] 不通过响应时间泄露任何信息

### 4.2 审计日志
- [ ] 关键操作有审计日志（登录/角色变更/权限修改/数据删除）
- [ ] 审计日志包含：actor / action / target / details / IP / timestamp
- [ ] 审计日志保留期 ≥ 180 天
- [ ] 审计日志可导出

### 4.3 敏感数据
- [ ] 密码/Token/2FA Secret 永不以明文存储
- [ ] 恢复码/API Key 明文仅在创建时返回
- [ ] 日志不记录密码/Token

---

## 五、多租户

### 5.1 数据隔离
- [ ] 核心实体（资源、内容）有 `team_id` 外键
- [ ] 查询默认带 `team_id` 过滤
- [ ] 不以 "前端传 team_id 参数" 作为隔离手段

### 5.2 权限隔离
- [ ] 团队成员角色仅影响本团队资源
- [ ] 跨团队用户需明确切换上下文
- [ ] 团队配额池不被其他团队消耗

### 5.3 成员管理
- [ ] 邀请机制有并发安全保护（唯一约束 + 行锁）
- [ ] 角色变更在同一事务内完成
- [ ] owner 不可被删除或降级

---

## 六、配额与套餐

### 6.1 配额模型
- [ ] 配额检查在业务操作前（pre-flight check）
- [ ] 配额定义由配置驱动，不硬编码
- [ ] 团队场景有 per-member cap

### 6.2 套餐变更
- [ ] 升级即时生效
- [ ] 降级可在周期结束时生效
- [ ] 套餐变更事件被所有下游正确消费

---

## 七、隐私与合规

### 7.1 数据权利
- [ ] 用户可导出自己的所有数据（结构化、机器可读格式）
- [ ] 用户可请求删除数据（物理删除或匿名化）
- [ ] 数据删除有明确的宽限期和级联策略

### 7.2 数据最小化
- [ ] 仅收集必要字段
- [ ] 提供隐私设置开关
- [ ] 敏感字段不暴露给分析系统

### 7.3 同意管理
- [ ] Cookie 区分必要/非必要
- [ ] 同意记录服务端存储（含 timestamp + version）
- [ ] 用户可随时修改同意设置

---

## 八、性能

### 8.1 热路径
- [ ] API Key 查找字段有索引（`key_hash` UNIQUE）
- [ ] Session 查找字段有索引（`token_hash` UNIQUE）
- [ ] 认证热路径避免全表扫描

### 8.2 缓存
- [ ] 用户偏好的高频读取可加短期缓存
- [ ] 配额计数器用 Redis（定期刷回 DB）
- [ ] 缓存过期策略合理

### 8.3 查询优化
- [ ] 用户列表分页 + 搜索索引
- [ ] 避免 N+1 查询（如用户 → 团队 → 成员）
- [ ] 大表（审计日志/登录历史）按月分区

---

## 九、生命周期

### 9.1 状态机
- [ ] 用户状态定义完整（registered → verified → active → suspended → deactivated → deleted）
- [ ] 状态转换规则明确，有唯一入口
- [ ] 状态转换有审计日志

### 9.2 清理策略
- [ ] 过期会话自动清理
- [ ] 过期邀请自动清理
- [ ] 软删除用户到期后自动处理
- [ ] 审计日志定期归档
