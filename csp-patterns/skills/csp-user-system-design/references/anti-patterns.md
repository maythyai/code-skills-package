# 用户体系设计反模式清单

> 本文是 `csp-user-system-design` 的深度参考文档，收录用户体系设计中最常见的反模式、后果与纠正方案。

## 一、数据层反模式

### 1. 用业务字段做主键

**症状**：`users` 表用 `email` 或 `username` 做主键。

**后果**：
- 用户更换邮箱/用户名时，所有外键关联断裂
- 隐私合规要求删除邮箱时，数据一致性崩溃

**纠正**：
```
错误：CREATE TABLE users (email VARCHAR(255) PRIMARY KEY, ...)
正确：UUID 主键 + email/username 唯一索引（可修改、可删除）
```

### 2. 角色用 ENUM 类型

**症状**：`role ENUM('admin', 'user', 'moderator')`

**后果**：
- 添加新角色需要 `ALTER TABLE`（生产环境高风险操作）
- 回滚困难

**纠正**：`role VARCHAR(50)` + 应用层 CHECK 约束

### 3. 一张大表存所有用户信息

**症状**：`users` 表有 50+ 列，包含认证、资料、偏好、统计数据。

**后果**：
- 查询缓慢（每次读偏好也要加载密码哈希列）
- 锁竞争严重（更新统计数据阻塞认证查询）
- 迁移困难

**纠正**：分表——`users`(认证)、`user_profiles`(展示)、`user_preferences`(偏好)

### 4. 物理删除用户数据

**症状**：用户注销时 `DELETE FROM users WHERE id = ?`。

**后果**：
- 所有关联数据的外键断裂或级联丢失
- 无法恢复（用户可能在宽限期内反悔）
- 审计追溯丢失

**纠正**：软删除（`deactivated_at` 标记），可配置保留期，到期后再物理删除或匿名化

## 二、认证层反模式

### 5. 多前端各自选择认证方式

**症状**：Web 用 Session、CLI 用持久 API Key、移动端用设备 ID，三套认证互相不认。

**后果**：
- 用户在 Web 登录后，CLI 仍需单独配置 API Key
- 会话无法统一管理
- 安全策略碎片化

**纠正**：所有认证通道统一解析到 `user_id`；WebSocket/CLI 也使用短期 JWT 而非独立持久 Key

### 6. 密码明文存储或弱哈希

**症状**：`password VARCHAR(255)` 存明文，或用 MD5/SHA1 单次哈希。

**后果**：数据库泄露 = 所有用户密码泄露。

**纠正**：
- bcrypt (cost ≥ 12) 或 argon2id
- 禁止自定义哈希方案

### 7. 不设登录限流

**症状**：登录接口无速率限制。

**后果**：暴力破解、字典攻击、账号枚举。

**纠正**：
- per-username 限制（5次/15分钟）
- per-IP 限制（20次/15分钟）
- 分布式计数器（Redis）+ 锁定机制

### 8. API Key 明文存储

**症状**：`api_keys` 表中 `key VARCHAR(255)` 存明文。

**后果**：数据库泄露即所有 API Key 泄露，且恢复 Key 无法通知用户（因为系统也不知道明文是什么）。

**纠正**：SHA-256 哈希存储，明文仅创建时返回一次。用户丢失 Key 只能重新生成。

## 三、授权层反模式

### 9. 前端控制权限

**症状**：`v-if="user.role === 'admin'"` 隐藏按钮，但后端接口不做权限检查。

**后果**：任何能发 HTTP 请求的人都能绕过。前端条件渲染只是 UI 优化，不是安全措施。

**纠正**：每个 API 端点独立做权限检查；前端条件渲染是锦上添花，不可替代后端校验。

### 10. 全局管理员自动获得所有团队权限

**症状**：`if user.is_super_admin: allow all` 在任何团队资源上都生效。

**后果**：
- 职责不清——平台运维不应自动看到客户数据
- 隐私合规风险——GDPR/CCPA 要求访问控制

**纠正**：全局 admin 需显式加入团队才能访问团队资源。

### 11. 权限检查分散在业务代码中

**症状**：在 20 个不同的 service 方法里各自写 `if user.role != 'admin': raise 403`。

**后果**：
- 权限规则不一致（A 服务用 `role != 'admin'`，B 服务用 `require_role('admin')`）
- 新增角色时需要修改 N 处代码
- 难以审计当前的权限配置

**纠正**：
- 中间件层做准入控制
- 权限服务统一提供 `check_permission(user_id, action, resource)`
- 权限矩阵集中定义

## 四、安全层反模式

### 12. 使用 `==` 比较密钥/签名

**症状**：`if request_signature == expected_signature:`

**后果**：时序攻击——`==` 逐字节比较，攻击者可通过响应时间逐位猜测正确的签名。

**纠正**：`hmac.compare_digest(actual, expected)` 常量时间比较。

### 13. 错误消息暴露用户是否存在

**症状**：
```
❌ "该邮箱未注册" vs "密码错误"  → 区分了用户存在与否
✅ "用户名或密码错误"                → 不区分
```

**纠正**：所有认证失败的响应消息完全一致（包括响应时间和状态码）。

### 14. 信任代理头未经验证

**症状**：直接读取 `X-User-ID` 头来识别用户。

**后果**：攻击者直接在请求中设置 `X-User-ID: admin-id` 即可冒充管理员。

**纠正**：代理认证必须有 HMAC 签名验证，且只在内部网络（如 K8s service mesh）内启用。

## 五、业务层反模式

### 15. 套餐信息与角色权限混淆

**症状**：角色检查中混入套餐判断：`if user.role == 'pro_user': allow_feature_x()`。

**后果**：付费用户不等于有管理权限，管理员不一定是付费用户。两个维度耦合导致逻辑混乱。

**纠正**：
```python
# 分离检查
def can_access_feature(user_id, feature):
    return (
        permission_service.has_permission(user_id, feature) and  # 权限维度
        subscription_service.has_feature(user_id, feature)        # 套餐维度
    )
```

### 16. 硬编码配额限制

**症状**：`if daily_usage > 100: raise LimitExceeded`。

**后果**：调整配额需改代码、走发布流程。

**纠正**：配额由配置驱动——数据库/配置文件/Feature Flag 服务。

### 17. 团队配额被单人耗尽

**症状**：团队共享配额池，无 per-member cap。

**后果**：一个重度用户消耗掉整个团队配额，其他人无法工作。

**纠正**：团队共享池 + per-member cap——单人不允许超过 N% 的团队总配额。

## 六、迁移/升级反模式

### 18. 缺少账号生命周期状态机

**症状**：`users` 表只有 `active` / `inactive` 两态，中间状态靠猜。

**后果**：
- 不知道用户是"刚注册未验证"还是"主动停用"
- 清理过期数据时可能误删
- 无法正确统计各阶段用户数

**纠正**：明确定义状态枚举和转换规则。
```
registered → email_verified → active → suspended → deactivated → deleted
```

### 19. 迁移脚本无回滚方案

**症状**：用户表迁移只写了 forward migration。

**后果**：迁移出错时无法回滚，可能丢失用户数据。

**纠正**：每步迁移都必须有对应的回滚脚本，并在 staging 环境完整验证。

### 20. 不做定期一致性检查

**症状**：`User.team_id` 与 `TeamMember` 表中该用户记录不一致，从未发现。

**后果**：用户看到的团队数据与团队成员看到的不一致。

**纠正**：定时任务校验关键关联的一致性，发现不一致时告警 + 自动修复（以 `TeamMember` 表为准）。
