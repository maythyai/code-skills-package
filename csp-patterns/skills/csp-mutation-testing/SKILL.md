# Mutation Testing

Inject small syntactic bugs (mutants) into your code, re-run your test suite, and measure how many mutants your tests *kill*. A survived mutant = a missing assertion = a real bug that would ship undetected.

## When to Activate

- Line/branch coverage >80% but bugs still escape to production
- Regression-critical code: payment, auth, parsers, serializers, state machines
- You want a second-order signal on test-suite quality (not just execution)
- Post-incident: prove the bug class can't regress silently
- TDD discipline check: are your red-green-refactor tests actually asserting, or just calling?
- Before a major refactor: baseline mutation score tells you how much safety net you have

## Mutation Vocabulary

| Term | Definition | Action |
|---|---|---|
| **Mutant** | A small syntactic change (`&&`→`\|\|`, `>`→`>=`, `return x`→`return null`) | Auto-generated by tool |
| **Killed** | Some test failed when this mutant was injected | ✅ Good — test caught it |
| **Survived** | All tests passed despite the mutant | ❌ Missing assertion — write a test |
| **Equivalent** | Mutation preserves semantics (unkillable) | ⚠️ Mark with `// Stryker disable` or PIT `@SuppressFBWarnings` |
| **Timeout** | Test hung on this mutant | Investigate — often infinite loop mutant |
| **No coverage** | No test executed the mutated line | ❌ Untested code |
| **Mutation score** | killed / (killed + survived + timeout) | Target 70–85% on core modules |

> Mutation score excludes equivalent mutants from the denominator. A score of 100% is theoretically impossible for non-trivial code.

## Setup & Canonical Commands

```bash
# StrykerJS (Vitest runner)
npm i -D @stryker-mutator/core @stryker-mutator/vitest-runner
npx stryker init                    # generates stryker.conf.json
npx stryker run                     # full run
npx stryker run --incremental       # reuse prior results

# PIT (Maven)
mvn test-compile org.pitest:pitest-maven:mutationCoverage
# report: target/pit-reports/<timestamp>/index.html

# PIT (Gradle)
plugins { id "info.solidsoft.pitest" version "1.15.0" }
./gradlew pitest

# mutmut
pip install mutmut
mutmut run                          # full
mutmut results                      # list survived
mutmut show <id>                    # diff for one mutant

# cargo-mutants
cargo install cargo-mutants
cargo mutants                       # full
cargo mutants --in-diff origin/main # only mutate changed lines (PR gate)
```

## Pattern 1: StrykerJS Config (scoped + incremental)

```json
// stryker.conf.json
{
  "$schema": "./node_modules/@stryker-mutator/core/schema/stryker-schema.json",
  "testRunner": "vitest",
  "mutate": [
    "src/core/**/*.ts",
    "src/payment/**/*.ts",
    "!src/**/*.spec.ts",
    "!src/**/__tests__/**"
  ],
  "coverageAnalysis": "perTest",
  "thresholds": { "high": 85, "low": 60, "break": 60 },
  "reporters": ["html", "progress", "dashboard"],
  "incremental": true,
  "incrementalFile": "reports/stryker-incremental.json",
  "timeoutMS": 60000,
  "concurrency": 4
}
```

Key decisions:
- **`mutate` glob**: scope to regression-critical modules. Whole-repo mutation is a nightly job, not a PR gate.
- **`coverageAnalysis: "perTest"`**: only re-runs tests that cover the mutated line — 5–10× speedup.
- **`thresholds.break: 60`**: CI fails below 60%. Tune per module; 60–70% for new code, 80%+ for payment/auth.
- **`incremental`**: reuses prior results; commit `reports/stryker-incremental.json` or cache in CI.

## Pattern 2: PIT Config (Maven, with history)

```xml
<plugin>
  <groupId>org.pitest</groupId>
  <artifactId>pitest-maven</artifactId>
  <version>1.17.0</version>
  <configuration>
    <targetClasses>
      <param>com.example.payment.*</param>
      <param>com.example.auth.*</param>
    </targetClasses>
    <targetTests>
      <param>com.example.*Test</param>
    </targetTests>
    <mutators>
      <mutator>DEFAULTS</mutator>
      <mutator>STRONGER</mutator>
    </mutators>
    <withHistory>true</withHistory>
    <historyInputFile>${project.build.directory}/pit-history.bin</historyInputFile>
    <historyOutputFile>${project.build.directory}/pit-history.bin</historyOutputFile>
    <threshold>
      <mutation>70</mutation>
    </threshold>
    <outputFormats>
      <outputFormat>HTML</outputFormat>
      <outputFormat>XML</outputFormat>
    </outputFormats>
  </configuration>
</plugin>
```

`withHistory` makes PIT incremental — cache `pit-history.bin` in CI for 5–10× speedup on subsequent runs.

## Pattern 3: Survivor Triage Workflow

Every survived mutant is one of three things:

```
Survived mutant
  │
  ├─ Missing assertion → write a test that kills it
  │     Example: mutant changed `>` to `>=`, no test covers boundary
  │     Action: add test with input exactly at boundary
  │
  ├─ Equivalent mutant → semantics unchanged, unkillable
  │     Example: `return x` → `return x` (dead code mutation)
  │     Action: mark with `// Stryker disable next-line` or PIT exclusion
  │
  └─ Untested code path → no test executes this line
        Action: either write a test, or delete the dead code
```

Triage report template:

```markdown
## Mutation Triage — src/payment/charge.ts (2026-11-10)

Score: 68% (34/50 killed). Threshold: 70% → FAIL.

### Survived (16)
| ID | Line | Mutation | Verdict | Action |
|----|------|----------|---------|--------|
| 12 | 45 | `>` → `>=` | Missing test | Add boundary test for amount == limit |
| 18 | 78 | `return null` → `return undefined` | Equivalent | Stryker disable |
| 23 | 91 | `&&` → `\|\|` | Missing test | Add test for retry && !aborted |
| ... |

### No coverage (4)
| Line | Code | Action |
|------|------|--------|
| 102-115 | legacyFallback() | Delete — dead code since v2.3 |
```

## Pattern 4: PR Gate with Diff-Scoped Mutation

```yaml
# .github/workflows/mutation.yml
on: pull_request
jobs:
  mutation-pr-gate:
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - run: npm ci
      - name: Stryker incremental (changed files only)
        run: npx stryker run --incremental --incrementalFile=.stryker-cache/incremental.json
      - uses: actions/cache@v4
        with:
          path: .stryker-cache
          key: stryker-${{ hashFiles('src/**') }}
      - name: Fail if score < 70%
        run: |
          SCORE=$(jq '.files[].mutants | map(select(.status=="Killed")) | length' reports/mutation.json)
          TOTAL=$(jq '.files[].mutants | length' reports/mutation.json)
          PCT=$((SCORE * 100 / TOTAL))
          [ $PCT -ge 70 ] || (echo "Mutation score $PCT% < 70%" && exit 1)
```

For Rust, `cargo mutants --in-diff origin/main` mutates only changed lines — ideal PR gate.

## Pattern 5: Nightly Deep Run + Dashboard

```yaml
# .github/workflows/mutation-nightly.yml
on: { schedule: [{ cron: "0 3 * * *" }] }
jobs:
  full-mutation:
    steps:
      - run: npx stryker run --concurrency 8 --timeoutMS 120000
      - name: Publish to Stryker Dashboard
        run: npx @stryker-mutator/dashboard-reporter
        env:
          STRYKER_DASHBOARD_API_KEY: ${{ secrets.STRYKER_DASHBOARD_API_KEY }}
```

Dashboard gives per-module trend lines. Track score *direction*, not absolute number — a module dropping from 82% → 74% over 3 weeks is a signal.

## CI Integration Strategy

| Gate | Scope | Threshold | Frequency |
|---|---|---|---|
| PR | Changed files only (`--in-diff` / incremental) | 70% | Every PR |
| Pre-merge | `src/core/**`, `src/payment/**` | 75% | Merge queue |
| Nightly | Whole repo | Track trend, no hard fail | Daily 03:00 |
| Release | Regression-critical modules | 80% | Pre-tag |

Never gate the whole repo at 85%+ on every PR — it's slow and demoralizing. Scope + incremental is the key.

## Anti-Patterns

- **Chasing 100% mutation score** — Equivalent mutants make this impossible. 70–85% is realistic; the last 15% is triage overhead, not safety.
- **Running on the whole codebase in CI** — Hours of compute, no signal. Scope `mutate` globs to core modules; nightly for full.
- **Not triaging survivors** — A survived mutant is either a missing test or an equivalent mutant. Ignoring it means ignoring a real gap.
- **Flaky-test amplification** — One flaky test can turn hundreds of mutants red (false kills) or green (false survivals). Fix flakiness *before* adopting mutation testing.
- **Using mutation score as a cross-team KPI** — Thresholds vary wildly by domain (payment 85%, UI 50%). Comparing scores across teams is meaningless and incentivizes gaming.
- **Mutating generated code** — ORM models, protobuf stubs, compiled assets. Exclude via `mutate: ["!src/generated/**"]`.
- **Ignoring timeout mutants** — A timeout often means the mutant created an infinite loop your tests don't guard against. Investigate, don't suppress.
