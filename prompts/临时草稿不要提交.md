使用 CSP 产品规划能力从零到一完成产品规划全链路（调研 → 战略 → 路线图 → 审视 → 收敛 → PRD SPEC），产出可直接交棒给 [[prompts/000-develop_pipeline_csp.md]] 的版本队列。

## 规划流程

### Phase 0：项目上下文探测（强制前置）
规划前先读清现状，读到即停：
1. 既有规划：`docs/strategy/STRATEGY.md` + `ROADMAP.md` 是否存在 → 决定首次/增量更新
2. 已发布版本：`git tag --list 'v*'` → 基线，规划续编
3. 07 复盘 findings：`.csp/review/REVIEW-FINDINGS-*.json`（open/deferred）→ 回流输入
4. 参考文件夹：`开源项目参考/`/`references/`/`竞品/` 等 → 若有，做竞品借鉴（Phase 0.5）

输出"规划就绪卡"：既有规划（有/无）→ 已发布版本列表 → 07 回流 finding 数 → 参考项目 → 本次定位（首次/增量）。

### Phase A：项目现状评估（非首次规划强制前置）

> 非全新项目（已有已发布版本/线上用户）**必须执行**；纯新项目（MVP 未上线）跳过。

**评估目的**：在规划"下一步往哪走"之前，先看清"现在在哪里"——用数据和实证而非感觉来判断产品当前状态，让每一轮规划都有事实基础。

#### A.1 产品健康度诊断

调用 `[[skill:csp-product-pulse]]`（时间窗口体验脉冲报告）+ `[[skill:csp-product-metrics-review]]`（北极星指标健康度）做产品健康度快照：

- **核心指标**：DAU/MAU、留存率（次日/7 日/30 日）、转化漏斗（各步骤转化率）、核心功能使用频次
- **异常检测**：指标突变/趋势拐点/环比异常，逐条标"信号强度"（弱/中/强）+ 可能根因假设
- **北极星子指标**：按 STRATEGY 定义的北极星指标拆解到子指标，逐子指标看健康度（healthy/watch/critical）
- 指标不可得 → 标 `[TBD-指标缺失]`，记录获取路径（需要的埋点/报表），作为后续版本的技术债输入

#### A.2 功能采用率盘点

调用 `[[skill:csp-user-analytics]]` 做逐模块/逐功能采用率分析：

- **高频功能**（采用率 >X%）：是否稳定可靠？有无进一步优化空间？
- **低频功能**（采用率 <Y%）：是入口不显眼（→ UX 问题）？是用户不需要（→ 考虑砍掉）？还是功能刚上尚未推广（→ 运营问题）？
- **死功能**（零采用率持续 N 个版本）：建议 deprecate 或砍，记入 Phase 2.5 审视候选项
- **功能使用路径**：核心任务的实际用户路径（是否与设计意图一致？有无绕路/卡住/放弃？）

#### A.3 用户痛点与反馈聚类

调用 `[[skill:csp-user-feedback-analysis]]` 做反馈聚类：

- **反馈分类**：按情感（正面/中性/负面/紧急负面）+ 主题聚类（如"登录困难""性能慢""功能缺失"）
- **痛点排序**：严重度 = 频次 × 强度 × 商业影响（高流失/高客诉/阻断核心路径），输出 Top-N
- **来自 07 复盘的回流 findings**：`.csp/review/REVIEW-FINDINGS-*.json` 中 open/deferred 项并入本阶段评估
- **支持渠道信号**：客诉工单/在线客服高频问题（如有）→ 标来源

#### A.4 体验与设计债审计

基于真实使用数据做体验问题发现（不只是"审美问题"，而是"用户用起来有问题"）：

- **关键路径摩擦**：核心任务完成时间是否增长？放弃率是否上升？中途退出点在哪？
- **违反用户习惯**（Nielsen 10 对照）：系统状态是否不可见（用户不知道在发生什么）？操作是否不符合平台惯例？是否强迫用户记忆而非识别？
- **设计混乱/不一致**：同一操作在不同模块的入口/反馈/交互是否一致？同类信息在不同页面的呈现是否统一？色调/字体/间距是否漂移？
- **功能定位错位**：是否有"设计时觉得重要、但数据证明用户不 care"的功能？是否有"用户高频使用、但入口藏在深处"的功能？
- **无障碍问题**：对比 WCAG 2.2 AA 标准，哪些页面/流程存在可达性障碍？

若已有 audit/critic/gap-analysis 的既有 findings（`.csp/audit/`、`.csp/critic/`、`.csp/gap-analysis/`），直接引用已有结论，不重复审查；只补充"当前数据视角下新暴露的体验问题"。

#### A.5 技术债与运维信号

扫描既有技术债记录 + 运维信号作为规划约束输入：

- **已知技术债**：`.csp/tech-debt/` + `csp-tech-debt-assessment` 产物（如有）→ 哪些债务正在产生"利息"（拖慢迭代/引发故障/增加维护成本）？
- **性能问题**：首屏时间/API 响应 P95/错误率/崩溃率 → 是否在恶化？
- **运维信号**：告警频率/on-call 负担/部署失败率 → 是否需要在版本中安排稳定性投入？

#### A.6 现状评估输出

产出 `docs/analysis/CURRENT-STATE-{date}.md`，包含：

```markdown
## 产品健康度快照
- 核心指标：{指标名=当前值，环比变化%}
- 北极星子指标健康度：{列表，每项 healthy/watch/critical}

## 功能采用率盘点
| 模块/功能 | 采用率 | 趋势 | 判定 | 建议 |
|-----------|--------|------|------|------|

## 用户痛点 Top-N
| 排序 | 痛点 | 严重度(频次×强度×影响) | 来源 | 对应版本建议 |

## 体验与设计债
| 问题 | 影响 | 依据 | 优先级 |

## 技术债与运维约束
- 阻碍迭代的债：{清单}
- 需安排稳定性投入的信号：{清单}

## 现状评估结论
- 本迭代必须解决的 P0 问题（安全/数据损坏/核心路径阻断）
- 本迭代应优先纳入的优化项（高频痛点/体验摩擦/设计混乱）
- 可作为长期投资主线的方向（技术债清偿/性能基线/无障碍）
```

> 现状评估的 findings **直接流入 Phase 2 版本序列规划**——痛点 → 优化主题 → 纳入版本功能行；死功能 → Phase 2.5 剔除候选项；技术债 → 版本投入预算。

### Phase R：市场调研与竞品分析
AI 自主完成全部桌面调研（多路并行搜索，证据带出处，缺口标 `[TBD]`），调用 `[[skill:csp-product-research]]`（创业方向/行业扫描/竞品深潜/经济模型）+ `[[skill:csp-competitive-analysis]]`（功能差距/差异化）：

**调研五面**：
1. **行业扫描**：赛道规模、增长率、政策环境、技术拐点
2. **竞品深潜**：本地参考文件夹 + GitHub/网络同类项目，逐项目分析功能矩阵，输出功能对照表
3. **客户洞察**：典型用户画像、核心场景、未被满足需求
4. **经济模型**：变现路径、成本结构、单位经济、商业验算
5. **方向可行性**："能不能做""有没有人在做""市场多大""机会窗口"

**产品审查视角**（调用 `[[agent:csp-product-lens-reviewer]]` 做前提挑战 + 战略后果 + 替代方案 + 目标-需求对齐审查，再按以下任务指示补充全视角审查）：

按七视角逐条审查（每条 finding = 问题 + 产品 sense rationale + 依据 + 严重度）：

**L1 定位审查**：产品核心价值主张是否清晰？首屏重点是否服务北极星？非核心功能是否喧宾夺主？与竞品的差异化是否成立、可感知？
**L2 竞品审查**：功能差距表（本产品 vs 竞品矩阵），差异化机会在哪？竞品做法哪些可取（借鉴非复制，开源协议兼容）？哪些是本产品不应跟随的？
**L3 用户审查**（辅助 `[[skill:csp-user-feedback-analysis]]`）：核心场景穿透率、用户反馈聚类、高频痛点、学习成本/路径摩擦
**L4 商业审查**：变现路径合理性、成本结构、单位经济、增长杠杆、ROI 预期
**L5 技术审查**：既有架构是否支撑规划方向？技术债是否会阻碍路线图？关键依赖是否成熟可达？
**L6 体验审查**：关键路径可用性（完成核心任务所需步骤/时间）、信息架构清晰度、状态覆盖完整性（loading/empty/error/success/disabled）、Nielsen 10 可用性启发式速查（①系统状态可见性 ②系统与现实匹配 ③用户控制权与自由度 ④一致性与标准 ⑤错误预防 ⑥识别而非回忆 ⑦灵活性与效率 ⑧美学与极简 ⑨帮助识别诊断恢复错误 ⑩帮助与文档）
**L7 演进审查**：版本序列与市场节奏是否匹配？竞品版本演进速度对比？本产品 roadmap 节奏是否可持续？

> 每条审查 finding 必带依据（file:line / 竞品截图 / 反馈原文 / 指标），推断标置信度/`[TBD]`，不臆造。

产物：`docs/analysis/MARKET-RESEARCH-{date}.md`（五面 + 七视角结论，每面独立成节）。

### Phase 0.5：竞品借鉴（有参考文件夹时触发）
若探测发现参考文件夹，逐项目提炼：
- **feature 借鉴**：扫参考项目的 features/README/skills/PRD/CHANGELOG，提炼可借鉴的功能模式，标注来源+路径
- **差异化判断**：对比参考项目定位，识别本产品差异化机会
- **版本映射**：借鉴的 feature 映射到 ROADMAP 版本主题，不照抄

红线：借鉴非复制、标来源可追溯、开源协议兼容（MIT/Apache 可借鉴，GPL 审慎避免传染）。

产物：`docs/analysis/COMPETITIVE-REFERENCE.md`（`来源项目 | feature | 借鉴点 | 差异化 | 拟纳入版本`）。

### Phase 1：战略锚点
基于调研结论，调用 `[[agent:csp-pm]]`（用户故事/验收标准/优先级/RICE）+ `[[agent:csp-analyst]]`（SWOT/五力/商业模型画布/成本收益），按 Rumelt kernel 提炼 `docs/strategy/STRATEGY.md`：

1. **诊断**：产品解决什么核心问题？现状的痛点/不对称在哪？
2. **指导方针**：我们的差异化选择是什么？为什么是现在做？与竞品的核心差异是什么？
3. **为谁**：目标用户/角色/核心场景（不是"所有用户"）
4. **北极星指标**：成功怎么看 + 2-3 子指标，未定标 `[TBD]`
5. **投资主线**：3-5 条方向性主题（如"核心体验"/"平台化"/"生态"），每条一句话
6. **明确不做什么**：聚焦的代价

STRATEGY.md 短而硬——anchor，不扩成 feature list。下游 PRD 读它 ground。

### Phase 2：路线图 + 版本序列
调用 `[[workflow:csp-roadmap-planner]]` 生成长周期多版本结构化路线，产出 `docs/strategy/ROADMAP.md`。

**版本号规则（默认 SemVer X.Y.Z）**：
- **MAJOR (X)**：不兼容的 API/架构变更、移除已弃用能力——**仅在 06 发布时验证到实际 breaking 变更才 bump**
- **MINOR (Y)**：向后兼容的功能新增/主题交付，每版本通常 MINOR+1
- **PATCH (Z)**：向后兼容 bug 修复/小补丁；允许跳号
- **pre**：`alpha.N`（功能未完）/ `beta.N`（功能完）/ `rc.N`（发布候选）
- **战略主题号 ≠ SemVer 发布号**：roadmap 的"v2.0=平台化"是叙事愿景，实际 tag 从上一已发 tag 增量续编（additive→MINOR+1），只在真实 breaking 时才到达 MAJOR 战略号
- **不跳 MINOR/MAJOR**：版本号是顺序计数器，不是"宏大程度"指示器；v1.105.269 完全正常
- **默认不用日期形式**：AI 产出节奏与日历无关，按年/季/月/日定版本无意义
- **不做估时**：Agent 开发下不估人日/工时——无意义。版本顺序由依赖 DAG + 优先级 + 攒批原则决定，不按日历排期

**攒批原则**（以模块为单位聚合）：
- 同模块功能打包到一个版本（每版本功能数以模块内实际 feature 数量为准，不设硬上限——一个模块如果有 8 个相关 feature 就全打包进一个版本），不"一个 feature 开一个版本"
- 不同模块/主题方向不同/体量过大 → 拆成下一版本
- **feat/fix 分轨**：feat 批（MINOR+1）与 fix 批（PATCH+1）不混合；同迭代既有 feat 又有 fix → 拆两个 tag

**版本序列格式**（每版本摘要级，不写详细 PRD）：
```
vX.Y.Z — {主题名} — status: planned
- 目标：一句话
- 新增功能（摘要列表，按模块内实际 feature 数量，不设硬上限）：不写详细 AC，只点明做什么；同步落 FEATURES.md
- 优化项（从 Phase A+I 流入）：[来源 CURRENT-NN] 简要描述优化内容
- 增长实验（从 Phase G 流入，如有）：[假设 X → 预期指标 Y 变化 Z%]
- 用户场景/竞品差距：本版本对应解决什么（引 Phase R 调研节 / Phase A 痛点）
- 价值：用户价值 + 业务价值
- 前置依赖：依赖版本/外部能力
- PRD SPEC：docs/prd/PRD-{slug}.md（Phase 5 产出）
```

v1.0 = MVP：聚焦 3-5 核心功能验证问题假设；后续版本按投资主线推进。

### Phase 2.5：集成必要性审视（强制 self-critique gate）
**强制**：版本序列产出后立即审视——已规划 ≠ 必要。默认姿态是「砍」不是「留」。

调用 `[[skill:csp-integration-necessity-review]]` 做 7 维逐功能裁决（定位/场景/重叠/成本/依赖/攒批/聚焦→纳入/降级/剔除/合并）

| 维度 | 问什么 | 不通过 → |
|------|--------|----------|
| 定位契合度 | 功能是否服务 STRATEGY 锚点？ | 降级或剔除 |
| 场景必要性 | 核心用户/场景真需要？ | 剔除（无场景支撑） |
| 与现有能力重叠 | 是否已做/同批次重叠？ | 合并或剔除 |
| 集成成本 vs 价值 | 实现成本 vs 用户/业务价值？ | 降级到远期或剔除 |
| 依赖可行性 | 前置依赖是否可达？ | defer 到依赖就绪 |
| 攒批合理性 | 是否该并入同模块其他版本？ | 合并 |
| 核心场景聚焦度 | 是否落在核心业务场景？边缘场景/凑数 → | 剔除或 defer |

**裁决**（每功能四选一，必记依据可追溯）：
- `纳入`：必要，留本版本
- `降级`：移到后续版本，标 `deferred` + 解除条件
- `剔除`：移出版本序列，记入 Not working on + 原因（不静默删）
- `合并`：并入同模块另一版本

**产出**：`docs/analysis/INTEGRATION-NECESSITY-{date}.md`（审视表 `版本→功能→裁决→依据→去向`）+ 回写净版 ROADMAP + FEATURES.md。

红线：已规划不等于必要（审视可剔除已列功能），剔除/降级必须记原因，self-critique 只过滤功能层不动战略锚点，明显重叠/偏离锚点直接裁决不打断。

### Phase 3：产品架构收敛审查
调用 `[[csp-product-design-convergence]]` 做收敛审查：
- 定位对齐：功能清单是否服务同一产品定位
- 导航准入：信息架构/模块边界是否合理
- 系统卫生：技术债/冗余/死代码评估
- 迭代优先级：功能排序与依赖链路

产物：`.csp/convergence/CONVERGED-FEATURE-PLAN.md`（收敛后功能清单，下游 PRD 功能以此为唯一事实源）。

### Phase I：迭代优化与体验提升（现状评估结论并入版本规划）

> **触发**：Phase A 产出 `CURRENT-STATE` 后**强制执行**，非首次规划的每次迭代都跑。纯新项目跳过。

**目的**：将 Phase A 发现的"现有产品的可操作问题"系统性地转化为版本优化主题，确保每一轮迭代不仅有新功能，还有对既有体验的持续改进。避免"只建不修，越建越乱"。

#### I.1 优化机会提炼

从 Phase A 的评估结论中提炼三类优化机会：

**UX 体验优化**（来源：A.4 体验与设计债审计 + A.3 用户痛点）：
- 关键路径摩擦 → 简化步骤/优化信息架构/减少点击/提供默认值
- 设计混乱/不一致 → 统一组件/统一交互模式/对齐设计 Token/统一命名
- 违反用户习惯 → 按平台惯例调整/增加状态可见性/减少记忆负担
- 信息架构问题 → 重组导航/合并散落入口/提供面包屑和返回路径

**功能优化**（来源：A.2 功能采用率盘点 + A.3 痛点 Top-N）：
- 高频功能的体验打磨（不只是"能用"，要"好用"）
- 低频功能的定位调整（改进入口/改进引导/或砍掉）
- 死功能 deprecation（按入口生命周期：上线→维护→deprecation(附 TTL)→退役）

**技术优化**（来源：A.5 技术债与运维信号）：
- 阻碍迭代的债 → 安排清偿版本
- 性能恶化信号 → 设定性能基线和改善目标
- 稳定性投入 → on-call 负担降低/错误率改善

#### I.2 优化项优先级排序

按 `用户价值 × 问题严重度 × 实现成本` 三维排序：

| 优先级 | 判定 | 处置 |
|--------|------|------|
| **P0-优化** | 核心路径阻断/安全/数据正确性/大量用户受影响 | 即修——直入下一版本 PATCH 或 MINOR |
| **P1-优化** | 高频痛点/显著体验摩擦/系统性一致性违反 | 攒批进下一 MINOR 主题 |
| **P2-优化** | 体验改进/视觉统一/低频场景打磨 | 编入后续版本序列 |
| **P3-优化** | 锦上添花/极低频 | 记录备查 |

#### I.3 优化项并入版本序列

将 P0/P1 优化项**直接并入 Phase 2 的版本序列**：

- 每个版本不仅有"新增功能"行，也有"优化项"行——优化是版本主题的一部分，不是"有空再顺手做"
- 优化项与同模块的新功能打包进同一版本（攒批原则同样适用）
- 纯优化版本（无新功能）用 PATCH 号（如 `v1.4.1`）；优化+新功能用 MINOR 号
- 优化项的来源在版本行标注（`来源: Phase A-I, finding CURRENT-NN`）

产出：优化项直接回写进 `ROADMAP.md` 的对应版本功能行（标 `优化` 标签），不单独落文件。ROADMAP 版本行格式追加 `优化项: [清单，标优先级和来源]`。

|------|------|------|

### Phase 5：每版本规划级 PRD SPEC
调用 `[[workflow:csp-prd-generation]]`（PM 视角）或 `[[pattern:csp-prd]]`（设计师视角）为净版序列每个版本产出规划级 PRD SPEC：

- 路径：`docs/prd/PRD-{version-slug}.md`，`status: Draft`，`prd_depth: planning`
- 结构：8 段大纲级填写——背景/目标/功能模块/用户故事/优先级（P0/P1/P2）/关键业务规则要点（规划级只写大纲，不穷举展开）/AC 骨架（每模块至少 1 条 Given-When-Then 锚点，复杂模块可多写）/风险与依赖
- 深度边界：规划级只写大纲级要点，不写工程级细节；功能清单以 `CONVERGED-FEATURE-PLAN.md` 为唯一事实源，SPEC 与 ROADMAP/FEATURES 三者功能清单一致
- 红线：只为净版留存功能产 SPEC（剔除/降级不进），绝不写 HOW（技术选型/数据库/框架禁止），不确定处标 `[TBD]` 留给内环 01 升级

内环 01 跑到该版本时探测到同 `target_version` 的 `prd_depth: planning` Draft → **升级模式**：原文件上 delta 补全为工程级（穷举规则/完整 AC/异常流/埋点），不新建文件。

PRD SPEC 产出后直接作为测试输入：`[[prompts/000-test_pipeline_csp.md]]` Phase TB 从本 SPEC 提取测试依据（AC→用例、业务规则→边界用例、关联维度→测试策略）。

产物：每版本一份 SPEC + 登记 `docs/prd/PRD-INDEX.md`。

### Phase G：增长与实验规划（可选，有线上用户时触发）

> 已有线上用户/指标的迭代**建议执行**；纯新项目/MVP 阶段跳过。

**目的**：基于现状评估数据，设计系统性增长实验，让产品迭代有假设-验证闭环，而不只是"我觉得该做这个功能"。

#### G.1 增长机会识别

调用 `[[skill:csp-product-metrics-review]]` 做转化漏斗分析 + `[[skill:csp-user-analytics]]` 做用户行为洞察：

- **转化漏斗各步骤流失率** → 哪一步是最大漏点？（如注册→激活 60%、激活→首日留存 40%）
- **留存拐点**：用户在哪个时间点开始流失？（Day 1/Day 7/Day 30 曲线形状诊断）
- **高价值行为**：完成哪些行为的用户留存/转化显著高于未完成用户？（→ 引导更多用户完成该行为）
- **获客渠道效率**：不同渠道的用户质量（留存/转化/LTV）是否有显著差异？

#### G.2 实验假设设计

针对增长机会，设计可验证的实验假设（每条假设 = 如果做 X → 预期指标 Y 变化 Z%）：

| 假设 | 目标指标 | 预期变化 | 验证方式 | 优先级 |
|------|---------|---------|---------|--------|
| 在注册流程增加社交登录 → 注册完成率提升 15% | 注册完成率 | +15% | A/B 测试 | P0 |
| 新用户首次登录后展示引导浮层 → Day 7 留存提升 8% | Day 7 留存 | +8% | A/B 测试 | P1 |
| 简化结账步骤从 5 步到 3 步 → 结账完成率提升 20% | 结账完成率 | +20% | A/B 测试 | P0 |

#### G.3 实验优先级与版本映射

按 ICE 评分（Impact 影响面 × Confidence 信心度 × Ease 实施容易度）排序：

- **高 ICE 实验** → 纳入近期版本（MINOR），与功能开发并行
- **中 ICE 实验** → 编入后续版本序列
- **低 ICE 实验** → 记录备查，条件成熟时再评估

实验不单独发版——与版本功能打包（如 v1.5.0 包含：新功能 X + 功能优化 Y + 增长实验 Z）。

#### G.4 实验复盘与迭代

每个实验完成后复盘：

- 假设是否成立？指标变化是否显著？是否有意料之外的副作用？
- 成立 → 固化进产品（全量上线，移除实验开关）
- 不成立 → 记录失败原因（为什么用户没按预期行为），形成"不要这么做"的知识库
- 不确定 → 调参数/换方案再试一轮

产出：`docs/analysis/GROWTH-PLAN-{date}.md`（增长机会识别 + 实验假设清单 + 优先级排序 + 版本映射）；实验完成的复盘结论回写进同文件。

───────────                                ──────────────

## 反模式速查

| 反模式 | 症状 | 正确做法 |
|---|---|---|
| 规划=feature list | 列功能无战略锚点 | Anchor not plan；战略是 what/why |
| 战略主题号当 SemVer 打 tag | 起步标 v2.0.0（MAJOR）但无 breaking | 战略号≠SemVer；additive→MINOR 增量 |
| 规划完不审视 | 已规划即保留，堆功能不过滤 | Phase 2.5 强制 7 维 self-critique，默认砍 |
| 审视静默删 | 剔除/降级不留原因 | 剔除必记依据，可追溯 |
| 功能发散堆砌 | 为"完整感"堆边缘场景 | 精简聚焦核心业务场景 |
| 跳过调研拍脑袋 | 版本主题无事实输入 | Phase R 先调研，锚点基于结论 |
| 规划止步 ROADMAP | 有版本表无 PRD SPEC | Phase 5 每版本一份规划级 SPEC |
| 臆造指标 | 编 DAU/收入目标 | 未定标 `[TBD]`，留给 01 确认 |
| 规划=排期 | Gantt 化堆日期/估人日/设截止 | Agent 开发下估时无意义（人 3 天的活 Agent 几分钟完成），路线图示方向不示日期；版本号 SemVer 增量续编，版本序列按依赖+优先级排序 |
| 过度问人 | 每节反复确认 | 默认优先，仅战略模糊时人工澄清 |
| 只建不修 | 只规划新功能，不优化既有体验 | Phase A+I 强制：每轮迭代必审现状，优化项与功能同权纳入版本 |
| 数据盲飞 | 无指标依据靠感觉排优先级 | Phase A 先做健康度快照 + 痛点排序，用数据驱动"该做什么" |
| 增长靠猜 | 做功能但不知道是否有效 | Phase G 实验假设-验证闭环，每个增长动作可衡量 |

---

按现状评估 → 调研 → 战略 → 路线图 → 审视 → 收敛 → 迭代优化 → 设计衔接 → PRD SPEC → 增长实验十步链执行，AI 自主完成，不打断我。

**非全新项目（已有线上用户/已发布版本）**：Phase A（现状评估）必跑 → Phase I（迭代优化）必跑 → Phase G（增长实验）建议跑。优化项与新增功能同权纳入版本序列，不"只建不修"。

**纯新项目（MVP 未上线）**：跳过 Phase A/I/G，从 Phase R 调研开始。

每个阶段按进度条播报，全部完成后输出总摘要，交棒 pipeline 启动交付。

## Phase TB：测试依据提取（Test Basis）

> **强制前置**：在写任何测试用例之前，先明确"测什么"和"凭什么判过"。

### TB.1 从 PRD 提取测试基线

读取 `[[prompts/000-product-planning_csp.md]]` 产出的 PRD SPEC（`docs/prd/PRD-{version-slug}.md`），提取测试依据：

- **功能清单**（来自 PRD §3 详细功能设计）：每个功能模块即为一个测试单元
- **AC 清单**（来自 PRD §6 验收标准）：每条 Given-When-Then 对应至少一条测试用例
- **业务规则**（来自 PRD §3 关键业务规则）：每条规则对应边界/等价类用例
- **非功能需求**（来自 PRD §7）：性能/安全/可用性约束 → 对应非功能测试
- **风险与依赖**（来自 PRD §8）：前置依赖未就绪 → 标记测试阻塞项

调用 `[[skill:csp-product-capability]]`（PRD→SRS）补充约束、不变量、接口契约——这些输入直接决定 API 测试和契约测试的范围。

### TB.2 识别测试关联维度

对每个 feature 从多维度分析"谁在依赖它、它依赖谁、出问题影响谁"：

| 关联类型 | 判断方法 | 测试策略 |
|---------|---------|---------|
| **纯后端功能**（无 UI 入口，仅被 API/其他服务调用） | 从 PRD/CMS 入口点判断：有 API 端点但无路由/页面入口 | 重点测 API 契约/边界/性能；不需要前端 E2E |
| **前端功能**（有 UI 入口/按钮/模块） | 有路由/页面/组件引用 | 必须做前端交互测试 + E2E + 视觉回归 |
| **前后端关联功能**（UI 触发 → API 调用 → DB 写入） | 一个用户操作跨 UI/API/DB 三层 | 跨层往返测试（UI→API→DB 状态前后一致） |
| **依赖外部服务**（第三方 API/消息队列/文件存储） | PRD §8 依赖列表 | 契约测试/Mock 测试/超时重试 |
| **共享数据/状态**（多模块读写同一实体） | 同一 DB 表/缓存 key 被多模块引用 | 并发测试/状态一致性测试 |

### TB.3 测试依据输出

产出测试依据表（每功能一行，直接作为 Phase TD 用例设计的输入）：

```
| Feature ID | 功能 | 关联 AC | 关联类型 | 关键业务规则 | 依赖 | 测试风险 |
|------------|------|---------|---------|-------------|------|---------|
| F-001      | 用户注册 | AC-01~05 | 前后端关联 | 密码 8-20 位/邮箱唯一/验证码 60s 过期 | 邮件服务 | 验证码超时边界 |
| F-002      | 数据导出 | AC-12~14 | 后端功能 | 最大 10 万行/CSV 格式/异步任务 | 对象存储 | 大文件 OOM |
```

产物：`docs/analysis/test-basis-{version}.md`（测试依据表 + 关联维度分析）。

## Phase TD：测试用例设计（Test Case Design）

> 从测试依据到可执行的用例，走 7 种黑盒技术系统化枚举——不靠记忆、不靠"想到的就写"。

调用 `[[skill:csp-test-case-design]]`（等价类/边界值/判定表/状态迁移/因果图/Pairwise/场景法）+ `[[skill:csp-qa-test-engineering]]`（测试金字塔分层/策略/计划）+ `[[skill:csp-test-engineer]]`（测试策略/编写/覆盖率分析）+ `[[skill:csp-test-spec]]`（TMS 每模块测试基线，从需求生成测试说明书）。

### TD.1 用例设计路由

按 feature 特征选择主技术 + 必补技术：

| 需求特征 | 主技术 | 用例量级 |
|---------|--------|---------|
| 范围/长度/日期约束 | 边界值分析 | 每输入维度 6-9 条 |
| 枚举/下拉/必填项 | 等价类划分 | 有效类合并 1-2 条 + 每无效类 1 条 |
| ≥3 条件决定一个输出 | 判定表 | 合并后 4-12 条 |
| status/state 生命周期 | 状态迁移 | 迁移数 + 非法迁移数 |
| 用户流程叙事 | 场景法 | 基本流 1 + 备选流 N + 异常流 M |

**硬约束**：
- 每条 AC 至少 1 条用例（P0/P1 的 AC 必须覆盖正常+边界+异常三类）
- 每个无效等价类单独一条用例（不可合并——合并后第一个校验短路，其余分支零覆盖）
- 每个状态迁移必须覆盖 on-switch + 非法迁移（断言"被拒绝 + 状态不变"）
- 每条用例填满 8 字段：ID/标题/前置条件/输入/步骤/预期结果/优先级/关联AC

### TD.2 前端交互用例专项

前端功能的用例必须覆盖用户实际操作路径——不只是"API 返回正确"，而是"用户在页面上点击后看到什么"：

- **按钮/操作可达性**：每个按钮/操作在何种状态下可点/不可点？hover/focus/active/disabled 各态是否正确？
- **模块间联动**：A 模块操作后 B 模块是否同步更新？不刷新页面数据是否一致？
- **前端校验 vs 后端校验**：前端校验通过但后端拒绝 → 用户看到什么？前端校验拦截但绕过 → 后端是否独立校验？
- **异步操作状态**：提交中按钮是否禁用？失败是否有可操作提示（非裸报错栈）？成功后数据是否刷新？
- **浏览器兼容**：Chrome/Firefox/Safari 核心交互是否一致？（可选，按项目要求）

### TD.3 后端功能用例专项

后端功能的用例关注接口行为而非界面：

- **API 契约**：请求参数类型/必填/默认值/边界；响应结构/状态码/错误码是否与 Spec 一致？
- **幂等性**：同一请求发送两次，结果一致且无副作用（扣款/发券类尤其关键）
- **数据完整性**：写入 DB 的数据是否完整？字段类型/长度/约束是否正确？失败是否回滚？
- **并发安全**：并发写同一数据是否产生脏数据？乐观锁/悲观锁是否正确？
- **异步任务**：任务是否被正确投递/执行/重试？失败是否有告警？

### TD.4 用例输出

- `docs/analysis/test-cases-{feature}.md`（完整用例集，表格式）
- `docs/analysis/traceability-{feature}.md`（AC 双向追溯矩阵：AC→用例 + 用例→AC）

## Phase TI：API 与集成测试

> 测服务边界——API 契约、DB 交互、跨服务通信。

调用 `[[skill:csp-api-tester]]`（功能验证/性能/安全）+ `[[skill:csp-cross-layer-testing]]`（UI→API→DB 往返 traceable）+ `[[skill:csp-contract-testing]]`（跨服务契约验证）。

### TI.1 API 测试维度

| 维度 | 测什么 | 怎么判过 |
|------|--------|---------|
| 功能正确性 | 有效输入→正确响应+DB 写入 | 响应结构/状态码/字段值与 Spec 一致 |
| 参数校验 | 边界/无效/缺失参数→明确错误码 | 错误码与 Spec 一致，不泄漏敏感信息 |
| 认证授权 | 无 token/过期/权限不足→401/403 | 未授权不可访问，RBAC 边界正确 |
| 数据一致性 | 操作前后 DB 状态一致 | DB 行数/字段/关联正确，失败回滚完整 |
| 幂等性 | 同请求两次→结果一致 | 无重复扣款/重复创建 |

### TI.2 跨层往返测试

对每个"前后端关联"功能，跑一次完整的 UI→API→DB 往返验证：

调用 `[[skill:csp-cross-layer-testing]]` — 在一个 traceable 的用例中串联三层断言：
1. 前端触发操作（点击/输入/提交）
2. 验证 API 响应（状态码/返回体/错误码）
3. 验证 DB 状态变化（行数/字段值/关联表/事务）

调用 `[[skill:csp-linked-test-runner]]` — 编排一个 feature 的全链路：seed DB → 驱动 UI 动作 → 验证 API → 验证 DB → 清理。

调用 `[[skill:csp-db-state-assertion]]` — 断言一个用户动作前后的 DB 状态变化（哪些行变了、变成什么），并通过 trace id 关联到 API 调用。

## Phase TE：端到端测试

> 测真实用户旅程——关键路径、跨页面流程、浏览器真机。

调用 `[[skill:csp-e2e-testing]]`（Playwright/Cypress/Selenium）+ `[[skill:csp-browser-testing-with-devtools]]`（Chrome DevTools 实机调试）+ `[[skill:csp-e2e-case-automation]]`（E2E 用例自动生成）。

### TE.1 E2E 测试范围

按用户影响面选择 E2E 覆盖路径：

| 路径类型 | 示例 | 覆盖要求 |
|---------|------|---------|
| 核心转化路径 | 注册→激活→首次使用→付费 | 全流程 must-pass |
| 高频操作路径 | 登录→搜索→查看→下单 | 全流程 must-pass |
| 数据变更路径 | 创建→编辑→发布→删除 | 全流程 + 每步后状态校验 |
| 异常恢复路径 | 支付失败→重试 / 网络断开→重连 | 每个异常分支 1 条 |

### TE.2 前端交互验证要点

E2E 测试必须覆盖前端真实交互——不仅仅验证"页面打开展示了"，还要验证：

- **按钮触发链路**：点击按钮 → API 调用 → 响应处理 → UI 更新，整条链完整
- **模块间数据联动**：A 页面操作 → 切换到 B 页面 → B 页面数据已更新
- **前后端校验各司其职**：前端校验拦截的给 UI 反馈、绕过前端直接调 API 的后端必须独立校验
- **状态流转可见**：loading→success→data display 或 loading→error→retry→success，用户在每个状态都有明确反馈
- **边界交互**：快速双击提交（防重复）、后退/前进（表单状态保留）、窗口失焦再回来

产物：`verify/ui-test-report.md`（E2E 测试报告，含截图/网络日志/console 日志）。

## Phase TA：系统审计（Test 之外的另一维——结构健康 × 可用性 × 可追溯）

> 测试回答"代码做对了吗"，审计回答"系统健康吗/可用吗/结构干净吗"。两者互补——功能测试全绿 ≠ 系统没问题。

### TA.1 审计与测试的区别

| 维度 | 测试 (TB–TQ) | 审计 (TA) |
|------|-------------|----------|
| 核心问题 | 功能是否符合 Spec | 系统是否健康、可用、可追溯 |
| 切入点 | PRD AC / 用例 / 边界值 | 模块结构 / 调用链 / 路由 / 代码健康 |
| 典型发现 | "注册表单缺邮箱格式校验" | "3 个模块重复实现了同一逻辑 / 4 个路由无导航入口" |
| 证据类型 | pass/fail + 断言输出 | finding + file:line + 严重度 + 影响分析 |
| 频率 | 每个版本 | 里程碑/大重构后/按需触发 |

### TA.2 审计入口

根据审计目标选择入口：

| 审计类型 | 触发场景 | CSP Skill | 输出 |
|---------|---------|-----------|------|
| **模块化审计 + 可用性审查** | 全面体检：模块健康/联动/Nielsen 10/裁决报告 | `[[skill:csp-audit]]` | `.csp/audit/AUDIT-VERDICT + AUDIT-FINDINGS.json` |
| **E2E 深度审计** | 发布前全量体检：全路由 sweep/按钮级点击/孤儿路由/结构健康 | `[[skill:csp-e2e-deep-audit]]` | `verify/ui-test-report.md + gap-analysis/GAP-REPORT` |
| **代码库审计** | 多维度代码扫描：安全/性能/可观测/架构 | `[[skill:csp-codebase-audit]]` | 各维度 finding 清单 |
| **结构审计**（轻量） | 迭代间快速扫描：死代码/重复/命名/依赖性 | `[[skill:csp-code-simplification]]` | 清理建议 |

### TA.3 审计覆盖维度

每个维度独立审查，finding 带 `file:line` + 严重度 + 修复建议：

| 维度 | 审什么 | 典型问题 |
|------|--------|---------|
| **模块化** | 模块边界/职责/依赖 | 循环依赖/职责重叠/贫血模块/god file |
| **需求可追溯** | 每条需求是否有测试覆盖 | 未覆盖 AC / 单层 happy path 覆盖（视同缺口）/ 孤儿测试 |
| **可用性（Nielsen 10）** | 系统状态可见性/用户控制/一致性/错误预防… | 操作无反馈/无撤销/不一致交互/无键盘可达 |
| **跨层集成** | UI→API→DB 往返是否一致 | 接口 200 但 DB 未落库 / trace_id 断裂 / 回路不闭合 |
| **代码健康** | 死代码/重复实现/命名/类型安全 | 死代码/重复逻辑/类型漂移/import 路径混乱 |
| **安全** | OWASP Top 10/依赖 CVE/权限矩阵 | 注入/越权/敏感数据泄漏/无速率限制 |
| **性能** | N+1 查询/慢 SQL/缓存缺失/首屏 | 热路径无索引/无连接池/首屏 >3s |
| **可观测** | 日志/指标/链路/告警 | 无结构化日志/无 trace_id/无告警 |
| **结构健康** | schema drift/类型检查/mock 债务/孤儿路由 | migration 说 head≠物理 schema / 类型检查失败 |

### TA.4 审计与测试的协作

```
测试 Pipeline                        审计 Pipeline
─────────────                        ─────────────
TB 测试依据（从 PRD）                TA 模块化拆解 + 可追溯缺口
TD 用例设计                          TA 需求→测试方法映射审计
TU/TI/TE 分层实施 ──→ 测试证据 ──→  TA 跨层集成验证（四层断言）
                                       TA 可用性审查（Nielsen 10）
TQ 质量门控 ←── 测试证据 + 审计 findings ──→ 裁决报告
```

- **测试找功能缺陷** → TB–TQ 分层覆盖
- **审计找结构/可用性/健康问题** → TA 多维度扫描
- **06 门控消费两者**：测试 exit 0 + 审计无 CRITICAL → 放行

产出：审计 findings 前缀 `AUDIT-F-NN`，与测试 findings 前缀不同（`GAP-F`/`UI-F`/`CRITIC-F`），可并存去重。P0 findings 标 `快速修复=true` 直发 04→05→06，P1/P2 走 roadmap 正常路径。

## Phase TSEC：安全测试

> 测系统安全边界——鉴权、注入、越权、敏感数据。

调用 `[[skill:csp-security-review]]`（鉴权/越权/注入/XSS/CSRF/敏感数据脱敏/依赖漏洞）+ `[[skill:csp-api-tester]]` 的安全测试模式（OWASP API Top 10）。

### TSEC.1 安全测试清单

| 类别 | 测试点 | 方法 |
|------|--------|------|
| 认证 | 弱密码/token 过期/会话固定/多设备登录 | 手动 + 自动化 |
| 授权 | 水平越权（访问他人数据）/垂直越权（低权限访问高权限） | 每角色每端点验证 |
| 注入 | SQL/XSS/命令/模板注入 | 自动化扫描 + 边界输入 |
| 数据保护 | 敏感数据加密存储/传输/脱敏显示/日志不泄露 | 读代码 + 读日志 |
| CSRF | 状态变更操作是否有 CSRF token | 自动化验证 |
| 依赖漏洞 | npm/pip/cargo audit | 自动化扫描 |

## Phase TQ：质量门控与上线验证

> 所有测试跑完后，过门控——决定能不能上线。

调用 `[[workflow:csp-verify-phase]]`（AC 验证/测试全绿）+ `[[workflow:csp-release-manager]]`（完整质量门控）+ `[[skill:csp-ultraqa]]`（QA 循环工作流：测试→验证→修复→重复直到目标达成）。

### TQ.1 质量门控矩阵

| Gate | 条件 | 不通过→ |
|------|------|---------|
| **代码门控** | Lint + TypeCheck + Build exit 0 | 阻塞 merge，回 05 |
| **单元测试门控** | 业务逻辑 ≥80%，工具函数 ≥90%，exit 0 | 阻塞 merge，补测 |
| **API 测试门控** | 全部端点覆盖 + 边界/错误码/幂等 exit 0 | 阻塞 merge |
| **E2E 测试门控** | 核心路径 all-pass + 新 feature 关联路径 all-pass | 阻塞 merge |
| **视觉回归门控** | 截图 diff = 0（排除已知预期变更） | 若为意外变更→回 05 |
| **性能门控** | P95 ≤ SLA，无退化 >15% | WARNING（不阻塞，记入下版本优化） |
| **安全门控** | 无 CRITICAL/HIGH 漏洞；依赖 audit exit 0 | 阻塞 merge（CRITICAL/HIGH） |
| **AC 验收门控** | 每条 AC 有对应用例且用例通过 → [[workflow:csp-verify-phase]] | 阻塞 release |
| **跨层一致性** | UI→API→DB 往返验证通过 → [[skill:csp-cross-layer-testing]] | 阻塞 release |
| **上线冒烟** | 生产环境关键路径通过（post-deploy smoke） | 触发回滚 |

### TQ.2 上线验证

部署后跑确认：

- **冒烟测试**：生产环境核心路径自动化验证（登录/注册/核心购买流程）
- **DB 迁移确认**：Schema 变更是否在生产正确执行？数据完整性？
- **可观测确认**：关键指标/日志/告警在生产中是否正常产出？→ `[[skill:csp-observability-testing]]`
- **功能开关确认**：新功能是否按预期开启/关闭？灰度比例是否正确？

### TQ.3 测试复盘

调用 `[[skill:csp-defect-mining]]` — 测试套件达到平台期时换方法挖掘新缺陷。
调用 `[[pattern:csp-ai-regression-testing]]` — AI 生成代码的已知缺陷模式回归。

输出 `docs/analysis/test-retro-{version}.md`（测试覆盖率/漏测分析/下版本改进）。

## 反模式速查

| 反模式 | 症状 | 正确做法 |
|--------|------|---------|
| 测试后补 | 代码写完再补测试 | TDD——先有测试依据→用例设计→测试代码→实现代码 |
| happy path 全覆盖 | 只测正常流程 | 每个无效等价类独立用例；每个非法迁移单独验证 |
| 测试与 PRD 脱节 | 测了但不知道测的是哪个 AC | AC 双向追溯：AC→用例 + 用例→AC |
| 前端只测 API | 只验证接口返回，不验证 UI 实际渲染 | E2E + 视觉回归 + 联动验证 |
| 后端不测前端关联 | 认为"API 正确=前端正确" | 跨层往返：UI→API→DB 三层断言一致 |
| E2E 替代分层 | 全写 E2E 不写单元测试 | 测试金字塔：单元 60% + 集成 25% + E2E 5-10% |
| 只看覆盖率数字 | 80% 覆盖率但全是 happy path | 覆盖率+等价类/边界/迁移覆盖率 |
| 不测 DB 状态 | 只断言 API 响应 | DB 前后状态断言 + 事务回滚验证 |
| 上线不冒烟 | 部署完就算上线 | 生产环境关键路径冒烟 + DB 迁移确认 |
| 漏测不补回归 | 线上 bug 修完不加回归测试 | 每个线上 bug → 至少 1 条回归用例 |
| 只测不审 | 功能测试全绿就当系统没问题 | 审计（TA）独立于测试——结构健康/可用性/模块化/可追溯缺一不可 |

## Phase G1：版本与变更管理

### G1.1 版本号管理

调用 `[[skill:csp-git-conventions]]`（Conventional Commits/原子提交/Tag 纪律）+ `[[skill:csp-changelog-management]]`（CHANGELOG 追加/分类/格式）：

- **SemVer X.Y.Z**：MAJOR=breaking / MINOR=additive / PATCH=fix

> **MINOR (Y) 是攒批发布，不是一个功能一个版本**：同一模块的多个功能打包成一个 MINOR+1 版本（不设硬上限——模块内有几个相关 feature 就打包几个），不逐功能 bump。只有不同模块/主题方向不同/体量过大才拆到下一版本。"一个版本一个功能"是模块内恰好只剩一个功能时的特例，不是默认形态。

- **feat/fix 分轨**：feat 批打 MINOR+1 tag，fix 批打 PATCH+1 tag；同迭代两者兼有 → 拆两个发布，不混合
- **Tag 格式**：`v` 前缀 + annotated（`-a`）+ 不可变（已推送不移动）
- **一 commit 一 tag**，禁多 tag 同 commit
- **纯文档 commit 禁打版本 tag**
- 详细版本号规则见 `prompts/version-management.md`

**多文件版本同步**：版本号是一个事实，但各生态工具各认各的文件。原则：**一处定义、多处派生、脚本校验、禁手填**。

| 文件 | 角色 | 同步方式 |
|------|------|---------|
| `VERSION` | 单一真相源（开发期 canonical） | 手改（唯一可手改的文件） |
| `git tag` | 发布锚点（发布后 canonical，不可变） | `git tag -a vX.Y.Z -m "..."` |
| `package.json` | 打包消费 | 从 VERSION 同步（`scripts/sync-version.mjs`） |
| `pyproject.toml`（如有） | 打包消费 | `dynamic = ["version"]` 或 sync 写入 |
| GitHub Release tag_name + title | 发布元数据 | 从 tag 自动创建 |
| `CHANGELOG.md` 最新条目 | 发布历史 | 发布时校验 == tag |

**同步校验**：发布前必须跑 `python3 prompts/scripts/version_integrity_check.py`——全源字符串完全一致，任一不一致 `exit 1` 阻断发布（T3 gate）。

**冲突消解**：若 `package.json`/`VERSION` 与已发布 `git tag` 不一致 → 以 tag 为 canonical，自动 bump 文件到 tag 版本，不问（仅多 tag 冲突/canonical 不明才人工）。开发期间（tag 未打）→ 以 `VERSION` 为 canonical，所有文件从它派生。

### G1.2 Commit 规范

Conventional Commits 格式（遵循 `[[pattern:csp-git-conventions]]` §3）：

```
<type>(<scope>): <subject>

[body]

[footer]
```

| Type | 用途 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(auth): add OAuth2 login` |
| `fix` | Bug 修复 | `fix(api): handle null user session` |
| `docs` | 文档变更 | `docs(readme): update install guide` |
| `refactor` | 重构（不改功能） | `refactor(db): extract query builder` |
| `test` | 测试相关 | `test(e2e): add checkout flow test` |
| `chore` | 构建/工具/依赖 | `chore(deps): bump react to 18.3` |

### G1.3 README 维护

每个版本发布时，检查并更新 `README.md` 的必要节：

- **项目简介**——项目是什么、解决什么问题
- **快速开始**——最小可运行步骤（clone → install → run）
- **项目结构**——顶层目录说明（链接到完整结构文档）
- **开发指南**——如何参与开发、环境要求、常用命令
- **版本历史**——链接到 `CHANGELOG.md`
- **许可**——LICENSE 引用

调用 `[[skill:csp-file-organizer]]` 在迭代间隙清理项目文件（重复文件/临时产物/过期文档归档）。

## Phase G6：产物大小治理

> 持续迭代的项目会积累大量产物——日志、changelog、ROADMAP、PRD、验证基线——这些文件天然持续增长，不加管理会导致 Agent 上下文超限、构建变慢、仓库体积膨胀。

### G6.1 按产物类型的治理策略

| 产物类型 | 增长模式 | 治理策略 | 工具 |
|---------|---------|---------|------|
| **日志** (`logs/*.log`) | 线性无限增长 | `.gitignore` 排除；日志轮转保留 7 天 | logrotate / 脚本清理 |
| **缓存** (`.mypy_cache/` `.pytest_cache/` `.turbo/`) | 工具自动重建 | `.gitignore` 排除 | gitignore |
| **数据库备份** (`data/backups/*.db`) | 每次备份产生新文件 | `.gitignore` 排除；保留最近 5 个，清理 >30 天 | cron / 脚本 |
| **CHANGELOG** | 每个版本追加一段 | 按年拆分：`CHANGELOG-{year}.md` → `docs/archive/changelogs/` | 手动 / 发布脚本 |
| **ROADMAP** | 每个版本追加一行 | shipped/deferred 版本保留 1 行摘要，详情移入 `ROADMAP-ARCHIVE.md` | Phase 2.5 审视时执行 |
| **PRD** (>80KB) | 单个 PRD 逐渐膨胀 | 拆分为主文档 + `PRD-{slug}-appendix.md`；已交付 2 个版本的 PRD 移入 `docs/archive/prd/` | 01 PRD 评审后 |
| **验证基线** (`.csp/artifacts/verify/`) | 每次回归产生一个目录 | 保留最近 3 个基线；更早的移入 `.csp/artifacts/archive/verify/` | 06 发布后 |
| **manifest.json** | 每次产物落盘追加索引项 | Registry 自身管理；超过 1MB 自动分片到 `.csp/manifest-shards/` | 构建脚本 |
| **第三方参考代码** (`docs/research/open-source-references/`) | git clone 包含完整 `.git/` 历史 | **禁止放入 docs 树**。使用独立 `references/` 目录或 submodule；用脚本同步，不入主仓库 | `.gitignore` + 脚本 |

### G6.2 单文件大小阈值

| 阈值 | 处理 |
|------|------|
| **50KB** — 通知阈值 | 新增/修改超过此值的 `.md` 文件，Agent 在下次操作时主动提示是否可拆分/归档 |
| **100KB** — 警告阈值 | 超过此值的文件在下一轮规划/发布时必须拆分（主文件 + archive）或归档 |
| **250KB** — 硬上限 | 除 registry.json / triggers.yaml（由构建系统托管）外，所有 `.md` 文件禁止超过此值 |
| **1MB** — 分片阈值 | registry.json / manifest.json 目标：构建脚本在接近此值时自动启用分片 |

### G6.3 定期归档节奏

| 时机 | 动作 |
|------|------|
| **每次 Phase 2.5 审视后** | ROADMAP 检查 `shipped` 版本 >20 个 → 最早 10 个移入 `ROADMAP-ARCHIVE.md` |
| **每次 06 发布后** | `.csp/artifacts/verify/` 保留最近 3 个基线，其余移入 archive |
| **每季度** | 清理 `data/backups/` 中 >30 天的备份 |
| **每年 1 月** | `CHANGELOG.md` 按年拆分，旧年移入 `docs/archive/changelogs/` |
| **PRD 交付后** | status=Approved 且已发布 ≥2 个版本的 PRD → 移入 `docs/archive/prd/` |
| **PRD 评审时** | >80KB 的 PRD → 拆分为主体 + appendix |

### G6.4 归档目录结构

```
项目根/
├── docs/archive/                  # 对外文档归档
│   ├── changelogs/                # CHANGELOG-2025.md, CHANGELOG-2026.md ...
│   ├── prd/                       # 已交付版本的 PRD
│   └── ROADMAP-ARCHIVE.md         # shipped/deferred 版本的历史详情
├── .csp/artifacts/archive/        # Agent 产物归档
│   └── verify/                    # 历史验证基线
└── references/                    # 外部参考项目（git submodule 或脚本同步）
    └── open-source/               # 竞品/参考开源项目
```

### G6.5 大文件检查脚本

`scripts/check-large-files.sh`：

```bash
#!/bin/bash
# Check project files against size thresholds
WARN_KB=50
HARD_KB=200

echo "=== Files > ${WARN_KB}KB (consider splitting) ==="
find docs/ prompts/ -type f \( -name '*.md' -o -name '*.json' \) \
  -size +${WARN_KB}k \
  -not -path 'docs/archive/*' \
  -not -path 'docs/research/*' \
  -exec ls -lh {} \;

echo ""
echo "=== Files > ${HARD_KB}KB (MUST split or archive) ==="
find docs/ -type f -name '*.md' -size +${HARD_KB}k \
  -not -path 'docs/archive/*' \
  -exec ls -lh {} \;
```

可作为 pre-commit hook 或 CI 检查项，建议集成到 `.github/workflows/` 中。
